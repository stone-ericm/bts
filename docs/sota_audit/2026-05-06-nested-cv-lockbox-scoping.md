# Nested CV / Lockbox Scoping

## Verdict

#5 is no longer accurately described as unstarted. The manifest-based validation contract exists:

- `bts validate split-manifest` writes a rolling-origin, purged split manifest with an explicit lockbox.
- `bts validate scorecard --manifest`, `bts validate conformal-gate`, `bts validate policy-value-eval`, and `bts validate rare-event-ce-is` consume that manifest and hold the lockbox out.
- The current durable split evidence is `data/validation/split_manifest_conformal_2026-05-06.json`, generated by the same split-manifest command and used by the conformal v2 refresh.

The remaining #5 problem is not the absence of lockbox infrastructure. It is uniform adoption and nesting discipline across all audit paths. Some paths are manifest-bound; others are descriptive, harness-specific, or seed-axis screens.

## Interpretation

Out-of-fold, leave-one-season-out, and leave-one-seed-out evidence are not interchangeable with a lockbox. OOF predictions can still share hyperparameters, thresholds, feature choices, or policy choices selected using the same outer evaluation span. Seed-axis LOO can be a useful determinism or provider robustness check, but it does not answer calendar-time leakage.

The uniform #5 contract should separate three roles:

- Outer temporal evaluation: rolling-origin folds or season/month holdouts, with fold-train strictly before fold-holdout.
- Inner tuning: any hyperparameter, feature, threshold, or policy-selection decision must use only data inside the outer train span, with its own time-respecting split.
- Lockbox: a future segment reserved for final go/no-go claims, never for tuning.

The existing conformal v2 path is the clean example to build on: manifest in, lockbox held out, result records `manifest_metadata` and `lockbox_held_out`.

## Next Work

This slice does not retrofit the runners. The next implementation slice should choose one path and make the split contract executable there:

- apply a manifest/lockbox mode to the falsification harness, or explicitly document why its latest-season holdout remains a separate falsification-only surface
- add a nested, time-respecting inner split to `bts experiment screen/select` so feature selection is not decided on the same dates used for outer scoring
- produce a dedicated lockbox certification artifact once a candidate production change exists

Until then, #5 should be considered infrastructure-present but adoption-incomplete.
