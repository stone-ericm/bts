### B4 — P1: LimitCPU does not bound the unit's cumulative CPU consumption

`scripts/audit/c1/launch.py:130–137` applies `LimitCPU=<declared CPU seconds>` and `RuntimeMaxSec`, but has no monitor of the unit's cumulative cgroup CPU time. `LimitCPU` is a per-process CPU resource limit. A command spawning children can exceed both its declared total CPU budget and the remaining cycle CPU budget without any individual process exceeding its inherited limit.

**Measured locally on synthetic processes:** a parent with `RLIMIT_CPU=(1,1)` spawned two sequential children that each consumed approximately 0.6 CPU seconds. Both children and the parent exited 0; cumulative parent-plus-child CPU was **1.244836 seconds**, exceeding the one-second limit. This verifies the resource-limit semantic issue, not Linux/systemd execution on the box. The mapping from the generated `LimitCPU` property to that resource limit and the lack of a cgroup-budget monitor are static findings. The existing box burner observation in the cycle index proves the single-process case only.

**Smallest fix:** enforce declared and remaining-cycle budgets against cumulative unit/cgroup CPU consumption, kill the whole unit at the bound, and retain a cycle-pause record. Verify with multiple child processes, not only a single burner. The 4-hour limit is otherwise defensible for the current single-process 4b evaluator, but the reviewed general C1 launcher does not support its claimed guarantee.

### B5 — P1: an overrun does not pause C1, and launch admission is not atomic
