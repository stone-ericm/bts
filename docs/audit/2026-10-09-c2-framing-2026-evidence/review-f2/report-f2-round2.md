### Implementability and required design revisions

**1. Make reservation issuance a trusted, serialized C1 operation.** As written, a caller can choose a fresh nonce, exclusively create a reservation for a permitted seed/budget/cap with small declared totals, invoke ordinary C1 with a command that sets that nonce, and let the real guarded payload exclusively consume it. Genuine C1 receipts can then accompany the forged combined decision. This uses the authentic C1 producer for its existing ledger-only check; it does not require forging that producer's records. The proposed acceptance predicates all agree, but none proves the wrapper checked the real combined balance. Randomness prevents guessing an existing nonce; it does not prevent creating a new one. Hard-link publication also does not make the linked bytes immutable.

Choose the issuer and its trust rule. A workable direction is a reviewed C1 planning/start operation that validates the combined inputs under its existing lock, chooses the unit, and publishes a reservation/receipt bound to that unit and fixed admission/pins/allowance/account snapshot before starting it. The payload validates that issuance against a trusted C1 record rather than merely another f26 output. Define exact schema/nonboolean numeric checks, sums, source-record identities/digests, expiry/abandonment or reconciliation rules, and an accepted command/admission identity. If the alternative is to trust an operator always to use the wrapper and never to manufacture/change reservation files, say that explicitly and narrow the code guarantee; that is not the claimed closure of the arbitrary-C1-command bypass.

**2. A status call is a refresh, not a transaction spanning launch.** Actual C1 `main` acquires `launch_lock` only for that invocation (`launch.py:428` onward). `_locked` sweeps/reconciles and returns status, and the lock then ends. The later C1 run reacquires it and performs its own ledger-only decision. A hypothetical ledger of 150 hours plus 1 off-launcher hour can admit a 12-hour reservation. An intervening completed C1 job using 2.5 hours leaves the eventual C1 ledger-only check at 164.5, still allowed, while the combined total plus reservation is 165.5. These numbers illustrate the source-level interleaving; they are not measurements of a real job. Outstanding reservations and intervening off-launcher charges also need serialization or a specified one-writer policy.

The real status command returns zero even with an active unit; it skips reconciliation in that case and reports active/gate/stops in JSON. It is not a successful-admission signal. `sweep` also reads a missing ledger as empty and writes a fresh header; malformed header-only input can likewise be replaced. Thus the stated “status first, only then read the ledger” can erase the missing/header evidence boundary 7 is supposed to reject. Require validation of the original records before a destructive refresh, explicit active/unreconciled refusal, and final combined admission plus unit/reservation publication/start under one serialized operation. Holding the lock externally and then calling the present C1 CLI is not a fix: its nonblocking flock attempt will refuse the nested launcher. The note must specify an integration/interface change, not assume the two existing subprocess calls share a lock.

**3. Specify the accounting phases and receipt identities.** Before prepare, require the ruled seed and valid authoritative ledger, not successful prepare/expect rows. Before expect, require the completed preparation and its matching account receipt. Before the first launch, require completed prepare/expect; before later launches, require the accounted/reconciled predecessors; at aggregate, include all ten units and attempts. Link receipts by admission/preparation/expectation digest and attempt/nonce/unit, rather than step names alone. Define begun, admitted, refused, failed, unresolved and completed states, with unknown costs pausing continuation. A refusal from C1 after the reservation was written cannot obey the current unconditional statement that a refused launch writes no reservation; it must retain and reconcile/abandon the intent.

The exactly-one admitted launch row rule must mean one selected successful run, with every other attempt retained, charged and judged. Otherwise a genuine C1 start failure before a payload claim, followed by Eric's recorded recovery and an acknowledged invocation, can conflict with boundary 12's permitted history. Define the separate C1 RESUME/invalidation/acknowledgment requirements and whether they authorize retry; an acknowledgment is not a blanket release of every gate. Define CONSUMED/claim publication under the claim lock too: the note wants consumption before the claim while recording that claim. Precompute a bound identity or use an explicit durable transition, and state the recovery for a crash on either side. Never make a validation call consume the reservation again or re-reserve the full budget already owned by the active unit.

**4. Define complete CPU observation and disjoint charge ownership.** A process sampling at its finally still has to serialize/fsync the account row, print/return, run other finally handlers and exit. It cannot report its own eventual complete lifetime CPU from that earlier sample. Either use a supervising measurement after wait with a accounted/bounded observer, or carry a conservative enforced reserve/settlement rule for the unobserved tail and crashes. Ordinary Python finally does not run on SIGKILL or interpreter/process death. The manager's backstop must be incorporated before continuation when a completion receipt is absent; merely mentioning it does not charge it.

The current `screen.cpu_seconds` adds RUSAGE_SELF and RUSAGE_CHILDREN (`screen.py:283`), while f26 separately records launcher child rusage. Extending the wrapper's charge through child completion using that clock and also summing a launcher-process row counts that child twice. Define self versus child sources, including the new status child and its waited descendants, so each CPU contribution has one additive owner. Guarded payload/guard CPU already belongs to C1; do not charge it again merely because it is a CLI invocation. Also state how seed-record startup, failed pre-entry imports, final accounting writes and aggregate output/exit are covered. Artifact `cpu_s_at_write` values should have an explicitly named relationship to authoritative completion charges, not an implied equality.

A reservation at exact combined-cap equality leaves no allowance for later off-unit launcher/settlement work or the final aggregate. Reserve those bounded future costs before launch, and give final effective-cap exhaustion/unknown-cost conditions an explicit stop/report rule before acceptance/opening. Boundary 13 currently requires account completeness and charges its own CPU, but does not say that exceeding the cap invalidates continuation. Accounting scope may honestly depend on trusted numbers/history; even under that assumption the proposed arithmetic must avoid both omitted CPU and false over-cap refusals from double-counting.

**5. Keep the plan certificate distinct and make the REDs behavioral.** I exercised only the current pure certificate helpers on synthetic text: a SIGN with this note commit plus an explicit design-only/no-code-admission sentence returns no certificate problem. This is not a full admission or exposure experiment; it confirms the parser lacks a review-kind check. Boundary 0 must identify the later fresh code-review certificate as the eligible one, so a plan SIGN cannot admit the unchanged blocked implementation.

Round-5 items 1 and 4 can be tested as behavioral REDs directly against the current public functions with coherent artifacts and valid controls. Item 2 must first settle the accounting state machine; item 3 cannot be implemented soundly as just status plus a new f26 file. Add negative tests for a fabricated fresh reservation with the right seed/cap/nonce, a genuine reservation rebound to another unit/claim/admission, and the intervening-ledger change; add valid-sequence controls for first prepare/expect, exact boundary reservations with separately budgeted overhead, acknowledged start failure/recovery, nullable catcher ids, and no double-counted CPU. Test the actual argv/guard environment path and genuine C1 record constructor, not a guard stub that predetermines acceptance. C1 exposes arbitrary commands as a remainder passed into the guard; supplying an environment variable is implementable with an actual environment-setting command or a reviewed launcher option, but a caller-supplied environment variable is not an authorization source.

Current fixtures often begin with no C1 ledger and only a prior row. Give controls the legitimate required accounting history before testing a different refusal, or new accounting/nonce checks will mask older boundary tests. New tests must not depend on a nonexistent API at setup; call the existing boundary and assert the missing refusal first. Compile/unique anchors and nonempty selectors are necessary checks for M115+, but mutation execution remains paused and none is evidence until run. This avoids repeating the round-four missing-attribute RED pattern.

Boundary 15 is honest about probabilities, retained membership and ties, but should expressly include the related limit that a correct recipe declaration is not independent proof of which fit produced the probabilities. Its raw-derivation limit is honest once 5 binds genuine prepared inputs; it also retains the frozen starter-proxy, official-date/resumed-event availability and serving-availability assumptions, rather than proving pre-pick validity. Boundary 7 candidly limits authentication of manual history/numbers; its present “complete CPU” promise is incomplete until observation, crash/recovery and additive ownership are defined.
