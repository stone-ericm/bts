## Findings

### C2R1-1 — Medium: the schedule discriminator bypasses typing of the reconciliation operand and permits incompatible request identities

**Locations:** `scripts/audit/c1_r3/count_build.py:183–193,217–221,232–241,264–270`.

`_typed_requests` validates a feed's `gamePk`, but validates only `season` when `kind_of` is `schedule`. It accepts a schedule record containing an arbitrary non-null `gamePk`. Immediately afterwards, `unresolved` hashes and compares `(attempt_id, gamePk)` for **every** completion and intent. That key contains neither request kind nor schedule season. Thus not every value reaching the join has passed its appropriate type check, despite the new function's stated contract.

Independent actual-`main` reproduction, alongside a valid receipt-bound game-7 feed and its pinned synthetic PA parquet:

```json
{"kind":"intent","attempt_id":"z","gamePk":8,"url":"https://statsapi.mlb.com/api/v1.1/game/8/feed/live","started_utc":"2026-10-04T23:00:00+00:00"}
{"kind":"completion","attempt_id":"z","kind_of":"schedule","season":2023,"gamePk":8.0,"url":"https://statsapi.mlb.com/api/v1.1/game/8/feed/live","outcome":"network_error","ended_utc":"2026-10-04T23:00:01+00:00"}
```

Both records pass the new validator: the intent has integer game 8, and the completion has integer season 2023. There is one intent and one completion for z, so neither witness map sees a duplicate conflict. Python then considers `(z, 8.0)` equal to `(z, 8)`, removing z from the unresolved set. The error completion is never selected for stored-feed binding.

**Measured result:** return 0; eligible=certified=1; quarantined=0; rate=0.0; one `CLAIM.json` and `results.json`; `count_table.json` and `bf_starts.json` published, with two BF start rows. PA and feed bytes were consumed. This is the old malformed-error reconciliation failure with two additional supported-discriminator fields, rather than an unavailable game counted toward the quarantine limit.

Two related compositions also published the same certified outputs:

1. A schedule intent s with `gamePk=null, season=2023`, followed by its sole schedule error completion s with `gamePk=null, season=2024`. Both primary identities are typed, but the reconciliation key is `(s, None)` in both cases. The completion for another season resolves the intent.
2. Change only the valid legacy game-7 **intent** to `kind_of="schedule", season=2023`, keeping its integer `gamePk=7` and feed URL. Its unchanged feed stored completion resolves it. The later stored-request check compares game IDs and URLs but not request kinds, so that contradictory request declaration can anchor a certified feed.

These records are deliberately incompatible synthetic witnesses. I found no evidence that either producer emits them or that they occurred historically. The defect is admitting unsupported/contradictory provenance, not a measured wrong historical count. `unresolved` itself is unchanged from r4: this is an uncovered limitation of the new validator and the claimed R4-1 closure, not a newly demonstrated numerical regression. The modern writer's real schedule shapes use null `gamePk` on request/response records and omit it on the separately identified stored record; preserving those shapes does not require accepting the witnesses above.
