## Part B

### B1 — a blocked long chain can indefinitely starve an independent alert

**Production defect, reproduced at the default bound.** `_claimable` stops selecting other targets once the number of *claimed notices* reaches `max_sends` (`notify.py:337–342`). A chain is taken whole. The send loop correctly releases successors after a failed head, but does not use the resulting unused send capacity to admit another target (`:362–387`). Consequently, one blocked chain can reserve the allowance on every run while attempting only one send.

Independent sequence, produced entirely by legitimate `enqueue` calls:

1. In queue-only mode, enqueue ten fault → verified cycles for target A, then another A fault. This leaves 21 notices across 11 valid episodes.
2. Enqueue an independent target B's fault. Its fake transport would succeed.
3. Flush with the default `max_sends=20`; only A's first notice raises a definite send failure.
4. Repeat with fresh notifiers, preserving state.

Each of four flushes returned:

```text
sent=0, failed=1, held=20, skipped_budget=0
B: status=pending, attempts=0
total attempted sends across all four flushes: 4, all for A
```

There is no crash, lease expiry, clock rollback, exhausted monotonic budget or corrupted state. Every state loads successfully. B is never attempted despite 19 unused send slots per flush. Since the failed head and held tail remain pending, the same claim selection repeats indefinitely while that head fails. The minimal version also reproduces with A's three-notice fault/recovery/recurrence chain and `max_sends=2`.

This contradicts the design's “Other targets continue” claim and R3-2's requirement to keep independent targets able to progress. The existing `test_r32_a_blocked_target_does_not_block_other_targets` uses only two A notices and the default allowance of 20 (`test_w0_r3_repair.py:281–290`), so B is already in the initial claim set. It passes with this defect. The long-chain bound test has no independent target. M27 and M28 test whole-chain reclamation and the send count, not unused-capacity starvation.

### B2 — impossible confirmation metadata is accepted and permanently suppresses a real queued fault

**False acceptance with silent loss, reproduced.** Validation checks only the equivalence between `status == "sent"` and a nonempty string `message_id` (`notify.py:158–159`). It does not require a sent notice to have a recorded attempt, a recipient or `last_attempt_at`.

Start with a real queue-only fault. Change just its delivery status and message ID:

```python
notice.update(status="sent", message_id="fabricated-id")
# Retained from the actual queue record:
# attempts=0, recipient=None, last_error=None, no last_attempt_at
```

All keys, sequence and lifecycle records remain intact. `load_state` accepts it. Enqueueing the identical continuing fault returns `new_notices=0`; configured `flush` returns all-zero counters and makes no fake send. The accepted impossible “sent” record silences the alert permanently under ordinary repetition.

The protocol cannot produce this combination: a successful completion increments attempts, records `last_attempt_at`, and stores the configured recipient in the same atomic save (`:393–408`). Detecting those missing relationships requires no transport authenticity assumption. This finding does **not** claim that validating a file can authenticate an arbitrary plausible message ID; it concerns a visibly impossible combination that current validation accepts. Both independent refusal tests, through `enqueue` and through `flush`, fail because no `NotifyStateError` is raised. Neither the shipped corruption tests nor M01–M28 cover it.

### B3 — the shared-lease invariant is assumed by reclamation but never validated

**False acceptance followed by rejection of a legitimate completion, reproduced from a corrupted state.** The whole-chain repair depends on all `sending` notices of a target sharing one claim time and lease. This is explicitly the reason given in the design and commit `808ae12`. `_validate` parses each notice's timestamps separately (`notify.py:160–164`) and checks status rank order (`:205–207`), but never verifies that relationship.

Using a real queued fault/recovery pair, plant two individually well-formed `sending` records with distinct tokens and these times:

| Notice | Claimed at, UTC | Lease until, UTC | At the test's 16:00Z observation |
|---|---|---|---|
| Fault | 15:40Z | 15:50Z | Expired |
| Recovery | 16:00Z | 16:10Z | Live |

`load_state` accepts this state. A configured flush reclaims only the expired fault, stops at the live recovery, and attempts the fault. When that fake send definitely fails, recording the result would produce `pending, sending`. `save_state` then raises:

```text
NotifyStateError: target …: a notice was delivered or claimed ahead of an earlier one
```

The on-disk pair remains `sending, sending`, and the failed attempt is not recorded. With the fixed observation clock, repetition takes the same path. With advancing time, the second lease may eventually expire; this probe does not establish permanent failure under all clocks.

I did **not** produce the split-lease state through legitimate operations. This is a missing corruption check, not evidence that the repaired writer itself emits it. Nonetheless, accepting it before action reintroduces the exact partial-reclaim shape the author's whole-chain fix was meant to exclude. Independent tests through both `enqueue` and `flush` show that it is acted on rather than refused untouched before any send. Distinct per-notice tokens are legitimate; the missing relationship is the common claim/lease times, not token equality. No ledger mutant exercises this relationship.
