## Verdict

**REVISE.** Reviewed at `d3d10e9533541f430789c025b96fe75e6f8d8d15`. The shared-writer serialization approach is viable, but the draft does not yet establish the closure required by registration lines 65–66. It omits live pick deletion, state regeneration, and conditional policy-shadow writers; leaves logical transaction completion undefined; and allows old processes to mutate a supposedly current generation without advancing its counter. A best-effort counter failure also contradicts the promised failure isolation. These are protocol decisions, not implementation details that can safely be left to code.

The scheduler risk is understated. Wrapping the delivery function would hold the lock across posting/DM and a subprocess trigger. Wrapping individual saves would instead publish intermediate pick/decision states. Neither is the claimed unchanged, sub-second transaction. No timing, size, installed-process, or production measurements were made in this review.

This is a source-only design review. I read the draft, registration, build plan and relevant code in this checkout; reverse-searched named save helpers, atomic-write helpers, direct writes, renames and deletions. I ran no tests or application paths, used no network, and read no runtime data, configuration, credentials, memory or notes. The only write is this ignored report. This verdict neither authorizes implementation repairs nor D7 deployment/A8 activation.

## Option A

**A1 — Serialization can exclude interleaving; it does not by itself certify completion.** Specify the actual logical groups, not just “every call site wraps its read-modify-write.” The scorer's group is its locked fresh reload, streak update and pick save. Reconcile's group includes all corrections and its subsequent streak write. A delivery attempt marker, successful delivery metadata, and its decision currently span separate saves and external work. A lock inside each helper would emit separate snapshots of partial groups. A lock around the whole function would include external work. Neither ambiguity can remain in the design.

Define a durable transaction identity and lifecycle: begun/pending, completed with the actual observed write outcomes, failed/unclosed, and the qualified disposition that permits subsequent captures. Bind outer transaction, root, epoch/season, process/run and loaded producer revision to the generation; a caller-provided `writer` string is not that identity. Do not derive the executing revision solely by running `git rev-parse` on a tree that can be replaced while an old process lives.

The existing best-effort functions make this distinction necessary: `write_decision` returns `None` on any caught exception (`daily_decision.py:105–106`), `_record_commit` swallows exceptions (`scheduler.py:956–965`), and the end-of-day skip caller ignores the return. “The context exited normally” does not prove all relevant saves completed. Mark unavailable/failed evidence without changing those business outcomes; never manufacture a successful complete transaction from the remaining bytes.

**A2 — The exit and next-writer rules must pass real interruption tests.** A `SystemExit` executes a context manager's cleanup; an unconditional publish-on-exit can seal exactly the partial state the test is intended to reject. A process kill bypasses cleanup and releases its kernel lock. Specify no completion publication on exceptional/unclosed exit, and handle both cases. After transaction N dies between saves, an unrelated successful writer N+1 must not silently erase the unresolved group and upgrade its outputs to healthy closure. Carry the transaction disposition until a reviewed closure/failure criterion is met. This need not repair production state. A coherent physical copy can be retained for diagnostics while the multi-file verdict remains pending/unverifiable.

**A3 — Best-effort begin/counter failures are a correctness conflict.** The draft handles publication failure after mutation by leaving the counter ahead, which works only if advancing that counter succeeded. Counter write/rename/fsync failure **before** mutation, followed by guarded continuation, can leave a readable old counter equal to an old sealed manifest while application bytes change. Returning “snapshot unavailable” in the failing writer is not enough to inform an independent reader.

The design must choose and justify a mechanism that durably invalidates acceptance before any relevant mutation. If that invalidation cannot be made durable, guaranteed fail-closed evidence and unconditional unchanged writer behavior cannot both be promised. State the refusal/quarantine/availability policy and any necessary separate scope decision under registration line 56. Do not quietly turn evidence errors into delivery exceptions or, conversely, allow them to leave old evidence accepted as current.

Specify durable ordering for epoch/begin records, transaction outcomes, counter, blob bytes and manifest acceptance, plus recovery from missing/corrupt metadata and counter rollback/reset. `util.atomic_write_text` fsyncs the file and replaces it but does **not** fsync the parent directory (`util.py:20–31`); it cannot alone justify crash-durable counter ordering. Distinguish process-kill guarantees from host-crash/restart guarantees, and either establish durable live-output namespace correspondence or invalidate/rebaseline on restart before a pre-crash generation is called current.

**A4 — Reader acceptance and freshness are underspecified.** Select numeric generations, not lexical filename order (`gen-10` versus `gen-9`). Require matching root/epoch/schema/season, valid transaction closure, sealed untombstoned manifest, complete inventory and verified referenced blob bytes. Missing/corrupt counter, unknown epoch, duplicate/conflicting generation or absent blob means unavailable, not fallback success. No ABA across restore, reinstall, rollback or season change: generation number alone is insufficient.

Bracket manifest/blob validation and replay with counter/epoch/lifecycle reads. If a writer starts during that work, reject the current-state claim, even if the immutable old capture can still be analyzed as historical evidence. A single comparison before replay is insufficient. Report the producer's capture interval and the reader's validation interval separately; equality proves only participating-writer stability through that validation point, not continuing currency after it. Define freshness/overdue bounds and bootstrap/no-write/no-games behavior; never relabel an old capture's timestamp as a new observation.

**A5 — Manifest membership is not just a glob of present files.** Bind exact root-relative names, raw byte sizes/hashes and a canonical inventory digest, the resolved input root, declared season/initial-state reference and independent rules version, and capture start/end/publication times. Enumerate date/disposition coverage through the as-of date, including today; record each required pick/decision as present, absent or unreadable, and any deleted input's transaction disposition. Distinguish legitimate legacy decision absence from missing modern finalization. Absence alone does not prove skip or no games. Missing history/unknown initial state remains unverifiable. Do not seed the oracle from the captured live streak or `_replay_season_streak`.

Define exact file patterns and exclusions for future dates, model shadows, policy shadows, archives, logs and scheduler state. Refuse path escapes/symlinks/ambiguous names and metadata collisions between different configured pick roots. Hash and consume the same retained bytes. Content addressing must have a durable immutable-blob contract, verifying reused blobs and refusing partial/corrupt references. `receipt_io` currently requires **seals as well as absence of tombstones** (`receipt_io.py:11–21,120–127`); the draft's tombstone-only statement is incomplete. Seal a manifest only after every reference is durable and valid. A seal cannot prove writer completion or inventory completeness by itself.

The manifest cannot truthfully contain the actual lock release time while it is still being published inside that hold. Record acquired time, capture interval and publication time inside the hold; give release a distinct later event if required. Do not stamp an anticipated release as measured.

**A6 — Reentrancy is possible, but a depth counter alone is not a complete design.** For nesting in one thread and the same canonical lock root, retaining the outer descriptor and acquiring flock only once is the right direction. Other threads must still serialize, and other processes must flock the same unchanged lock inode. Key ownership/depth by canonical root and PID/thread, define descriptor lifetime and exception unwind, and reset inherited ownership/descriptors after fork or reject that usage. A global per-thread depth that treats root B as nested while holding root A would skip B's lock. Sharing an open descriptor across independent thread owners can also defeat the intended ownership; only the actual outer owner may unlock it. Never replace/unlink the lock file, and prohibit or order multi-root acquisition. A per-root process/thread mutex plus retained outer flock is one explicit implementation, not a requirement to invent a general lock framework. Verify the chosen behavior on supported execution hosts rather than assuming one flock implementation's details.

`scoring_lock` can remain an API alias, but its semantics are not literally unchanged: generation writes and additional peers change its exit behavior and hold duration. Nested `save_pick`, `save_streak` and decision helpers need the same owner protocol and one generation per declared logical group, without a second descriptor/flock or nested publication.

**A7 — The proposed deploy transition is unsafe.** Same `.scoring.lock` serializes old scorers with a new capture. It does **not** enroll them in generation accounting. Counter=N / sealed manifest=N; an old scorer acquires that lock, writes pick/streak, releases without advancing the counter; the new reader still accepts N as current. Old delivery/selection/decision writers do not take the old scoring lock at all. Old saver writers take another lock. Establishing the first new generation therefore solves neither case.

Require a cutover epoch with verified participating writer revisions and no remaining incompatible scheduler, grader, reconcile, CLI, dashboard or recovery writers for the selected inventory. Include scheduled jobs and processes already executing at deployment, not just the replaced scheduler. Keep W-state unavailable during mixed-version operation; baseline the actual persisted state after qualified cutover, without inventing complete history or initial state. Rollback/restore invalidates the epoch. This is a D7 runbook requirement, not authorization to stop/restart anything during this review.

**A8 — Production waits and lock ordering need an explicit boundary.** `_deliver_and_lock_pick` contains DM/post (`scheduler.py:1060,1088`), health notifications, and `_trigger_live_forward_capture_on_lock`, whose subprocess timeout defaults to 10 seconds (`:2222–2229`). Whole-function locking is not “file I/O only.” Prediction/network/retry/sleep/subprocess work must remain outside the proposed short state hold.

Specify short persisted phases: begin/reserve the attempted selection under serialization; release for the existing transport; then reload/validate the bound attempt/selection under serialization and finalize the relevant persisted outputs. A completed attempt-marker phase is still pending delivery/finalization, not a completed scoreable group. Preserve actual send-failure/unknown outcome, retry and cutoff semantics. Recheck cutoff after any added wait at the last responsible send boundary. Existing stale in-memory objects and preview guards must not overwrite a peer commit merely because their final `save_pick` now takes a lock. Any changed selection, retry, scoring, finalization or send order needs explicit separate repair/scope treatment; “wrap with no other change” does not resolve this.

If the contest saver joins this capture, require a single lock order everywhere: state lock, then saver lock. Never acquire the state lock while holding the saver lock; never have snapshot publication reacquire the saver flock already held by a nested transition. Cover dashboard, fetch auto-earn, manual setter and CLI transitions. If its audit log is also consumed, include rejected/probe audit-only appends and their own lock paths. Excluding that separate comparison from core P3 avoids these extra production dependencies.

Remove “cost is milliseconds,” “sub-second waits,” and “waits are bounded (scoring is sub-second)” as established facts. Unchanged blobs still require inventory enumeration and current-byte verification; each manifest records the full inventory; new candidate saves create new blobs. Slow disk/fsync, paused or hung producers, and lock contention can delay delivery. Specify the latency/resource validation and contention/overdue policy. Timeouts must not silently skip scoring or authorize sending after cutoff, and watchdog reads must never acquire the production lock or synchronously request a capture that does so.

## Alternatives

**B is not a lock-free multiwriter solution as written.** Writer 1 changes sequence 0→1, writer 2 changes 1→2 while writer 1 is still active: a reader can see equal even 2 around mixed files. Writers need serialization or an equivalent correctly specified multiwriter protocol, durable sequence updates and ordering around every mutation, including delete and same-byte write. A crash must leave the transaction unclosed; a later writer must not erase that fact. Counter reset/ABA and begin-update failures remain. “Writers never wait” is unsupported. A corrected serialized-writer seqlock can support a lock-free reader, but it does not avoid writer enrollment or the transaction questions above.

Equal even version readings can be evidence if a verified writer protocol binds **every** relevant mutation to those version transitions; that is different from repeated equal content hashes. Registration line 66 does not categorically forbid that separately justified mechanism. Its capture still needs exact inventory/bytes, completion interval, immutable retention for the verdict and attribution tests. B should be compared on this basis, not rejected solely because the copier is not the original scorer.

**A smaller candidate: separate producer capture from every write.** Retain one participating-writer serialization/version/lifecycle protocol for the core inventory, but issue snapshots at declared producer capture points or from a separately reviewed periodic producer job. That producer takes the writer lock, checks transaction closure, copies actual persisted inputs into a private immutable capture, binds inventory/interval/version, and publishes it. The watchdog only reads that output and validates currency; it never runs the lock-taking producer itself. A write after capture means pending until a new qualified capture. This removes a full-season snapshot from every preview save/attempt/nested helper exit. It still requires all relevant mutation paths to participate and a mixed-version cutover.

If publication is moved outside the hold, retain a sealed/immutable spool of the **actual captured bytes** and their capture identity; do not hash or reread mutable source files after releasing the lock and call that the locked capture. Justify current-version checks and interrupted capture availability. Prefer this smaller option for the next draft unless producer-bound every-write evidence is independently needed. This is a design candidate, not a measured performance win or approval.

**Narrow the captured product, not the required date coverage.** Core local replay does not need counterfactual policy outcomes or the separate contest saver. Explicitly excluding them reduces writer surface while retaining today's terminal production slots and the local saver. Capturing a narrower historical archive or only “settled before today” fails the current registered predicate; an immutable offline archive can remain a different, clearly labeled product. An owned watchdog lock cannot make any live source immutable.

## Open questions

1. **Scheduler risk:** not acceptable as the draft's unconditional whole-function wrap. Keep external work outside short declared persisted phases, carry pending transactions between phases, validate fresh identity/guards after waits, and choose an evidence-failure policy before code. Changes in business order/selection need separate scope disposition under line 56. B does not remove this requirement. Prefer the separate producer capture candidate if it meets the declared freshness requirement; otherwise revise A with measured acceptance limits before D7.

2. **Precise inventory / saver:** for core P3, include the active root's exact canonical production `<YYYY-MM-DD>.json` files for the declared season, corresponding `<date>/decision.json` bytes or explicit absence/unreadability, `streak.json` including its **model** `saver_available`, complete date/disposition coverage through as-of including today, and pinned independently declared initial-state/rules references. Include future-file/exclusion policy in inventory metadata. Exclude `*.shadow.json`, `*.policy_shadow.json`, archives, evolution logs, scheduler state and account-state files from this core oracle. This exclusion is a recommendation the revised contract must adopt explicitly, not a claim the draft already does so. Policy shadow is counterfactual and cannot supply an explicit production skip in place of the captured decision.

   Exclude `account_state/saver_state.json` from the core local replay; retain the separate compatible entered-date contest comparison as an independently qualified check or explicit deferred/unverifiable prerequisite. The current live decision loader deliberately uses this contest saver even for its model-only fallback (`contest_state.py:304–309,333–340`); do not confuse it with the local replay saver. If P3 is intended to certify **decision-state provenance** as well, enlarge and review that product separately: actual selection-time source bytes/references and account/season/date/currentness, contest observation/manual alternative and ledger dependencies as applicable, plus their writers. An at-commit snapshot of whatever contest state happens to be current cannot prove what selection consumed earlier.

3. **Deploy transition:** reject the first-write proposal. Use an explicit invalid/unavailable epoch during mixed-version operation; verify all relevant process/job revisions and participation, establish the new epoch and baseline only after compatible cutover, and invalidate on rollback/restore/recovery. Same-path flock compatibility is useful mutual exclusion for old scorers, not current-generation evidence. Unknown old writers mean unverifiable. Registration gates 5 and line 82 still require full-diff code SIGN, affected-certificate dispositions/reruns and Eric's D7 approval, followed by installed producer-to-consumer verification.

4. **Retention:** keeping captures through 2027 is a reasonable provisional policy, without a size guarantee. Estimate/test growth from unique changed bytes plus generation count × full-manifest size; dedup does not bound either term. Specify root/epoch/season separation, immutable reference integrity, storage/backup placement, disk-full behavior and resource limits before deployment. Measure representative and stress workloads synthetically; supply the acceptance budget without inventing measurements here. No pruning is simplest for initial acceptance. Any later pruning must preserve manifests referenced by verdicts and every referenced blob, and handle concurrent readers under a separately reviewed policy. Storage exhaustion withdraws qualifying evidence and becomes visible overdue work; it must not silently preserve a false current claim.

## Test plan

The draft's tests are necessary but insufficient for gates 1–2. No tests were run in this design review. Specify these production-shaped synthetic tests before implementation:

1. **Complete writer enrollment and actual bytes:** invoke every selected real entry path from the inventory, with HTTP/DM/subprocess leaves faked. Include both scorer branches, reconcile changed/unchanged/slot-only/cutoff-refusal, private/delivered/attempted-unknown/failed delivery, classification, EOD skip, CLI run/preview, scheduler selection/fallback, archive/delete and regeneration or enforced active-root refusal. Include every policy/saver writer only if retained in the selected product. Assert raw blobs equal actual persisted bytes, exact inventory membership/absence and transaction identity/outcomes. Count generations per **declared phase/group**, not an unspecified one per entire delivery function.

2. **Interruption at actual orderings:** pause and hard-kill a subprocess after streak-before-pick scoring, after pick-before-decision finalization, and after reconcile correction-before-streak. Test caught write errors, propagated ordinary exceptions, `SystemExit`, cancellation, and kill during publication. A reader must not return either verified agreement or corruption from the unclosed group. Assert the last older generation is not called current; persistently unclosed work produces the correct overdue signal.

3. **Next-writer recovery boundary:** kill N between saves, then execute unrelated successful N+1. Require retained failed/pending transaction disposition and no accidental healthy closure. Separately exercise a qualified, explicitly defined recovery/rebaseline; the watchdog performs no repair. Include a restarted producer and a retry of the same logical attempt.

4. **Concurrency/reentrancy:** independent processes and threads, nested scorer→save_streak/save_pick, delivery→decision, exception unwind, independent roots, alias canonical paths, and fork/inherited-descriptor behavior. Attribute each mutation to its actor and bind lock/capture intervals.
