## Findings

### F1 — High: outcome-bearing parquet bytes are read before either the claim or the freeze manifest

`scripts/audit/c1_r3/count_build.py:131–149` reads all five complete parquet files at line 135, then writes `manifest.json`, then writes `CLAIM.json`. Selecting three columns later does not undo the earlier `read_bytes()` of the complete outcome-bearing files. The shared admission module explicitly promises a claim before the first outcome-bearing read (`scripts/audit/c1/admission.py:18–25`), and the plan requires publication of the freeze before fitting-input reads.

**Verified:** an in-memory `_run` trace was `read:pa_2023.parquet → write:manifest.json → claim → read:feed`. Injecting a failure at manifest publication left a parquet read and **no claim**. `claimed_runs` examines only directories containing `CLAIM.json` (`admission.py:162–175`), so that interrupted invocation leaves no one-run barrier. The existing interruption test starts much later, after quarantine and claim publication.

There is also a static durability gap: `main` creates the run directory at line 125, but no operation fsyncs its parent, `run_root`. `durable_write` fsyncs the claim file and its immediate directory, not the parent entry that makes the newly created run directory recoverable (`admission.py:126–138`). Thus process-crash ordering and full directory-publication durability both need attention; I did not perform a power-loss experiment.

### F2 — High: a report-shaped string and an arbitrary X-34 row are admitted as acceptance/publication

`admission.py:64–74,87–108` looks for a SIGN prefix and any occurrence of the supplied full commit hash in a caller-selected report at the exposure commit. It does not independently establish the accepted report/commit identity or completion of required edits. A replacement executable commit can be named in a newly authored report before X; this passes the closure comparison because the replacement is now the reference. This still has the deferred 4b B2 self-declaration problem, with a report-shaped intermediary.

**Verified:** `_review_signs` returns `[]` for both `**SIGN OFF REFUSED.**` and `**SIGN WITH EDITS pending application.**`, provided the supplied hash appears anywhere in the report. An in-memory Git model with ancestry and a clean unchanged closure also made real `admission_check` return `[]` for that pending report and a first-published row reading `| X-34 | unrelated diagnostic; no historical fitting approved | withheld | Codex |`. Only the row identifier, first-parent presence and unchanged text are checked; registered exposure scope and freeze binding are not.

The current unset `admission.json` correctly refuses normal entry before a data read. That useful current refusal is not proof that a future populated record requires an actual SIGN and actual historical-fit X-34. The test named `test_a_commit_that_changes_code_cannot_declare_itself_reviewed` (`tests/scripts/test_c1_admission.py:78–83`) supplies neither a report naming its replacement hash nor a freshly published row; it cannot distinguish the repaired authority boundary from those independent refusals.

### F3 — High: invalidation still accepts the wrong source and an unreviewed historical correction

`admission.py:148–159` checks the exact run/claim wording, which improves on 4b's unrelated-row bypass. However, `cells[-1].startswith("Eric")` accepts other names, and the only correction check is ancestry. There is no binding to acceptance of the correction, its review, or the correction actually authorized for that failed claim. A well-formed ruling naming an arbitrary existing ancestor meets the code predicate.

**Verified:** the same synthetic run/claim row returned `[]` with source `Eric 2026-10-05` and with source **`Erica 2026-10-05`**. The correction was modeled as an ancestor; no correction-review record was supplied. The suite's accepted invalidation uses a constructed register string and current HEAD, and checks only that the correction exists in history (`test_c1_admission.py:109–128`). It does not establish the deferred B1 reviewed-correction requirement. Normal `main` additionally requires a clean tracked tree; the source/correction defects survive committing such a row and do not depend on an uncommitted register edit.

### F4 — High: X00 labels and increasing indices are insufficiently checked as starter/order certificates

`count_meta.py:48–73,89–108` distinguishes X00 from X01+, but truncates arbitrary numeric codes through `int()`, checks uniqueness of slots rather than players, and discards substitution rank/action information. `count_verify.py:33–43` subsequently checks only membership and aggregate `(is_home,batter)` counts. It never verifies substitutions, batting-slot transitions or evidenced zero-PA starters. Every missing starter PA becomes N=0 at `count_table.py:20`, irrespective of whether source completeness/replacement evidence supports that absence.

**Verified, all with `verify_game(...) == []` and matching independent synthetic PA counts:**

- Swap batter 101's and 102's X00 slot codes while leaving their PA order unchanged: the contradictory slot assignment is certified.
- Put substitute 111 (code `101`) before starter 101 in the same slot: the replacement/return contradiction is certified.
- Give the persons in slots 1 and 2 the same ID 101: both slots are certified, and the same batter's count is used twice.
- Supply `battingOrder=100.9`: it becomes a certified slot-1 starter.
- Supply `halfInning="unknown"`: it silently becomes away.
- Keep increasing `atBatIndex` while later plays have earlier start timestamps: the chronological contradiction is ignored.

The X00 distinction is a useful source witness on a valid canonical boxscore; production's `//100` parser alone does not certify it for contradictory records. Likewise, strictly increasing authoritative indices are useful order evidence, but checking them alone does not discharge the registration's substitution/chronology checks. A cyclic pattern alone must not replace the authoritative certificate. No claim is made that these malformed cases occur in the unread historical feeds.

### F5 — High: complete-start BF and historical date/source availability are not certified

`count_meta.extract` does not inspect completion status, complete boxscore PA/BF totals, or a completion witness. `count_verify` equates agreement with the parquet to completeness. A feed and parquet can share the same truncation. `count_bf.py:15–21` then labels the matched pitcher counts as per-start BF and contributes them to the fixed league median.

**Verified:** a two-PA feed marked `Suspended`, with two matching parquet rows, is certified and produces BF=1 for each pitcher. A similarly unfinished `In Progress` feed is also accepted. Thus the zero-PA exclusion and workload median can be computed from an incomplete source while all existing completeness checks pass.

The starting-pitcher cross-check uses the first **PA-ending** event, not the first actual pitcher appearance/facing evidence. A synthetic starter 250 appearing in a non-PA event before reliever 260 completes the first PA is rejected as a starter mismatch. Conversely, if an opposing side has no retained PA, the cross-check is skipped and its pitcher is still emitted as certified BF. The boxscore-first/first-faced strategy needs full-play/action/start evidence, including a starter removed before completing a PA; it cannot claim more than its retained-event check proves.

Official date is copied without validation against season or parquet date. **Verified:** `officialDate="2026-06-01"` with declared feed season 2023 passes verification against 2023 synthetic rows and appears unchanged in BF history. The three selected parquet columns cannot establish the required date/season relationship. Workload rows also lack a completion/availability witness; `provenance.json` saves only producer timestamp, decoded hash and certification, not the source receipt's retrieval time/identity. Producer version is not retrieval availability.

**Resolved aspects:** ordinary doubleheaders retain distinct `game_pk` values at the same official date. A synthetic 716404 fixture with official date 2023-09-28 and resumption 2023-10-02 correctly excludes the resumed PA from N and keeps it in BF, keyed to 9/28. Actual production `parse_game_feed` on that synthetic fixture gave identical PA events and resumed flags. This does not inspect the real game or establish completed-source availability.

### F6 — High: parquet coercion/filtering can silently change eligibility and completeness

`count_build.py:92–96,151–152` groups before validating identities, allows pandas' default null-key dropping, coerces IDs with `int()` and home flags with `bool()`, and combines seasons with dictionary `update`. It does not validate the frozen parquet schema, season/date fields, duplicate game ownership across seasonal inputs, or the asserted absence of `is_resumed_portion`.

**Verified:**

- A synthetic source containing good game 7 and a row for game 8 with null `batter_id` completes `_run` with **return 0, eligible=1, certified=1, quarantined={}**. Game 8 vanishes before the census.
- `game_pk` values 7.1 and 7.9 collapse to integer 7 and overwrite the same count cell.
- String `is_home="False"` becomes home=True.

For the declared legacy schema, comparing all feed PA-ending rows by side/batter before applying the feed's resumed exclusion is appropriate, and that comparison is implemented. It must be preceded by typed/schema validation. An enriched or otherwise unsupported parquet is currently accepted instead of refused; reading only three columns does not enforce the declared legacy/scoring-reader assumption. Filtering raw rows for contest counts must also remain distinct from BF's complete workload input.

### F7 — High: digest checks do not bind the receipt to the declared file/request identity

`feed_inventory` (`count_build.py:82–89`) selects stored completions, coerces receipt IDs/season paths, and silently chooses the last receipt for a key. `_run` uses the receipt's unchecked path and checks the nested feed pk against the receipt pk, not the filename or top-level feed pk. No canonical path containment, conflicting-receipt reconciliation or unresolved-intent check is performed.

**Verified:** actual `_run` returned **0, certified=1** when receipt `gamePk=7` named `2023/8.json.gz`, containing a fully hash-matching feed with nested pk 7. An otherwise identical run with an additional unmatched intent also returned 0. Separately, top-level feed `gamePk=8` with nested pk 7 is certified as 7. A traversal path beginning with `2023/` is not rejected by `feed_inventory`; the subsequent path join can leave the fixed feed root (static finding; no outside file was read).

The stored and decoded SHA checks themselves correctly reject changed bytes before extraction, and parsing uses the same verified buffers. I found no successful byte-hash mismatch bypass. The missing boundary is source/file/request identity and reconciliation, not a broken hash comparison.

Retain the documented legacy limit: these original feeds have per-game receipts, without per-attempt response/retry evidence, and the five schedules are unreceipted. No schedule read is necessary for the declared parquet-game eligibility. Do not require or fabricate retroactive response receipts, or use this review to authorize acquisition/resumption. Validate the available per-game binding and explicitly refuse newly unresolved/contradictory acquisition state.

### F8 — Medium: the freeze manifest is incomplete and does not retain its input inventory

The manifest at `count_build.py:137–144` contains code/closure objects, an admission object, a digest of three-field inventory lines and parquet digests. It omits the reviewed registration/hash, accepted review hash, exposure-row/manifest binding, serving recipe, retraining schedule, active blend/aggregation/fallback definitions, environment/calibration/deterministic/seed settings, supported input schema and fixed eligibility/as-of rules required by registration X-E1 (lines 96–101). The registration is also absent from the executable/contract comparison closure. A committed change to its rules does not itself invalidate this gate.

The inventory listing is discarded; neither its canonical paths nor receipt identities/bytes are archived in `manifest.json`. The digest cannot recover that inventory, and changing a receipt path leaves the same listing digest. `provenance.json` supplies useful decoded hashes after processing but does not bind the omitted receipt/path/availability fields. Closure git object IDs are useful immutable code identifiers; they do not substitute for runtime configuration or source inventories.

The reader also unconditionally calls `gzip.decompress` at line 157. This fits the currently supplied gzipped acquisition but does not preserve X-E1's explicit plain/gzipped static-input support. Plain retained JSON with valid stored/decoded pins raises rather than being supported. This is a fidelity deviation, not evidence of a plain file in the actual corpus.

### F9 — Medium: exceptional unresolved games disappear from the required quarantine accounting

Metadata/schema/timestamp failures at `count_build.py:160–161` escape before the census is written. Missing receipt-named files similarly raise at line 154. An irrelevant ineligible feed is also parsed before its eligibility is checked and can abort the eligible build. The normal census implementation correctly counts missing inventory games and applies **strictly greater than 1%**, never retaining a bad game just because the fraction is small. It does not receive these exceptional unresolved cases.

**Verified:** a receipt-bound synthetic suspended feed with `startTime="garbled"` raises `ValueError` from the production timestamp helper. Only `manifest.json` reaches the intercepted writer; there is no census or per-game quarantine reason. Both production and this extractor raise on that malformed timestamp, so this is not a measured resumed-flag parity difference. The module's claim that an unparseable time is simply marked resumed (`count_meta.py:10–11`) is false for this case; missing timestamps do follow that branch.

A provenance mismatch should continue to refuse the whole run; do not turn a broken trust anchor into an allowed ≤1% omission. Metadata failures need explicit quarantine decisions, while fatal provenance/publication failures need durable stopped/incomplete accounting. Failing closed without results is useful, but does not satisfy the promised census of every unresolved game.

### Test-strength disposition

The hand-computed category counts, add-one smoothing, N=0 conditioning, overflow reporting, ordinary resumed split, strict 1% boundary and stored-byte mismatch tests substantiate those particular behaviors. The target remains the certified starter's resumed-excluded N≥1 distribution, with category 8 representing N≥8 and overflow N>8 reported; there is no requested scientific refit.

The suite cannot establish the missing certificates. Several verification fixtures derive expected parquet counts from `M.extract` itself (`test_count_build_parts.py:13–15`; `test_count_build_e2e.py:33–34`), so an extraction error shared by both sides can pass. The end-to-end harness replaces admission and tracked-tree checks and reduces the five seasons to one (`test_count_build_e2e.py:42–48`). It checks that a claim exists eventually, not that every input read follows it. The substitution test tests the counting helper without certifying its intentionally partial feed. The BF fixture includes a relief change and later starter return without action metadata proving that return was legal (`test_count_build_parts.py:74–83`). The 716404 test checks only identity fields, not completion or availability. These are useful unit checks with limited contracts, not independent end-to-end acceptance evidence.
