## B1 — An old malformed pick can now prevent every live decision, including a healthy first fetch

- **Location:** `src/bts/contest_state.py:304-305`, calling `_resolved_pick_dates` at `:206-220` before selecting the contest observation.
- **Concrete state:** on 2027-03-24, `data/picks/2026-09-26.json` contains valid JSON `[]`. No contest observation is needed to reproduce it. It also reproduces with a healthy auto observation `{"active_streak":0,"recorded_at":"2027-03-24T12:00:00Z"}` and either value of `require_contest_state`.
- **Wrong outcome:** the newly unconditional history scan calls `body.get` on the list and raises `AttributeError`. A historical `null` does the same; `{"result":[]}` or `{"result":{}}` raises `TypeError` at set membership. These are not `ContestStateError`, so the scheduler's contest-state alert/recovery path does not catch them. A fresh account fetch cannot repair the unrelated historical pick; every subsequent attempt fails until that file is repaired or removed.
- **Base comparison:** the exact loader from `git show 12dbaaa:src/bts/contest_state.py` returns streak 0/model-only without an observation, and streak 0/stale with the healthy first-fetch observation, including `require_contest_state=True`. Neither base path needs this scan.
- **Real CLI demonstration:** real `preview --date 2027-03-24 --picks-dir ...`, including build, feature computation, model training and selection, exits 1 with the new loader and `AttributeError`; substituting only the exact base loader makes it exit 0 and save the preview. HTTP was synthetic; no network was used.
- **Smallest fix:** validate that each decoded body is an object and its `result` is a string before accessing/hash-testing it; skip unsupported historical files as invalid JSON is already skipped. Add the loader cases and a CLI regression. Do not let unrelated historical corruption block an otherwise usable first-fetch observation.
- **Evidence:** `scratch/probe_state.py`, `scratch/state-results.json`, `scratch/state-run.log`.
