## Part 1

This section is my independent review of revision 2. Its findings and boundary assessment were recorded before reading the previous reviewers' reports. Code reads were limited to judging whether the proposed bindings and tests fit the actual launcher, admission API, account writers, run stages, and fixtures. ### D1 — A genuine C1 receipt can still attest to the wrong account (blocking)

Boundaries 8 and 9, note lines 225–256, give C1 a caller-selected `--extra-charges <path>`. C1 validates only the file's structural rule and sums its rows. The receipt fixes that file's length and hash. The payload compares the hash with the first `extra_bytes` bytes of the actual account. Neither boundary requires C1 to read the canonical account path, requires the receipt to include the current launch's begun row and identity, or proves that the selected prefix was the whole canonical account at decision time.

Consider a canonical account with the ruled prior, a completed preparation, a completed expectation, and all required digest links. A caller passes C1 a second file containing only an earlier prefix of those same bytes. That file meets the stated C1 structural rule. C1 makes a genuine combined decision against the smaller total and issues a receipt for the payload's actual unit. The prefix hash check succeeds against the canonical account; its later preparation/expectation or attempt charges are outside the receipted prefix. The canonical account can separately pass the payload's predecessor checks. This does not forge a receipt or rewrite its producer's files. It exploits the producer's unbound input. In particular, merely rejecting a payload with no receipt does not establish that the reviewed wrapper supplied the receipt's account.

I checked the arithmetic and prefix property on synthetic bytes: with a 152 CPU-h C1 ledger, 80.01 seconds in the supplied prefix, a 0.5-hour overhead reserve, and a 12-hour budget, the receipted sum is 164.522225 hours and passes 165. Adding the canonical preparation/expectation charges used by the example makes it 165.622225 hours and fails. These are constructed values, not measurements or an execution of future combined-mode code.

C1's launch lock correctly serializes its own sweep, reconciliation, decision, PENDING, and start when the receipt is added there. It does not lock account writers. The current account writer in `f26.py:728` has no C1 lock, and the proposed wrapper writes its end and child-charge rows after invoking C1. The note's round-5 item 6 says an extra charge between decision and start is impossible under the lock. That is true of another cooperating C1 launch, but not of an account append. A synthetic append completed while the actual `launch_lock` was held. The prefix rule intentionally tolerates later appends, so it cannot establish that these omitted charges are covered.

Required design: bind C1's read to the canonical account and the current attempt, read/hash/sum one immutable byte snapshot, and define serialization or an enforceable reservation for every account writer that can add charges while the decision is outstanding. Distinguish permitted post-decision bookkeeping covered by the overhead reserve from another step's charges. An alternate older-prefix file must be a RED with a complete legitimate canonical history, not just an absent-account fixture.

### D2 — The account cannot distinguish the live current launch from an unresolved attempt (blocking)

Boundary 7, lines 175–207, declares begun followed by exactly one of completed, refused, failed, or unresolved; it then requires an `admitted` launch row, a state it has not defined. More consequentially, a begun row without an end is classified as unresolved and pauses every further step. Boundary 8 has the wrapper write begun before calling C1. Boundary 10 requires the payload to check the account phase before claiming.

The real C1 sequence is in `launch.py:452` onward: it writes PENDING, invokes `systemd-run`, and returns. The guard starts the payload through `Popen` (`guard.py:183` onward). The payload can run before `systemd-run` returns and before the wrapper can append its admitted/completed end row and its launcher-process CPU row. At that instant a valid launch has exactly the unfinished begun row the note says pauses every further step. A blanket implementation refuses the valid first payload. An implementation that exempts every unfinished launch silently permits an unrelated unresolved attempt. Neither choice is the specified state machine.

The same issue arises when a step writes its own begun row and then checks the global unresolved rule, including the aggregate, whose own begun reserve is expressly included. The note needs an identified current attempt exception, rather than an implicit exception left to the coder. Each attempted prepare/expect/launch/aggregate needs a unique attempt identity linking its begun, end, child charge, and any settlement. Seed, step, admission digest, and a unit assigned only later do not distinguish multiple refused pre-C1 attempts of the same seed. The statement that a settlement names "the attempt" does not supply that identity or its matching rule.

Settlement accounting is also incomplete. C1's real reconciliation already charges either the guard's CPU or the full declared budget for a missing/invalid terminal record (`launch.py:218`, `ledger.py:add_guard_row`). A launcher-process row can exist while RECONCILED is missing, and the note then calls for a settlement CPU figure. It does not say whether that figure replaces a missing wrapper/child charge, adds only an uncharged remainder, or includes the unit CPU C1 already owns. Summing every nonnegative `cpu_s` row, as boundary 8 proposes, cannot by itself prevent double counting a provisional/end charge plus its manual settlement. It likewise cannot infer a missing child's charge from an unrelated settled attempt.

Required design: specify attempt identities, an explicit in-flight transition bound to this reservation/unit, the exact legal state set, when an unfinished attempt becomes unresolved, and whether every settlement is a delta or a replacement with a defined nonadditive predecessor. Require a valid control in which the payload runs before the wrapper returns, and controls for acknowledged failures before receipt, after receipt, after PENDING, and after payload start. A planted already-completed wrapper row is not a control for this timing.

### D3 — The CPU ownership and final-cap rule still need an executable definition

Boundary 7 now correctly separates wrapper self CPU from the waited C1 child. This fixes the obvious `screen.cpu_seconds` plus child-rusage overlap. Process-start RUSAGE_SELF also captures the CLI process's imports, and the two-second tail is honestly labelled a reserve rather than a measurement.

The proposed owner list nevertheless leaves a concrete class of CPU unassigned. Preparation, expectation, aggregate, and the wrapper's pre-C1 admission all invoke git through `admission._git` and related subprocess calls. RUSAGE_SELF does not include these children. The note permits `children` only for the launcher-process row, with its delta around the C1 child. These other waited children belong neither to the guard's detached payload cgroup nor to that delta. Calling this whole-process CPU does not count them. The tail reserve is described as covering final append, shutdown, and interpreter exit, not admission subprocess work. Define the owner and sample for these children, preserving the separation from the asynchronous guarded unit.

Boundary 13 and lines 208–211 also need two explicit cap decisions: before opening outcomes, and before returning/publishing a disposition using the aggregate's measured charge so far plus its tail. An entry check that includes only the aggregate's begun reserve can pass and then be exceeded during recomputation/resampling. The 0.5-hour future reserve is a declared allowance, not an enforced CPU bound on the aggregate, and it is not a substitute for the final check. The design must say how the begun reserve is replaced or counted with the end charge, and what output survives when the final charge crosses the cap. The same specification is needed for repeated refused/failed aggregate attempts. I did not measure aggregate CPU or assume that it exceeds either reserve.

The stated limitation about not authenticating a manual figure or proving nontruncation is honest. It does not excuse missing required links or undefined additive ownership: those are the gate's expressly claimed responsibility.

### D4 — The proposed directory pre-read rule omits the launch wrapper (blocking)

Boundary 5, lines 147–151, expressly checks actual arguments for `run` and `aggregate`, before opening files. It does not require that check for `launch`. The real wrapper calls `load_trusted(inputs_dir, pins)` before its C1 invocation (`f26.py:1860` onward), which opens the pinned 2026 PA, table, and expectation through the caller's inputs path. Round-5 item 6 changes reservation production, not this read. A caller can therefore invoke the reviewed wrapper with a second directory containing identical pinned bytes; the wrapper reads it before the eventual payload refuses its noncanonical argument. The note itself correctly says that a later hash/refusal cannot undo an out-of-inventory read.

Specify the canonical `inputs_dir` and inventory `data_dir` checks at the wrapper's own first protected-read boundary, and require the account phase and required preparation chain there as appropriate. Test it with a complete valid history and an alternate directory whose file contents would otherwise pass the pins. Instrument opens so the test proves refusal before reading, rather than just an eventual refusal by the payload.

### D5 — A clean working-tree check is not a fixed register snapshot

Boundary 14, lines 304–312, promises that every gate reads committed text and no working-tree row absent from HEAD. Its proposed mechanism is a clean `git status` followed by reads of the checked-out file. Between those operations, another process can edit the file or advance HEAD. The actual APIs also read the register more than once across admission, seed validation, and claims. A clean check at one instant does not make the later path's bytes the checked commit's bytes or fix one invocation's register.

The trust source can remain GIT: capture one full HEAD at entry, read the register's bytes directly from that commit, and carry that snapshot and commit through all row parsing, chronology, and decision checks. Keep the dirty-register refusal as an additional rule if desired. Alternatively specify a lock covering all relevant writers and reads. Do not leave the guarantee dependent on an unstated no-concurrent-edit assumption. Include a test that changes the checkout's register immediately after the cleanliness check; no injected working-tree row may become authority. The source-token limitation about Eric's actual authorship remains separate and is correctly disclosed.

### D6 — The certificate change exceeds the declared default-off shared scope

Boundary 0 and round-5 item 1 put the mandatory Review-kind check into the shared `admission._review_signs`. The scope statement says only the launcher and its tests change under C1, with everything else confined to `f26.py`, its tests, and evidence. The real `_review_signs` is called by shared `admission_check` and by `invalidation_problems`, not only by this test. The existing C1 admission tests at `tests/scripts/test_c1_admission.py:26`, `:64`, and `:76` intentionally accept plain SIGN certificates without a Review-kind field. Code reads also establish that the historical count build, rank-4a research, and framing screen call the shared admission gate.

A mandatory unconditional check would change those default callers and correction certificates even with no combined-mode flags. Existing cycle tests passing would not detect this collateral admission change. The needed design/code distinction is sound, but implement it in the F26-specific gate, or expose an explicit default-off shared certificate policy and review/test that additional C1 change. Do not retroactively reject unrelated certificates. The manager's condition (a) specifically promises legacy launcher behavior; the broader "everything else" scope claim also has to be corrected if shared admission is modified.

### D7 — Reservation-only identities need crash recovery and collision coverage

Boundary 9 promises that unit names are never reused. The real `unit_taken` checks PENDING, TERMINAL, RECONCILED, OVERRUN, RESUME, and ledger rows (`launch.py:265`), but not the new RESERVATION. The real durable writer uses replacement, not exclusive creation (`guard.py:145`). If the launcher dies after RESERVATION and before PENDING, the only surviving identity is invisible to that collision checker. The synthetic reservation-only control returned false from current `unit_taken`.

This is a required implementation clarification, not evidence that a real random collision occurred. Add reservation-only identities to combined-mode collision handling and lifecycle/attempt recovery, test a forced collision and the receipt-to-PENDING crash window, and state how that attempt is settled without either overwriting its receipt or charging a seed budget for a job that never started. Preserve the stated default-off behavior deliberately. Round-5 tests that only assert the order of successful writes do not exercise this cut point.
