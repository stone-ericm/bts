## Why
Two defects found by the reviewers of change set 6b-1, in code that change set did not touch (`build/cs6b1-review/`):
- **A.** `daily_decision.parse_decision` catches only `json.JSONDecodeError`. A day's `decision.json` with an accepted schema and `"action": []` (or `{}`) raises `TypeError` (set membership on an unhashable value); a body nested 20,000 deep raises `RecursionError`; bytes that are not UTF-8 raise `UnicodeDecodeError` from the loaders. `scheduler.run_single_check` reads the decision with no handler whenever the day's pick file exists, and nothing above it in `run_day` or `bts schedule` catches: the scheduler exits, systemd restarts it after 30 seconds, the first past check raises again, and the day is a restart loop with no pick and no alert of its own. The same read escapes from `check-results`, `check-pick-entered`, `day-outcome` (exit 1, no DM, for `TypeError` and `RecursionError`), the skip-policy shadow update and two health checks.
- **B.** `health.alert._resurface_note` and the dedup read in `dispatch_dm_for_health_alerts` use the decoded status file with `.get(...)` before checking it is an object. A status file holding `[]`, `null`, a string or a number raises `AttributeError` on EVERY call (even one with no alerts, and with no recipient) until the file is removed; a nested body raises `RecursionError`; `"critical_count": "x"` raises `TypeError`; `"sent_sources": [1, {}]` raises `TypeError`; `"sent_sources": [1]` sends the DM and then records it as FAILED. Most callers on the pick path (`_alert_contest_state_failure` from `run_single_check` and from two places in `run_day`, the missed-pick alert, the late and void delivery refusals, the unconfirmed-lock alert) are not wrapped: the exception ends `run_day` and the process restarts into the same file. The end-of-day health run swallows it and sends no health DM at all.

The repository's convention for an unreadable state or pick file is `contest_state._UNREADABLE = (OSError, ValueError, RecursionError)` followed by an `isinstance(..., dict)` check. This change set applies it to these two readers. It changes no decision, selection or delivery rule.

## Known limits (state them in the handover; they are not findings)
- A malformed PICK file (`<date>.json`) still raises from `picks.load_pick` and still stops the scheduler's checks. That is deliberate here: treating an unreadable pick file as absent would let the scheduler choose and deliver again over a pick that may already have gone out. It needs its own ruling.
- A malformed decision record is now simply "no record": the scheduler falls back to the pick file's own delivery markers (as it does today when the decision file is missing or is invalid JSON), `check-results` scores a delivered pick by that fallback, and the skip-policy shadow treats the day as not a skip. Nothing reports that the record was malformed.
- A status file that cannot be read gives no dedup and no failure banner for that call; the next successful write replaces it. A directory or an unwritable file at the status path still prevents the write (logged), so a DM can repeat on every call that day.
- The dashboard's own reader of the health status file (`web.py`) is not changed.
