## Why
`health.alert.dispatch_dm_for_health_alerts` reads its status file twice (`_resurface_note` for the failure banner, then the same-day dedup) and uses the decoded value before checking what it is. A status file holding a non-object (`[]`, `null`, a string, a number) or a deeply nested body raises BEFORE the empty-body and recipient gates, so on every call, even one with nothing to send. An invalid `critical_count` raises when `status` is `failed`. A bad `sent_sources` matters only in the dedup branch (`status == "sent"`, the same ET day, a body, no failure banner): `[1, {}]` raises before sending, and `[1]` sends the DM and then records it as FAILED (the sort of mixed types raises inside the send's handler); a string is split into characters. Most pick-path callers are not wrapped (`_alert_contest_state_failure` from `run_single_check`, from `_deliver_and_lock_pick`'s state-read refusal and from both `run_day` fallback refusals; the missed-pick alert; the late and void delivery refusals; the direct unconfirmed-lock alert): the exception ends `run_day`, systemd restarts the scheduler, and it can meet the same file again. The end-of-day health run and the morning and stale-reading lanes contain the error but send nothing and leave the bad file in place.

This change set makes the status file's CONTENT unable to make the dispatcher raise or misreport. It changes no alert text, key, dedup rule or return value for a conforming file.

## Known limits (state them in the handover; they are not findings)
- A corrupt status file costs that lane its dedup once: one alert per key can repeat, and the next successful write restores coverage for the keys in that send. Persistent corruption or a status path that cannot be written (a directory, permissions) allows a repeat on every eligible call; there is no fixed daily cap. A failure or skipped-recipient write also resets the day's coverage, as today.
- No failure banner is shown when the previous status cannot be read.
- The dashboard's reader and renderer of the status file are unchanged (`status: []` can still break the renderer).
- Invalid caller inputs, logging failures, transport failures and interrupts are outside this hardening.
- **Not in this change set:** a malformed `decision.json` still raises from `daily_decision.parse_decision` and still stops the scheduler's checks (ruling R37, an open hazard); a malformed pick file likewise.
