## Why
At the start of a season nobody knows what MLB's contest endpoints return, and last season's files are on disk. The owner's decision for that stretch: **each day's pick runs on a streak the operator supplies for THAT contest date; a day nobody supplies one has no pick.** Today's manual override cannot express that: it is a value that lasts a number of hours, so it can leak into the next day or lapse in the middle of this one, and it does not say what the saver is.

This change set adds the observation supplied for today and makes the decision use it today, saver included. It does NOT yet refuse a day that has none (change set 4b and 6 do), it does not wake a pick that was already decided (change set 5), and it does not touch the automatic observation or the fetch. **It is not to be deployed on its own:** until the later change sets land, a day with no observation still picks on whatever automatic file is on disk.

## Definitions
- **One clock per operation.** In the NEW dated command mode, and in each call of `load_decision_streak_state`, `load_contest_streak_state` and `health/contest_state.check`, capture ONE timezone-aware `now`: the caller's when supplied, otherwise one wall-clock read. Pass that same value to nested readers and the date predicate, and use it for all classification, season and date decisions, timestamps and output in that operation. **Today** is its `America/New_York` date, including when execution finishes after midnight. The legacy `set-contest-streak` mode, including its saver-helper timestamps, keeps `main`'s clock behaviour under rows 1 and 12. (The health check already captures one clock and passes it down: preserve that.)
- **A dated observation** is `account_state/contest_streak.manual.json` whose `schema_version` is exactly the string `"bts_contest_streak_manual_v3"`. It is **for** its `effective_date`. It is **in effect** exactly when its `effective_date` equals today. "In effect" is a pure function of the observation and `now`: if the clock is set back, an observation for that earlier date is in effect again; nothing remembers that it had lapsed.
- **Timestamp grammar** (for `expires_at` and `recorded_at`): a `str`; a trailing `Z` is replaced by `+00:00`; the result must be accepted by `datetime.datetime.fromisoformat`; the result must have a `tzinfo` (a naive timestamp is INVALID, not assumed to be UTC).
- **Valid** dated observation. Checked in this order; the first failure is the one reported:
  1. the file is readable, is UTF-8, is JSON, and is an object (change set 1's `_UNREADABLE` handling: `ContestStateError`);
  2. `effective_date`: present, a `str`, accepted by `datetime.date.fromisoformat`, and equal to that date's `.isoformat()` (so only the padded form is valid in the FILE);
  3. `season`: present, `type is int`, equal to the year of `effective_date`;
  4. `expires_at`: present, in the timestamp grammar, and the same instant as `23:59:59.999999` on `effective_date` in `America/New_York` (any UTC offset spelling of that instant is valid);
  5. `active_streak`: present, `type is int`, `0 <= active_streak <= 57`;
  6. `best_streak`: present, `type is int`, `active_streak <= best_streak <= 57` (a `best_streak` below `active_streak` is reported as `best_streak`'s failure);
  7. `saver_state`: present, one of the strings `"not_earned"`, `"active"`, `"used"`;
  8. `recorded_at`: present, in the timestamp grammar;
  9. `source`: present, a `str` (it may be empty);
  10. `reason`: if present, a `str` (it may be empty); it may be absent; `null` is invalid.
  Every other key is ignored whatever its value, including the legacy keys `override_expires_at`, `source_date`, `streak`, `saver_available`, `username`.
- **Legacy manual file:** any manual file whose `schema_version` is NOT exactly the v3 string (including a missing, null or unknown schema). It is parsed exactly as on `main`, with every laxity `main` has. A file that looks like a dated observation but has the wrong schema string is a legacy file; the command never writes one.
