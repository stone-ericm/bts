## Why
At the start of a season nobody knows what MLB's contest endpoints return, and last season's files are on disk. The owner's decision for that stretch: **each day's pick runs on a streak the operator supplies for THAT contest date; a day nobody supplies one has no pick.** Today's manual override cannot express that: it is a value that lasts a number of hours, so it can leak into the next day or lapse in the middle of this one, and it does not say what the saver is.

This change set adds the supplied-for-a-date observation and makes the decision use it on that date. It does NOT yet refuse a day that has none (a later change set does), and it does not touch the automatic observation or the fetch.

## Definitions
- **Today** is the calendar date, in `America/New_York`, of the caller's `now`. Every function below already takes a `now` or reads the wall clock.
- **A dated observation** is `account_state/contest_streak.manual.json` with `schema_version == "bts_contest_streak_manual_v3"`. It is **for** its `effective_date`. It is **in effect** exactly when its `effective_date` is today. There is one manual file; writing a new observation replaces the old one.
- **Valid** dated observation: a JSON object with exactly these properties:
  - `schema_version`: the string above.
  - `effective_date`: a string that `datetime.date.fromisoformat` accepts AND that equals that date's `.isoformat()` (so only the padded `YYYY-MM-DD` form is valid in the FILE; the command writes that form).
  - `season`: `type is int`, equal to the year of `effective_date`.
  - `expires_at`: a string that parses to a timezone-aware datetime equal to the last microsecond of `effective_date` in `America/New_York` (`23:59:59.999999`).
  - `active_streak`, `best_streak`: `type is int` (a bool is not an int), with `0 <= active_streak <= best_streak <= 57`.
  - `saver_state`: one of `"not_earned"`, `"active"`, `"used"`.
  - `recorded_at`: a string that parses to a timezone-aware datetime.
  - `source`: a string. Optional `reason`: a string. Other keys are ignored.

**Known limits, by design (state them in the handover, do not work around them):**
- A day with no dated observation behaves exactly as today (the automatic file or a legacy override is used, or the model). Refusing such a day in live mode is a later change set.
- An observation written for a future date sets the saver flag immediately, not on that date.
- The saver recorded in the observation is a record of what the operator entered; the flag file remains the one authority the decision reads.
