## Why
Change set 4b-2 made a LIVE decision refuse an automatic contest observation the season switch does not cover. But "live" is a configuration setting: `_contest_state_required(config)` is true only when `scheduler.contest_state_required` or `health_checks.contest_state_expected` is set. `config/orchestrator.example.toml` has both off, with `pick_delivery = "public"`. A box restored in March with picks going out by DM and neither setting on would pick on last season's contest streak with no refusal and no alert: the hazard the whole build exists to close. Separately, `bts run` (scheduled three times a day by the legacy Mac installer `scripts/cron-setup.sh`, and usable by hand; `scripts/cron-setup-pi5.sh` installs grading only) posts publicly and always uses the optional loader, and `bts orchestrate` posts to the public feed whatever `pick_delivery` says.

This change set makes that configuration impossible to run by accident: the commands that start the scheduler or the orchestrator refuse it, the existing entry-intent check reports it (so the cron installer refuses too), `bts run` uses the live refusal whenever it is not a dry run, and the example configuration turns the settings on. It does NOT change what "required" means inside the scheduler (ruling R32: forcing it on for DM and public delivery would silently change what hundreds of existing scheduler tests exercise), and it does not touch `bts preview` or the dashboard (change set 5 and later). **Nothing from change set 4a onwards may be deployed before the remaining change sets land.**

## Definitions
- **Effective scheduler delivery:** what `bts.scheduler._pick_delivery_mode(config)` returns (`"public"`, `"dm"` or `"private"`), or its `ValueError`.
- **Contest state required:** what `bts.scheduler._contest_state_required(config)` returns today, by Python truthiness of either setting. Its meaning is unchanged.
- **Outward delivery:** a new pick going out by DM or to the public feed.

**Known limits, by design (state them in the handover, do not work around them):**
- **The check is at the command, for new launches.** Code that calls `run_day`, `run_single_check`, the delivery helpers or `orchestrator.orchestrate` directly bypasses it. A process already running keeps the configuration it loaded. Committed decisions and sends in flight are untouched.
- **The refusal goes to stderr only.** This change set guarantees the refusal and its reason, not a notification and not a successful rollback. With DM delivery and neither setting, a restarted scheduler exits 2 before READY and before any heartbeat; under systemd it then restarts every 30 seconds or stops on rate limiting; the end-of-day health check cannot run. The deploy workflow's blocking `systemctl restart` can fail before its canary, leaving the new commit installed, or the canary can roll back to code without the gate. What can alert is the independent five-minute heartbeat cron (a stale or missing heartbeat, restart counts) and the next morning's `bts day-outcome`, each only if installed and routed.
- **So the operator's prerequisite is:** before any deploy or first start of a restored box, put both literal settings in the service's real configuration file, confirm with that revision's `bts entry-intent`, install the intended cron, and look at `bts season-contract status`. (The lead adds this to the season-start checklist; do not edit `docs/ops/`.)
- **Not covered:** private delivery with research intent (the offseason mode) still picks on whatever is on disk and can lock locally; `bts preview` and the dashboard use the optional loader, and a pick file the preview wrote can still be delivered without re-selection (change set 5); `check-pick-entered` can DM the names of an already committed pick; reports, result replies and anything a person enters by hand are outside the gate; an entry-check cron installed earlier stays installed after the configuration changes.
- **`bts schedule --dry-run` is not harmless today** (heartbeat, notifications, schedule fetch, possibly idling on an off day); this change set only adds the warning.
