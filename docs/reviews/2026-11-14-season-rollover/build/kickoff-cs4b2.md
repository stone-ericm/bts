## Why
Change set 4b-1 gave the season a switch (`account_state/season_contract.json`, `bts season-contract status` and `enable`) and made the fetch write the automatic observation only when the season is switched, stamped with the season and the switch's `activation_id`. But every decision still accepts whatever automatic file is on disk. Ruling R24: **an automatic observation is used for a LIVE pick only after the operator has switched this season to automatic; until then the live pick runs on the day's dated observation, or there is no pick.** Ruling R30: the automatic file must carry the season AND the identifier of the current switching, so that after a revoke and a re-enable (for example after restoring the box from a snapshot) a file written before the re-enable is not used.

This change set adds that refusal to the live decision, reports it in the health check and in `status`, and adds `bts season-contract revoke`. Non-live reads (previews, dry runs, the dashboard) are unchanged. **Nothing from change set 4a onwards may be deployed before change set 6.**

## Definitions
- **Y**, **one clock per operation**, **switch state**: as in change set 4b-1. `load_decision_streak_state` and `health/contest_state.check` already capture one `now` (change set 4a); the switch state they consult is computed from that same `now`. `revoke` captures one `now` at callback entry.
- **Live** means `load_decision_streak_state(…, require_contest_state=True)`.
- **The selected observation** is what `load_contest_streak_state` returns today, by its existing rules, unchanged: a dated observation in effect; else an unexpired legacy manual override; else the automatic file; else an expired or undated legacy manual file; else `None`. Its existing errors (an invalid manual file; a refused, corrupt or, when required, undated automatic file) are raised as today and come BEFORE anything this change set adds.
- **Covered by the switch:** the selected observation is the automatic file, its `schema_version` is exactly `auto_v2`, its `season` equals Y, the switch state is `automatic`, and its `activation_id` equals the switch snapshot's.

**Known limits, by design (state them in the handover, do not work around them):**
- **No wake and no retry.** A refusal does not schedule anything. A pick is made when a later scheduled check runs after the operator has supplied an observation or switched the season; if no check remains, there is no pick that day. The command to re-run selection is change set 5.
- **A refusal can appear between selection and delivery** (a `revoke`, or midnight, between the two): the delivery path's own state read then raises, its caller alerts, and the selected pick is not delivered on that attempt. Callers outside an existing `except ContestStateError` (the orchestrator's later reads) propagate the error as they would any other `ContestStateError` today.
- **`revoke` does not use a no-replace system call** (ruling R31). Its target check and its rename are two steps: a file created at the stamped target name by another process between them would be replaced. The names carry a microsecond stamp and nothing else in the code writes them.
- **`bts run` and other non-scheduler entry points use the optional loader** and are not protected by this refusal, even when they post. Change set 6 owns the configuration and entry-point check.
- **`revoke` is not atomic and takes no lock.** Between its steps the season is revoked while the manual file or the saver flag is still in place. A fetch already running when it is issued can write the automatic file (it will carry the OLD `activation_id`, so it is not covered after a re-enable) and can re-create the saver flag. The runbook step (change set 6) is: stop the scheduler and wait for any fetch, then `revoke`, then `status`.
- **Live means the configuration says so,** not the delivery mode: private or research mode with `contest_state_required` or `contest_state_expected` set is refused in the same way, and without those settings a public or DM run is not protected. Change set 6 owns the configuration check.
- **`enable` is still the operator's statement,** and a restore done without `revoke` is not detectable.
- **The health alert of row 5 is the daily prompt** during the opening stretch: from midnight until that day's dated observation is entered it is CRITICAL. How often it is DM'd is the dispatcher's existing behaviour; change set 6 revisits it.

2.
