## Why
In a live configuration the day's pick needs a usable contest state: today's dated observation (`bts set-contest-streak --date …`) or a covered automatic reading (change sets 4a to 4b-2). If neither is there, the operator first hears of it when the FIRST lineup check refuses (`run_single_check` → the `contest_state` alert), which is 45 to 180 minutes before the first game, and a correction entered after the last check cannot produce a pick at all (change set 5b was not built: a restart is not a safe way to choose again, `build/cs5b-check/contract-check.md`). Likewise a stale automatic reading is first reported after the pick has gone out (change set 4c). The scheduler wakes hours earlier (`default_init_hour_et`, 10:00 ET, or an hour before an early first game) and fetches the schedule. This change set makes the scheduler look at the contest state THEN, once, and DM the operator, so the state can be put right before any check runs. It changes no decision, no check, no delivery.

## Definitions
- **The morning check** runs inside `scheduler.run_day`, once per call, directly after the scheduler state has been initialised and saved (`carry_forward_skip_state(state, previous_state)` then `save_state(state, picks_dir)`) and before the main loop. It runs only when ALL of these hold: not `dry_run` (that path has already returned); the schedule has at least one game (the no-games path has already returned); `_contest_state_required(config)` is true; the delivery mode is DM or public; `date` equals `_now_et().date().isoformat()` (read once; the same sample is the check's `now`); and `previous_state` is `None` or `previous_state.pick_locked` is false.
- **The morning status file** is `picks_dir.parent / "health_state" / "contest_morning_check_dm_delivery_status.json"`. It is used only by the refusal DM of row 2.
- **The stale warning's status file and key** are change set 4c's: `contest_stale_reading_dm_delivery_status.json` and `incident_key="contest_state:stale_reading"`.

## Known limits (state them in the handover; they are not findings)
- One morning refusal DM per ET date (its own file and key); the first refused lineup check still sends the existing alert, so a day with no usable state produces two DMs, hours apart, plus the end-of-day health DM. A failed morning send is retried only if `run_day` runs again that day.
- The check runs when `run_day` starts for the day: at the morning wake, or at any restart. On a day whose first game is early (a 06:10 ET start wakes at 05:10) the notice is short.
- It reads the state once. A state that goes bad later (a dated observation that is in effect at the check and lapses at midnight; a reading that turns stale during the day) is reported by the existing alerts and by 4c.
- A schedule whose games are all postponed still counts as having games.
- Private delivery and configurations where contest state is not required get no morning check. `run_day` called for a date that is not today gets none.
- It does not tell the operator the pick could not be re-chosen after a late correction; the runbook does (change set 6b-2).
