## Why
A required live decision refuses unavailable contest state when a check or fallback reaches the loader. A check with no predictions can skip that read entirely, and end-of-day health can report the first refusal. A covered automatic observation's recorded-at age is currently reported on confirmed stale delivery (change set 4c). There is no late re-selection mechanism (change set 5b was not built, `build/cs5b-check/contract-check.md`), so a correction entered after the last check cannot produce a pick. This change set uses the scheduler's existing startup, after the schedule fetch, for ONE best-effort snapshot of the contest state before the first lineup check, when time permits, and DMs the operator. Lead time depends on the slate, the schedule fetch and service startup: a normally idled night slate has hours, a thin slate may have minutes, and a due check has none. A same-day restart may be eligible. The morning refusal has a separate dedup file and key; existing immediate and end-of-day alerts still run. With a continuing refusal, successful alerts can include the morning DM, a check-time refusal, a missed-pick alert if an undelivered preview is present, and an end-of-day digest if its keys are not covered. Cron and prior-slate alerts are independent. The change set changes no decision, no check, no delivery.

## Definitions
- **The call site** is in `scheduler.run_day`, immediately after `carry_forward_skip_state(state, previous_state)` and its `save_state(state, picks_dir)`, and before the main loop. The existing gates apply: not `dry_run`, a nonempty schedule (both have already returned otherwise), `_contest_state_required(config)` true, the effective delivery mode DM or public, and `previous_state` is `None` or `previous_state.pick_locked` is false. `_now_et()` is sampled ONCE there, as `now`, for the date comparison, the margin, the decision read, the age calculation and the DM date. `first_check_et = min((run["time_et"] for run in runs), default=None)`.
- **The time margin** (the lead's ruling, in place of the contract check's supervised child process with a five-second deadline): the morning check is made only when `first_check_et` is not `None` and `first_check_et - now >= timedelta(minutes=MORNING_CHECK_MIN_LEAD_MIN)`, with `MORNING_CHECK_MIN_LEAD_MIN = 10` a module constant in `bts.scheduler`. With less lead (a due or nearly due first check, a thin slate just after wake, an empty plan) the check is skipped with one stderr line `  Morning state check skipped: first lineup check is due within 10 minutes.` (or `  Morning state check skipped: no lineup check is planned.` for an empty plan) and the loop is entered at once. Reason: the health DM transport can spend about 195 seconds in timeouts and backoff; ten minutes of lead keeps that from delaying the first check, without putting a process fork into the scheduler. The check runs inline, in the scheduler's own thread.
- **The helper** is `scheduler._morning_state_check(config, picks_dir, date, now, first_check_et)`. It returns at once, doing nothing, unless `date == now.date().isoformat()`. It then returns, doing nothing, when the date already has a scoreable decision (`daily_decision.load_decision` then `is_scoreable_commit`), or its pick file shows a confirmed delivery (`picks.pick_was_delivered`) or an unconfirmed attempt (`delivery_attempted`); the decision is consulted independently of the pick file, and an unreadable decision or pick file counts as "nothing found" for this purpose. Otherwise it calls `load_decision_streak_state(picks_dir, require_contest_state=True, now=now)` exactly once and applies rows 2 to 4.
- **The morning status file** is `picks_dir.parent / "health_state" / "contest_morning_check_dm_delivery_status.json"`, used only by row 2. **The stale warning's status file and key** are change set 4c's: `contest_stale_reading_dm_delivery_status.json` and `incident_key="contest_state:stale_reading"`.

## Known limits (state them in the handover; they are not findings)
- It is a snapshot. The first check reads the state afresh; a same-day manual write or correction, a dated observation lapsing at midnight, a fetch, a switch or flag edit, or the 14-hour boundary can change the later answer in either direction. An accepted morning state can still end in a skip or no delivery; an already-repaired state can receive a delayed advisory; a read during a `revoke` can accept a dated observation that a later check refuses.
- With less than ten minutes to the first planned check there is no morning check (a 06:10 ET opener, a thin slate whose start−180 check is minutes after the wake, any restart close to a check).
- Dedup is the dispatcher's, per ET date, in each lane's own file: a successful persisted send suppresses repeats across serialized restarts that day; a failed send, an abrupt exit after a send, or a missing, corrupt or unwritable status file can repeat it on every restart. Status writes are neither atomic nor locked across processes. A failed morning CRITICAL is retried on the next eligible start with the dispatcher's failure banner; a failed morning WARN is not bannered.
- The check runs inline: a slow DM transport delays entry to the loop by up to its own timeouts (about 195 seconds), which the ten-minute margin covers; there is no end-to-end deadline on file or DNS stalls (the systemd watchdog is the backstop, as for every other alert).
- A legitimate all-postponed nonempty slate can produce a false alarm. Private delivery, a configuration where contest state is not required, and a `run_day` for a date that is not today get no morning check.

## Amendment 1 (2026-11-18, after round 1 of the review: Codex BLOCK B1 to B3, Carbon BLOCK B1)
1. **Row 1's "any `BaseException`" is withdrawn.** The morning work contains ordinary exceptions only (`Exception`), at the call site and at both guarded stderr writes. A `BaseException` that is not an `Exception` (`KeyboardInterrupt` from the operator's SIGINT, `SystemExit`, `GeneratorExit`, an exception group holding one) is NOT caught: it leaves `run_day` exactly as it would on the base while the scheduler waits for its first check, before any further DM or check. Reason: nothing durable is in flight in the morning work, so swallowing an interrupt only hides the operator's cancellation. (Change set 4c's delivery work keeps its `BaseException` guards: there a pick is mid-send.)
2. **"An unreadable decision or pick file counts as nothing found"** means: any `Exception` raised by the helper's decision read or pick read (malformed shapes, wrong types, deeply nested JSON included) is treated as "nothing found" and the helper goes on to the state read.
3. **Row 2:** the dispatcher is called after the `ContestStateError` handler has been left, with the refusal carried forward only as the bounded text `ascii(str(error))[:800]`, so that a failed send cannot log the refusal again as exception context.
4. **Known limit added:** the ten-minute margin covers the DM transport's own timeouts and backoff (about 195 seconds) but not a peer that keeps a response alive a few bytes at a time; in the reviewers' simulations such a response delayed the first check by one to four minutes past its target. Only the systemd watchdog bounds it.
5. **Known, in code this change set does not touch:** a malformed `decision.json` for the day makes the lineup checks themselves raise; a status file that decodes to a non-object (`[]`, `null`) makes the dispatcher raise on every start until it is removed.
