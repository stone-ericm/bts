## Why
A day's pick lives in a file (`<picks_dir>/<date>.json`). Several paths deliver a pick from that file WITHOUT choosing it again: the fallback refresh when the re-prediction fails or returns nothing or returns the existing pick; `select_pick`'s returns of the existing pick; a restart; the catch-up branches of `bts run` and `bts orchestrate`. The delivery step reads the live contest state only to print the streak and to see that a live read succeeds; it does not ask what state the saved pick was chosen on.

The contract check reproduced what that allows on `main`: the 03:00 `bts preview` cron chose a double on last season's uncovered streak of 0 and saved it; the operator then supplied the day's dated observation (streak 56, saver used); the fallback's re-prediction failed; the scheduler DM'd both names with "Streak: 56", marked the pick delivered and locked it. Both legacy commands posted the same double publicly.

This change set records, on the pick file, the state the pick was chosen on, and makes every live outward delivery of a saved pick check it. It does not add a way to wake the scheduler or re-run selection on demand (change set 5b), and it does not change selection.

## Definitions
- **Live:** a scheduler or orchestrator whose `_contest_state_required(config)` is true; `bts run` when it is not a dry run (always, since change set 6a); `bts orchestrate` as the command (it is refused by 6a's gate unless contest state is required).
- **The state's identity:** `DecisionStreakState` gains two fields with defaults, `observation_kind: str = "model"` and `dated_identity: dict | None = None`, set by `load_decision_streak_state` from the observation it selected, using the snapshot and the pinned clock it already has: kind `"dated"` with `dated_identity = {"effective_date": <padded YYYY-MM-DD>, "active_streak": <int>, "best_streak": <int>, "saver_state": <str>}` for a dated observation in effect; `"automatic"` when the selected observation is the automatic FILE (decided by the file, not by `source`); `"legacy_manual"` when it is a manual file that is not a dated observation; `"model"` when there is none. `dated_identity` is `None` for the last three. Nothing else about the loader changes.
- **The chosen-on record:** a new field of `DailyPick`, placed LAST, `chosen_on: dict | None = None`. A VALID record is a `dict` with exactly the keys `schema`, `required`, `kind`, `streak`, `saver_available`, `dated`, where: `schema` is exactly `"bts_pick_chosen_on_v1"`; `required` and `saver_available` are `type is bool`; `kind` is one of the four strings above; `streak` is `type is int`, `0 <= streak` (and `<= 57` when `kind` is `"automatic"` or `"dated"`); `dated` is `None` unless `kind` is `"dated"`, in which case it is a `dict` with exactly the four keys of `dated_identity`, a date string that parses and round-trips as padded `YYYY-MM-DD`, counts that are `type is int` with `0 <= active_streak <= best_streak <= 57`, `active_streak` equal to the outer `streak`, and a `saver_state` among `not_earned`, `active`, `used`. Anything else, including a missing key or `null`, is NO record.
- **A fresh choice:** a `select_pick` result that has BOTH a policy decision (`sel.decision is not None`) and a pick (`sel.pick_result` with a `daily`). That includes singles and doubles from the MDP and from the heuristic. A skip has a decision and no pick. All four returns of the existing pick are REUSE, not a fresh choice.
- **Matches** (a record, a live decision state): the record is valid AND `required is True` AND either (a) the state's kind is `"dated"`, the record's kind is `"dated"` and the record's `dated` equals the state's `dated_identity`; or (b) the state's kind is `"automatic"` and the record's kind is `"automatic"`. Nothing else matches. Under (b) the streak, the saver, the activation and the season are deliberately NOT compared, and a pick chosen under an automatic reading matches again after a dated override lapses (ruling R33). The comparison is with the state the delivery read returned; there is no transaction with what happens after that read.
- **A saved pick, at a send:** every pick EXCEPT one for which the caller hands the delivery function the fresh selection of this same cycle whose `pick_result.daily` IS the object being sent (identity, `is`). A pick reloaded from its file, or sent with no selection in hand, is saved.

**Known limits, by design (state them in the handover, do not work around them):**
- **A refusal does not choose again.** The pick stays on disk and the day stays unlocked; a later scheduled check or a fallback refresh that succeeds may replace it. If the re-prediction keeps failing, or no check remains, the day has no pick: the alert says why, the missed-pick DM (row 10) still fires, the end-of-day record is written only for a genuine skip, and `bts day-outcome` reports `no_decision` the next morning. A way to force a check is change set 5b.
- **Under an automatic observation nothing but the kind is compared** (definition (b), ruling R33): a saved pick chosen at one automatic reading can go out after a fetch, a saver-flag edit, or a `revoke` followed by `enable` and a fetch has changed the reading. Its worst case is a double chosen at a low automatic streak going out at a high one after a failed re-prediction. That is today's behaviour for automatic readings, kept on purpose so that ordinary in-season days do not lose picks.
- **A preview's pick is never deliverable live, even when the state it read was the same as the live one.** If the first live selection of the day also fails, the day has no pick.
- **A dated pick loses its match at midnight ET** with the observation, and after any correction of the four values.
- **Private delivery and configurations that are not live are not checked.** `check-pick-entered`, incident alerts and the dashboard can still show a saved pick's names.
- **A pick file written before this change set has no record** and is refused for live outward delivery until it is chosen again.
