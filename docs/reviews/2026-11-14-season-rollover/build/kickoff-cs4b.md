## Why
The automatic contest observation (`account_state/contest_streak.json`, written by `bts fetch-contest-streak`) does not say which season it belongs to, and nothing in the code can tell: nobody has seen what MLB's endpoints return across a season boundary, and three rules that tried to infer it from dates and local files failed review (ruling R23). The ruling that replaced them (R24): **an automatic observation is used for a live pick only after the operator has looked at what the endpoints return this season and switched that season to automatic.** Until then the live pick runs on the dated observation of change set 4a, or there is no pick.

This change set adds the switch (one small file per season, three commands), makes the fetch stamp the season on what it writes and write the observation only once the season is switched, and makes the LIVE decision refuse an automatic observation the switch does not cover. Non-live reads (previews, dry runs, private research mode) are unchanged.

## Definitions
- **One clock per operation.** Each new command, the fetch's NEW steps (rows 4 and 7), and each call of `load_decision_streak_state` and `health/contest_state.check` use ONE timezone-aware `now` (the caller's when supplied, otherwise one wall-clock read) for every season decision this change set adds. Code this change set does not touch keeps its own clock reads. **Y** is the calendar year of that `now` in `America/New_York`.
- **Timestamp grammar:** as in change set 4a (a `str`; a trailing `Z` read as `+00:00`; accepted by `datetime.fromisoformat`; timezone-aware).
- **The switch file** is `account_state/season_contract.json`. It is **valid** when, checked in this order (the first failure is the one reported): (1) it is readable, UTF-8, JSON and an object (change set 1's `_UNREADABLE` handling); (2) `schema_version` is exactly `"bts_season_contract_v1"`; (3) `season` is `type is int`; (4) `status` is exactly `"automatic"` or `"revoked"`; (5) `switched_at` is `null` or in the timestamp grammar, and is not `null` when `status` is `"automatic"`; (6) `revoked_at` is `null` or in the timestamp grammar, and is not `null` when `status` is `"revoked"`; (7) `note` is absent, `null` or a `str`. Other keys are ignored.
- **Switch state for Y**, decided by ONE function used by every row: `absent` (no file), `corrupt` (the file exists and is not valid: an error, never "not switched"), `other_season` (valid, `season != Y`), `revoked` (valid, `season == Y`, revoked), `automatic` (valid, `season == Y`, automatic). **Season Y is switched to automatic** exactly in the last state.
- **A season-stamped automatic observation** is `contest_streak.json` whose `schema_version` is exactly `"bts_contest_streak_auto_v2"`: the `auto_v1` properties plus `"season"` (`type is int`), the Y of the fetch that wrote it.
- **Live** means `require_contest_state=True`.
- **A dated observation in effect:** as defined and implemented by change set 4a (`dated_observation_in_effect`).

**Known limits, by design (state them in the handover):**
- `enable` is the operator's statement after looking at `status`; the code does not verify what MLB's endpoints mean. If the counters are carried over from last season, switching makes the live pick run on them. The opening-stretch procedure (dated observations until the readings have been watched for some days) is the protection.
- Between `enable` and the next successful fetch there is no season-stamped automatic observation; a live pick in that window needs today's dated observation.
- A restore done without `revoke` is not detectable.
- Non-live reads still use whatever automatic file is on disk.
- During the opening stretch the health check reports the refusal as CRITICAL from midnight until that day's dated observation is entered. That is the daily prompt to enter it; how often it is DM'd is the existing dispatcher's behaviour and is revisited in change set 6.
- `revoke` does not touch the automatic file: it stays on disk, unused by live decisions until `enable` and a new fetch, still read by non-live paths.
