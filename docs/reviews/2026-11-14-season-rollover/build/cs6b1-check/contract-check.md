## Production start and lead time

**NOTE · Lifecycle.** `compute_wakeup_time` uses `min(10:00, first pitch − 60m)` with defaults, including games before 11:00. Previous `run_day` looks ahead, saves the wake for a games day, finishes polling and health, then `_idle_until_next_wakeup` watchdog-sleeps to it and exits. The off-day branch also looks ahead and idles, without EOD. An empty lookahead uses the next 10:00, a past wake with games uses now +1m, and a failed lookahead uses now +15m. If EOD overruns a stored wake, idle returns immediately with a warning. The user unit runs `bts schedule` without `--date`, `Restart=always`, `RestartSec=30`, `Type=notify`, `WatchdogSec=1800`. There is no startup wait in `bts schedule` or `run_day`. The CLI captures the launch ET date before loading TOML. 23:40 selects that evening's date and meets the same-date guard if still before midnight. 23:59:59 with a two-second load keeps the old date and fails the guard. 00:00:01 starts the new date immediately, satisfying the guard. The guard normally holds at a real morning handoff. A launch/fetch crossing midnight or an explicit other slate date can fail it. A pre-midnight wake for a hypothetical sub-01:00 next-day start would launch the old date.

**NOTE · Earlier placement.** The previous night's run can tell an operator when to look tomorrow. It cannot judge tomorrow's dated observation, which can only be entered for today ET, and a fetch can change the answer overnight. An extra readiness check after the previous run is optional. Keeping the existing wake is enough for a startup snapshot, with zero guaranteed lead on overdue checks. R36 needs no reminders, action-change keys, special saver logic, restart advice, or extra re-selection path from design §2.4/R34.
