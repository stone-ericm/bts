## Why
A covered automatic observation can remain eligible regardless of the age of its `recorded_at`. The loader and the end-of-day health check report settlement coverage (counted in settled local pick files), not age. Fetch cron runs at 01:10, 02:10, 10:30 and 13:30 in the host's ET timezone. Handled fetch failures leave the accepted automatic file in place and replace the fetch status with the latest error and the DM cooldown stamps. A configured fetch-failure DM can arrive at the failing invocation, at most once per six hours per category for successful sends. A write-stage exception can leave a partially completed update. The owner's decision (design record `design/design-v3.md`, "Owner decision"; rulings R28 and R35): a pick on such a reading is **still made and delivered**, the operator gets **one warning DM per date**, and the pick **records** what it ran on, with "stale" judged **by time**. This change set adds a delivery-age record and a best-effort warning tied to the pick that goes out. Selection and delivery eligibility follow the existing rules.

This change set does not change selection, the loader's `status`, the health check, the fetch, or any refusal.

## Definitions
- **`AUTOMATIC_READING_STALE_HOURS = 14`**, a module constant in `bts.contest_state`.
- **The reading record**, `bts.contest_state.automatic_reading_record(s, now)`: takes an aware, UTC-representable `now`, uses no clock and no I/O, and returns `None` for kinds other than `automatic` (`s.observation_kind`). For automatic: keep `s.contest_recorded_at` exactly if it is a `str` of at most 128 printable ASCII characters (U+0020 to U+007E), else use `None`. Parse that string with Python 3.12 `datetime.fromisoformat` (including a terminal `Z`). A missing value, a failed parse, a missing offset or an overflow when normalizing to UTC gives `reason="unreadable"` and `age_hours=None`. Otherwise subtract the two UTC instants as `timedelta`s: `reason="future"` if the elapsed time is strictly below −5 minutes, `"old"` if strictly above 14 hours, and `None` otherwise. `age_hours = round(elapsed.total_seconds() / 3600, 2)`, for display only. Return exactly these keys in this order: `schema` (`"bts_pick_automatic_reading_v1"`), `recorded_at`, `age_hours`, `stale` (`reason is not None`), `reason`. The function accepts every real loader result with a valid caller `now`.
- **The record validator** (one function, used by all three pick loaders): accept only a dict with exactly the five keys and the schema above; a `recorded_at` of `None` or the bounded exact string above; an exact `bool` `stale`; a `reason` of `None` or one of the three exact strings; `stale == (reason is not None)`. For `unreadable`: `age_hours is None` and an unusable reading time (as the reading record defines usable). Otherwise: a usable reading time and an exact, finite `float` `age_hours`, rounded to two places, of absolute value at most 87,660,000. Rounding permits `14.0` with `old` or with no reason, and `-0.08` with `future` or with no reason: accept `old` at `age_hours >= 14.0`, `future` at `age_hours <= -0.08`, and no reason on `[-0.08, 14.0]`. A valid record is returned with its fields in the order above; a missing or invalid decoded value is `None`. Whole-file decoder behaviour is as it is today.
- **A qualifying attempt**: inside `scheduler._deliver_and_lock_pick`, a required (`_contest_state_required(config)`) DM or public delivery after the existing 5a check (or the same-cycle exemption), the formatting, the DM-mode recipient check and that branch's FINAL cutoff check have all succeeded.

## Known limits (state them in the handover; they are not findings)
- The warning arrives after the pick has gone out; a correction afterwards does not change that day's pick. An earlier warning (at the morning schedule fetch) is change set 6b.
- With a readable, writable status file and serialized scheduler calls, successful stale warnings dedup per warning ET date (key `WARN_ATTENTION:contest_state:stale_reading`, in its OWN status file, so it never touches the existing health DM dedup record). A failed warning can be retried on a later eligible call; it is not resurfaced. A process crash or a lost status file can lose the warning or allow a duplicate. There is no replay and no exactly-once guarantee. With no recipient configured nothing is sent.
- The rule measures the age of the last accepted fetch, not whether MLB's counter is right: missed refreshes warn even if the value is still correct, and a reading can be fresh and wrong (MLB has not settled last night's round; the loader's `lagged` / `stale` status describes that and is not alerted here).
- `recorded_at` is the fetch command's start time, not the response time.
- 14 hours is a constant, not configuration. The legacy commands do not warn. A pick delivered under a dated observation records `null`.
