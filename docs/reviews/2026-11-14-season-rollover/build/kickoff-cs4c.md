# Change set 4c of the season-boundary build: a pick delivered on a stale automatic reading (draft 1)

**Tier A** (the delivery point of the pick path). Base: `main` at the commit named in the author's brief (it contains change sets 4a to 6a and 5a). One commit on branch `sb-cs4c`.

## Why
Once the season is switched to automatic, the live decision uses `account_state/contest_streak.json` as long as its schema, season and activation identifier match (4b-2). Nothing looks at how OLD that reading is. The loader's `fresh` / `lagged` / `stale` status counts settled local pick files, not hours, changes no behaviour, and is not alerted when stale by an unconfirmed miss; the health check's lag warning is logged only. If the fetch cron (01:10, 02:10, 10:30, 13:30 ET) fails for a day, the evening's pick is chosen on yesterday's reading and nobody is told. The owner's decision (design record `design/design-v3.md`, "Owner decision"; ruling R28): such a pick is **still made and delivered**; the operator gets **one warning DM per date**; and the pick **records** what it ran on. "Stale" is judged **by time** from the reading's own `recorded_at` (the time of the last accepted fetch), never from local pick files.

This change set does not change selection, the loader's `status`, the health check, the fetch, or any refusal.

## Definitions
- **The reading's time**: the `recorded_at` string of the automatic file the live decision selected, parsed with `datetime.fromisoformat` (an exact `str`; a trailing `Z` is accepted by Python 3.12). It is **usable** only if parsing succeeds and the result is timezone-aware.
- **`AUTOMATIC_READING_STALE_HOURS = 14`** (a module constant in `bts.contest_state`; the design record's value: longer than the longest gap between two scheduled fetches, 13:30 to 01:10, plus slack).
- **The reading record** for a decision state `s` at an aware instant `now`, `bts.contest_state.automatic_reading_record(s, now)`: `None` unless `s.observation_kind == "automatic"`. Otherwise a dict with exactly these keys, in this order: `"schema": "bts_pick_automatic_reading_v1"`, `"recorded_at"` (the raw string, or `None` when the file had none or it was not a string), `"age_hours"` (a float rounded to 2 places, `(now − reading's time)` in hours, or `None` when the time is not usable), `"stale"` (bool), `"reason"` (`None` when not stale; else exactly one of `"unreadable"` (time not usable), `"future"` (reading's time more than 5 minutes after `now`), `"old"` (`age_hours` strictly greater than 14, compared before rounding)); the reasons are tested in that order and the first that holds wins. The function is pure: no file, no clock (it uses the `now` it is given), and it never raises for any decision state the loader can return.
- **A live outward delivery**: inside `scheduler._deliver_and_lock_pick`, contest state required (`_contest_state_required(config)`) and delivery mode DM or public, at the point directly after 5a's saved-pick check has passed (or was skipped for a same-cycle fresh choice) and before the delivery text is formatted.

## Known limits (state them in the handover; they are not findings)
- The warning arrives at delivery, when the pick is already going out; a correction afterwards does not change that day's pick (change set 5 limits). An earlier warning (at the morning schedule fetch) is change set 6b.
- One DM per ET date for this key (`WARN_ATTENTION:contest_state:stale_reading`), by the dispatcher's existing per-day dedup; a failed send is resurfaced by the dispatcher's existing rule. If the recipient is not configured nothing is sent.
- A reading can be recent and still wrong (MLB has not settled last night's round): the loader's `lagged` / `stale` status still describes that and is not alerted here.
- 14 hours is a constant, not configuration.
- The legacy commands do not warn.
- A pick delivered under a dated observation records `null`.
