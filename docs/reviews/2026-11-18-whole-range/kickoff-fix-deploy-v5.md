## Rulings (bts-wr-fresh3 under the lead's delegated design authority; Eric can overrule)
- **V1, one hold record with an `activating` state (settles r4 "E3 and material 4" and "E3 — abandoned activation").** States: `pending` → (all checks passed) `activating` → (activation verified) the record is unlinked; any failure → `failed`. The record carries the owner's identity: `deploy_id` and the owner unit name `bts-deploy-<deploy_id>.service`. **Owner alive** means BOTH: a non-blocking shared `flock` on `transaction.lock` fails with `EWOULDBLOCK`, AND `systemctl show bts-deploy-<deploy_id>.service -p ActiveState --value` (system scope, read-only, bounded) is `active` or `deactivating`. `check-clear --scheduler` and the cron gate return clear for `activating` only while the owner is alive; for `pending`, `failed`, `activating` without a live owner, and unreadable records they return held. A new deploy's preflight that finds `activating` or `pending` with no live owner first reconciles it to `failed` (step `abandoned`), stops and verifies the scheduler and pages, then refuses (`DEPLOY NOT STARTED — abandoned … reconciled`); the next deploy proceeds over the `failed` record. There is no separate activation file.
- **V2, the completion hook.** The owner unit is started with `--property=ExecStopPost=/usr/bin/python3 -I /usr/local/bin/bts-deploy-hold reconcile --deploy-id <id>`. `reconcile` acts only on this deploy's record: `pending` or `activating` → `failed` (step `owner-ended`), stop and verify the scheduler, one page (unless the owner's own E4 already recorded its page for this deploy); unlinked or `failed` → no-op. It is idempotent and never touches another deploy's record.
- **V3, recovery authorization (settles r4 "E1 — compatibility and window").** When the heartbeat is absent, stale or unreadable, preflight refuses (`window`) unless the run is a `workflow_dispatch` whose new input `recover_sha` equals `TARGET_SHA` exactly (40 hex). The input is added to `deploy.yml`'s `workflow_dispatch.inputs` (a file change, not a GitHub setting) and passed into the SSH environment through `envs`. A push never carries it. INCIDENT §5 says Eric supplies it only after verifying any earlier send and entry and the window, and that `recover_sha` authorizes exactly one target.
- **V4, entry reminders during a hold: NOT built.** r4's G3 cron/timers row asks `check-pick-entered` to require delivery evidence before an actionable reminder while held. Ruled out: the command's message for a delivered, unentered pick is the one Eric most needs during an incident; changing its evidence rules is its own change set. Cost if wrong: during a hold, a stale or privately committed record can still produce the same reminder it would produce without a hold (today's behaviour). Ledger it.
- **V5, the uv check.** The hand release verifies dependencies with `uv sync --locked --check --offline --extra model` as `bts` (bounded); ANY non-zero exit, including a usage error from a uv that lacks `--check`, refuses with the fixed message `hand release refused: the environment could not be verified as synced for <7 hex>; use a deploy`.
- **V6, imports.** `bts deploy-canary` imports `bts.scheduler` and `bts.model.predict` (there is no `bts.predict`; r4 E6 is right) and the lazy backends the configured scheduler needs, without calling any scheduler entry point.

## Amendment 1 (2026-11-20 14:00, on the author's design checkpoint `WRDDESIGN-a7030f2b`)
- **V9, containment is finished by whoever finds it unfinished.** E4 keeps its order (durable `failed` record first, so every gate closes, then stop and verify, then the page). The owner records per-run evidence `/var/lib/bts-deploy/run-<id>.evidence` (fsynced): `stop` = `verified` / `unverified` / `not-attempted`, `page` = `attempted` / `not-attempted`. The V2 hook and the V1 abandoned-reconciliation path act on a `failed` record of THEIR run (hook) or of the abandoned run (preflight) whenever that evidence shows `stop` not `verified` or `page` `not-attempted`: they finish the stop and verification and make the one unclaimed page attempt, then update the evidence. "Unlinked → no-op" stands; "`failed` → no-op" now means "failed with complete evidence".
- **V10, the monitor during a live activation.** A readable `activating` record whose V1 owner is alive and whose `armed_at` is within the owner budget (23 minutes) suppresses pings exactly as a young `pending` does (no success, no `/fail`; the in-progress line names the run). Anything else pages.
- **V11, after a release.** Both releases (the deploy's verified unlink and the hand release) first write `/var/lib/bts-deploy/last-release` (fsynced; `released_at` UTC epoch, `kind` `deploy` or `hand`, `deploy_id`). With no hold entry, the monitor sends a success ping only if the heartbeat is fresh by the base rules AND its `timestamp` is later than `released_at`; otherwise it pages `/fail` with `Deploy hold released at <UTC ISO> (<kind>); no scheduler heartbeat since. See INCIDENT.md §4.` When the file is absent the monitor is byte-identical to the base. Durable unlink plus the per-run evidence (activation `verified` recorded before the unlink) is sufficient proof of a verified activation; the result file is reporting only.
- **V12, unheld cron jobs and the venv.** Every UNHELD `uv run` cron line gains `--no-sync` (`uv run --no-sync …`), so no unheld job can sync the project environment while a deploy resets and syncs it; nothing else in those lines changes. The four held commands are unchanged inside their gate. Insulation from the reset itself (an unheld job loading partly replaced code during the build phase) is NOT built: ledgered (those jobs write no pick, result, streak or contest state).
