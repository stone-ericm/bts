# NOT YET

**MUST FIX — job-switch recovery needs proof that the box was fenced.** V2 switches jobs at the right time on a verified box. C1d then waives job verification whenever the record is absent and *any* failed hold exists. A failed hold proves neither what cron can launch nor that another unit cannot start. Losing the record after a canary failure and restoring an old crontab now admits a reset with an ungated writer. C1a also mistakes a failed switch that already installed cron for a never-provisioned box, so it can refuse the fingerprint refresh needed to fix forward.

**Smallest design change.** Keep the owner’s switch. Before invalidating `installed.json`, fsync a root-owned switch checkpoint in the existing per-run evidence. Bind it to the run, the verified old installation or first-provision fence, and the approved before/after bytes of each job artifact by hash. Admit missing-record recovery only if the checkpoint accounts for the actual partial installation, or if the explicit first-boot fence still holds. Keep fingerprint, legacy-unit, environment and window checks on both paths. Preserve the checkpoint across abandonment and pre-arm failures, and retire it only after the new record is durable. A missing record with an unrelated hold requires verified provisioning or repair. The installer uses this distinction too.

## 3. Manager environment

**MUST FIX — unstable input and circular recovery.** A lingering user manager can retain values imported in one session and lose them on restart. A normal SSH agent setup can import a different `SSH_AUTH_SOCK`; local graphical or operator sessions can import display variables. This does not happen on every login. The source is the manager’s current environment, not a stable settings file. A harmless added value changes the digest; an intentionally changed `UV_PROJECT_ENVIRONMENT` also changes it. In both cases C1d refuses before `install-jobs`, so “followed by a deploy” cannot record the change. The probe hashes representative output only. Debian 12 import/reload/reboot behavior remains for A7, as does its exact byte order.

**Smallest stable alternative.** “Certify the exact approved service/monitor environment inputs, with fixed launch values for settings that select the runtime or guard. Compare those stable bytes and verify the effective values in A7. Exclude session-only manager values from the proof. If approved runtime values remain inherited, specify and compare a sorted projection of just those names from the manager interface, and test that uncovered variables cannot change these execution paths. Keep the separate legacy test-root refusal. An approved change to a covered value is staged and applied within the held transaction, with the old approved values checked at admission and the new values checked before activating. Hand release validates the current values. Keep secrets out of logs.” Include actual `.env` inputs, including the monitor’s target, and use the same policy for scheduler, dashboard, canary and render.
