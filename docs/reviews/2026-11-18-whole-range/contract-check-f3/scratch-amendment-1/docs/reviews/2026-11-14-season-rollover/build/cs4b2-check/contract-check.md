Carrying an old activation in a REVOKED tombstone cannot authorize anything. Every changing enable issues a fresh one; no-op enable retains it. Restoring only an OLD automatic file after re-enable cannot cover it. Restoring an old matching SWITCH+automatic pair, or the old automatic switch beside that old observation, can cover it again; enable then no-ops. That is a restore overwriting the revocation, requiring revoke AFTER restore, and is the named undetectable-restore limit. A fetch begun before revoke retains the old ID and cannot cross a later fresh enable; a fetch begun after enable can install matching bytes even if it later exits 1. Real pre-replacement failure stayed mismatched; real post-replacement status failure left an accepted matching observation.

For EVERY row above, operations factor independently: valid-argument revoke writes a same-Y valid revoked snapshot then quarantines manual/saver; enable no-ops only on automatic, otherwise generates a new ID and leaves observations/saver alone. Fetch's prior-account/auth/response errors come first; after validation it writes matching v2/status/ledger/conditional saver when automatic, status+ledger only when absent/other_season/revoked, and failure status/possible DM when corrupt. Manual precedence does not alter fetch writes. Status remains inspection plus actual-live evaluation; it neither repairs nor authorizes an operation.
The deliberate one-selected-observation simplification is **safe under these predicates**, merely less informative than inspecting both. Concrete sequence: expired legacy streak 12 beside covered automatic streak 7 selects 7 and accepts; health retains its expired-manual WARN. The expired statement no longer overrides automatic authority. With an absent/revoked/old switch the SAME sequence refuses reason 3; with unexpired legacy it refuses reason 2; with corrupt auto it raises. This cannot launder an uncovered automatic file. Rejecting merely because an expired manual exists would impose an additional policy absent from R24/R30.
