**M1 — MUST FIX, design: season equality cannot enforce the promised post-enable fetch barrier.**
Row 9 accepts any parseable current-season auto_v2 beside an automatic switch for Y, regardless of switched_at, revoked_at or recorded_at. The probe's June 1 auto_v2 satisfies those predicates beside a July 15 re-enable. Thus row 2's “until then a live pick needs today's dated observation” and the final known limit's “until enable and a new fetch” are false for re-enablement, repaired/corrupt switch files, and same-season restored snapshots. This is not the named inability to detect a restore performed WITHOUT revoke.
Concrete compliant recovery: stop services, restore an earlier Y snapshot (automatic streak 7), revoke, verify MLB and enter today's dated streak 12/saver used, manually fetch 12 while revoked (ledger/status only), inspect it, enable, restart services, then suffer a failed fetch. Tomorrow the dated observation lapses and row 9 silently accepts the restored 7. The operator supplied the observation and used revoke, yet gets a wrong live streak. Even without a restore, re-enablement can reactivate the very observation being distrusted. The larger enable transaction promoted the inspected attempt before enabling; this design never connects that evidence to the accepted file.
Smallest design change preserving one-file enable and avoiding timestamp ordering: add an **activation identifier** to the switch, issue a fresh identifier on every enable that changes a nonautomatic state, stamp it on a switched fetch, and require equality as well as season equality for live acceptance. Missing/different identifiers require a successful new fetch or today's dated observation. Define no-op enable to retain its identifier; cover malformed identifiers in ordered validation. This changes the state model; alternatively invalidating the automatic file at enable changes its one-file write contract. The lead must choose and revise rows 2/4/8/9 and the limits before commissioning. Merely deleting the post-enable promise accepts the wrong-state recovery above and does not preserve its intended protection.

**M2 — MUST FIX, rows 2–4: failure, crash and concurrency guarantees are incomplete.**
Actual success order is observation → status → ledger append → conditional saver (`cli.py:2211–2242`). Injected failures at each stage exit 1 without _fail/DM; status can already claim success when ledger or saver fails. Saver transitions also create a lock and append their best-effort audit. Removing the observation write removes its incidental creation of account_state: a cold not-switched ledger append now fails unless its parent is created explicitly.
Replacement failure/concurrency definition:
> Guarantees concern each invocation's completed writes, without another writer; atomic_write_text protects one replacement, not a transaction or power-loss durability of directory entries. Before enable/revoke, stop and wait for the scheduler, fetch and other account-state writers; after a restore, revoke before restarting any of them. No command cancels a decision/fetch that already read state. Concurrent enable/revoke is last-replacement-wins; a captured automatic fetch may finish after revoke, and a decision may finish on its earlier manual/automatic snapshot. These are not serialized by the saver's separate lock. Status is an inspection of snapshots, not an atomic cross-file view. Enforce stronger guarantees only by adding shared serialization to the design.
Replacement row 2 failure/success clauses:
> A failed write before replacement exits 1 and, without another writer, leaves the prior switch unchanged. Successful replacement installs this invocation's switch even if output is interrupted; a retry recomputes state and can no-op. A no-op reports the valid snapshot it read, not a guarantee about the pathname at exit. No-op enable ignores a newly supplied note. Other application state files are untouched; temporary-file creation/removal is part of the switch write.
Replacement row 3 sequencing/failure clauses:
> Validate arguments first. Write (a), then attempt (b); on failure of (b), stop without attempting (c). On successful/absent (b), attempt (c). Do not roll back completed steps. Use UTC for revoked_at and convert the captured now to UTC before formatting the shared rename stamp. With producers quiesced, check targets and never replace an existing target, including a dangling symlink; an existing target is a failure only for a source that needs moving. A rename failure leaves that source in place; report every completed rename, the failed step and any unattempted step. After (a) the switch snapshot is revoked, but today's manual observation can STILL authorize decisions until (b) succeeds; after (b) automatic decisions refuse, while the old saver can remain until (c). Crash/retry has exactly these partial states; retry uses a new stamp/reason/time and does not repair missing history. Report “this invocation wrote revoked”, not irrevocable global state. Success explicitly says today's dated observation was removed and today's undelivered pick now needs a replacement observation; print the dated command template and enable command. The saver warning appears only on health paths that reach the flag block, not unconditionally after revoke.
Replacement row 4 persistence clauses:
> After validation and one switch snapshot, automatic writes observation, then success status, then ledger, then conditionally invokes saver earning; not-switched writes success status then ledger and never reads/writes the saver or observation. Create account_state before appending. Stop at the first persistence failure: exit 1, name completed steps, and state that observation/status/ledger/saver may disagree. Do not roll back, promise no partial append, or call this a clean fetch rejection. A failed append may leave a fragment; retry can append another snapshot, and ledger order need not equal observation replacement order. Saver lock/write errors may propagate as persistence failures; its existing audit-append failure remains logged/best-effort. Crashes leave the completed prefix. Define application-state write spies to allow helper temporary files and, on automatic saver transitions, the existing saver lock/audit files.
The larger shared state lock prevented a late fetch from undoing quarantine. Ran the real helper after renaming a used flag: best 7 recreated not_earned, policy saver True. Interleaving deduction: fetch captures automatic/best 7; revoke quarantines used; fetch resumes and recreates not_earned; after re-enable a later best ≥10 can promote active despite the verified used observation. This can produce a wrong saver/live pick, not merely untidy evidence. The quiescence requirement above must be explicit for all revocations, not just the restore procedure. Revoking mid-selection cannot retract a DM already sent; a dated writer running after quarantine can legitimately recreate today's authority.
Another interleaving: enable reads revoked, revoke writes its new revoked record, enable replaces it with automatic, revoke completes both renames and prints “IS revoked”. The printed global claim is false; no-op enable/status can likewise report a snapshot already replaced. Two same-clock revokes can target the same quarantine name; check-then-rename is safe only under the stated serialization, not against a concurrent target creator. If the intended CLI must guarantee quarantine against concurrent commands, the small design needs shared locking as well as M1; wording alone cannot supply it.
