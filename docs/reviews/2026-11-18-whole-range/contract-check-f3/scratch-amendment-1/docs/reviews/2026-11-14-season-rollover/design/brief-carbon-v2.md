Your design (`design-carbon.md`) was attacked (`design-attack-codex.md` in the repository root of this copy) and the lead has ruled (`docs/reviews/2026-11-14-season-rollover/design/RULING-R24.md`). Write `design-v2.md` in the repository root: the specification an implementer who has seen none of this could build from. No code in tracked files. The rules of your first brief still apply (read the real code for every claim about current behaviour, say what you ran, no network, say "unsure" where you are).

If you think a ruling is wrong, say so in a section of its own with a concrete counterexample; do not silently build something else.

## Contents
1. **Records and formats.** Exactly what is stored and where: the attempt record (what each fetch response contained and the mapping it used) apart from the last accepted observation; the manual observation for one contest date (streak, best, saver state, who and when); the season-scoped marker that says the automatic counter may be trusted, and what setting it requires; the restore acknowledgment; how the saver's continuity is marked unverified and reconciled. For each: file, fields, who writes it, what a reader does when it is missing, malformed, from another season, or older than it should be.
2. **The decision table under R24.** Every input combination to its outcome: the streak used, the saver passed to the policy, whether a pick is made, the alert (log line or DM, through which existing mechanism, at what moment), and the exact recovery command. State the precedence where two rows could both apply. No row may depend on which local pick files exist, and none may end in a refusal without a recovery that actually runs another selection.
3. **Operator commands.** Name, arguments, what each refuses, idempotency, and the command that re-runs selection after a recovery with its latest useful start. Say which already exist on `main` and which are new. Then the edits to `docs/ops/2027-season-start.md` (the rows that really cover this: check the file, the earlier draft cited the wrong row).
4. **The switch to automatic.** What the operator is shown before switching (for example the recorded attempts across the opening days beside the season's own entries and results), what the command checks and refuses, and how the switch is undone. The switch is an explicit act; do not replace it with an inference.
5. **How each finding is closed.** F1 to F6 and every row of the attack's decision-table coverage and operator-mistake tables: the part of this specification that closes it, or why it stays open.
6. **Change sets, smallest first.** For each: the files, the behaviour in a few lines, the RED tests as one line each (state, expected outcome), and the false green the attack named that each test must not be. Mark which depend on the unmerged extra-attempts work (`sr-lastcheck`), which must be live before the first pick of 2027, and which can go first because the attack left them standing (defensive reads including a corrupt `streak.json` beside a valid observation; the `streak.json` season tag on real legacy bytes; the saver mapping and the `not_earned` 10 to 15 warning).
7. **Questions only the owner can answer,** in plain words, each with the default the build uses until he answers.

Keep it under 350 lines. When the file is complete, print `SRD3-<first 8 hex characters of the sha256 of design-v2.md>` and then `DONE`.
