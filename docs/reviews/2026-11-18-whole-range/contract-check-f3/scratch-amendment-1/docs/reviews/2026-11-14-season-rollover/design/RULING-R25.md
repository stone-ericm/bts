# Ruling R25: what changes in the build specification after its check (lead session, 2026-11-14 late evening)

Input: `design-v2-check-codex.md` (marker `SRD4-3b8fca37`), verdict NOT YET for change sets 4 to 6, with the frame of R24 kept. Its eight findings are accepted except where narrowed below. Change set 1 is already being built from a narrower contract (`../build/kickoff-cs1.md`) that keeps dated version-1 files readable, which is what finding C1 asks for.

| # | Finding | Ruling |
|---|---|---|
| C1 | Early change sets reject formats whose writers arrive later | Accepted. Every change set states what it still reads and writes from before it, and a strict reader is switched on only in or after the change set that ships its writer. Nothing relabels a version-1 observation as verified. |
| C2 | `retry-pick` has no result contract and its latest start leaves no time to enter the pick | Accepted. The latest start is computed from the cascade budget the scheduler actually uses, plus the existing operator reserve, against the earliest cutoff among the pick's games; the command reports what happened (picked and delivered, picked and not delivered, skipped by policy, no predictions, refused) with a distinct exit code for each, and never reports success for an attempt that delivered nothing. |
| C3 | A lock alone does not stop the daemon overwriting what a retry committed | Accepted. The specification defines one transaction for a check (take the lock, reload state from disk, decide, write, release) used by the daemon's checks, fallbacks and end-of-day writes and by the retry. A finalized skip is reopened only by a named operator action, stated in the recovery text. |
| C4 | Restore safety is promised without a restore procedure | Narrowed. No new restore command and no restore-state file. A restore is handled by what the design already has: the runbook's restore procedure stops the scheduler and the fetch, restores, then revokes the season contract, so the next pick needs an explicit observation for its date (streak, best and saver), after which the operator re-enables the contract. The code cannot detect a restore made outside the runbook; the specification says so instead of implying a guard. |
| C5 | The 36-hour saver rule is not in R24 and proves nothing | Accepted: the rule is dropped. The saver flag keeps the authority it had in 2026 (set by the fetch's earn rule on an accepted observation, by the command line, and by the dashboard), is treated as spent when it is uninitialized or after a contract revocation until the next explicit observation, and the known limit is ledgered: a saver earned and consumed between two accepted fetches is not visible to the code, and Eric marks it used. |
| C6 | The decision table is not total | Accepted. Research and preview are gated before the refusal rows; a timestamp slightly in the future is treated as age zero up to the tolerance and rejected beyond it; a mismatch between the status file and the accepted observation is a stale reason, not a diagnostic beside a fresh row; the saver has one precedence order including a same-date manual observation; when several stale reasons apply the order is stated. No live state falls through to the model replay. |
| C7 | Alert promises contradict the dispatcher and each other | Accepted. One DM when a refusal is first seen on a contest date, one reminder at the last planned check before the pick's fallback deadline if it is still refusing, and a new DM whenever the required action changes (the incident key includes the action). A stale-reading warning is sent once per contest date. Times are described as the scheduler's actual wake and check times, not fixed clock times. The specification states the window Eric has to act, and does not treat a sent DM as read. |
| C8 | The switch to automatic lacks evidence and a transaction | Accepted. Manual observations are appended to a history file so the status view can show them beside the recorded attempts; `enable` is an operator attestation after inspection, with its writes, their order and what a crash between them leaves defined; the specification states which endpoint behaviours the automatic contract supports and that manual operation continues, without a bound, when they do not hold. |

Also accepted from the check's last section: every recovery command named in the specification must exist on `main` or be specified in a change set (`reconcile --date` does not exist); commands report resulting state, not that they ran; the runbook states the operator's duties and the response window.

Cost if wrong, C4 and C5 (the two places this ruling removes machinery): a restore done outside the runbook, or a saver consumed between fetches and not marked, leaves the saver wrong until Eric corrects it; the policy then differs only at streaks 5 to 15, and the streak itself is unaffected.
