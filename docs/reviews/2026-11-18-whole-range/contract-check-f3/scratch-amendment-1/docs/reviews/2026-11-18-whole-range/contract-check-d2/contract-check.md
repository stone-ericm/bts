# NOT YET

**MUST FIX — C1/C6 need a safe point to switch the installed jobs.** The installer publishes target jobs and reloads target units while the old checkout can still run. A job can start between installation and the Actions test gate, or outlive crontab replacement. The next deploy can refuse before arming the hold. At 10:29 on the October checkout, install, let the deploy fail or queue, then let the 10:30 fetch run. Even the new gated line runs old code with a clear hold and can overwrite a 2027 observation with the old format. Putting October’s crontab back later cannot recover the observation. A scheduler sleep window constrains the scheduler, not cron or the Actions queue.

**Smallest design change.** Split passive staging from publication. On an already guarded box keep the current installation in effect through admission and verify it against the currently installed revision. Bind the reviewed staged payload to the approved target. In the owner, arm the durable hold, stop and verify the old services and drain writers, then apply the staged files under that same transaction lock. Allow this installer entry for the owner’s own `pending` record only. Keep that run’s hook compatible with both versions until it ends. Verify target bytes before activation and keep the hold on a partial switch. Provision the first guarded deployment separately, with a persistent first-boot fence on old jobs and services until they are verified or replaced.

## Seven questions

1. **MUST FIX — systemd 252 unit evidence.** I read the local round-3 review’s v252 `systemd.unit.xml` and `service.c` findings on user drop-in precedence and condition skips. I found no local copy of v252’s `systemctl` implementation or man page. The documented distinction to verify is that `cat` displays backing files from disk and `show` uses the manager’s loaded properties. The expected framing is `# <fragment>\n` + literal fragment, then `\n# <drop-in>\n` + literal drop-in for the scheduler. Exact output, empty `DropInPaths` behavior, property order, and detection of changes to previously unknown drop-ins remain unverified. Older systemd output often places `MainPID` before `ActiveState`; argument order is no proof. An extra byte source for stale loaded definitions is the manager’s stable effective settings (working directory, environment directives, success statuses and static execution configuration). Execution properties that include last-run PID/status/timestamps need a stable projection, or use a controlled reload plus verification under the installation fence. None of these captures inherited environment, active process identity or executable contents. [Local v252 review](../../docs/reviews/2026-11-18-whole-range/contract-check-deploy/contract-check-r3.md)
2. **MUST FIX — environment.** `environment.d`, user-manager `DefaultEnvironment=` and `set-environment` can supply inherited variables absent from the fragment. A manager administrator can set `UV_PROJECT_ENVIRONMENT` to another existing venv, or a routine credential rotation can leave stale delivery settings. The units also read the mutable checkout `.env`. Python `-I` ignores Python-specific environment controls but does not clear the environment before the dynamic loader runs. C2’s fixed root closes the old test-root selection, not inherited execution settings. See A7 and the C1/C2 text below. The corresponding unavailable local v252 references are `environment.d(5)`, `systemd-user.conf(5)`, `systemd.exec(5)` and `systemctl(1)`.
3. **MUST FIX — render against the target.** At `0645be4b`, cron setup lines 61–78 run `uv run bts entry-intent` in the checkout. That can sync the live venv even during a failed hold. `619abda7` has `entry-intent` (CLI line 1612), but its startup rules precede the target’s. Adding `--no-sync` alone still runs the old policy. Use the staged target’s verified runtime and `--no-sync` as specified below.
4. **MUST FIX — T holder claim is false.** The deploy owner (installer source 930–952) reconciles abandoned pending/activating and finishes failed records before preflight. Hand release (1072–1097) refuses pending/activating but can release a failed record with unfinished containment. Reconcile (577–591) takes T itself, and leaves another run’s hold alone. The starting installer creates T but never takes it. C1a’s new taker refuses pending/activating and accepts failed without finishing containment. The monitor and condition inspect T and use no T lock, cron admits via W, and dashboard saver takes W. A Linux read-only open of the 0644 T file can also take an exclusive flock. A dying owner with a durable failed hold and no stop/page evidence can be followed by a long reinstall while its hook times out. The existing scheduler can remain running, since ExecCondition only guards starts. Even a successful hand release can erase the only route to finish the old incident.
5. **NOTE — Debian cron round trip is conditional.** The local Vixie `crontab(1)` documents stdin installation and stdout listing. It is the Mac man page. Bookworm’s Debian-specific `crontab(1)` behavior to confirm is that listing omits the three generated spool header lines by default and includes them with `CRONTAB_NOHEADER=N`. Canonical valid LF input should round-trip with that variable unset. A missing final LF is an invalid cron input, not evidence of a successful round trip. A7 must run the actual package with both environments, including absent table/nonzero exit versus a valid empty table. Keep stdout, exit and stderr separate.
6. **NOTE — keep the dashboard liveness check.** K5 and R53 distinguish a candidate process from the installed configuration. `dashboard()` at 841–882 verifies the active unit owns the :3003 listener by `ss`, cgroup and cwd, then requires HTTP 2xx (tailnet, loopback fallback). An unrelated listener returning 200 passes without the identity check. Keep it at the candidate stage, with separate wrong-PID and wrong-cwd tests.
7. **MUST FIX — midnight admission and real sleep windows.** `window()` at 609–628 requires at least 30 minutes of known sleep for ordinary admission. `scheduler._idle_until_next_wakeup()` publishes a sleep through the next morning even on a no-games day. At 23:29:59 with wake at 07:00, a slow healthy run reaching activation at 23:45:05 refuses after reset/sync, although it is inside the owner’s 20 minutes and still in the same ET date. Starting at 23:44:50 and observing for 30 seconds moves that refusal to unlink. The dashboard and scheduler each observe 30 seconds and the test gate/queue precedes the owner runtime. `RuntimeMaxSec` triggers termination, and stop and hook work may continue. It is not an end-to-end wall-clock deadline.
