# NOT YET

**MUST FIX.** RD1's `disable` removes an enablement path. It neither contains a running scheduler after controller loss nor makes `enable` followed by the stamp an atomic release. RD2 assumes that a failed reset leaves the candidate installed. The restored code can overwrite a valid 2027 observation before the next deploy. The smallest design change is one durable host-owned deploy state, armed before reset, that inhibits scheduler starts and only the affected pick/contest writers (`check-results`, `reconcile`, `fetch-contest-streak`, `preview`). Drain existing instances before mutation. Leave monitoring and analytics-only timers running. Give a provisional scheduler start a bounded on-box owner that stops it on controller loss, and release the hold and publish the successful UTC timestamp through one durable commit after the canary. Install and verify the guard on the restored box before deployment or activation. Healthy canary behavior and no automatic rollback still apply.

Reviewed the supplied draft at base `fef05b5b`. The draft source commit `979e0b47` is absent locally. Round 1 replayed the exact base YAML under Bash 3.2. Round 2 ran 34 draft-ordering Bash shim cases and ran actual archived/current contest writers against synthetic MLB data. Systemd documentation is cited for semantics. The probes made no real systemd, SSH, notification, CI or pytest calls. [Base log](contract-probe.log), [round-two replay](round2_replay.py), [model](round2_probe.py), [results](round2-probe.log)

**RD1 boundary replay.** Before disable, reboot starts the previously enabled revision. After disable, reset, sync, legacy cleanup, restart, HEAD check, wait and canary, the normal local link is absent and fresh boot stays down. Shell loss differs from a reboot: the old process survived the model's reset/sync, and the candidate survived restart/HEAD/wait/canary. HUP and TERM at reset, sync, restart or wait ran the modeled handler when its commands returned. A trap cannot bound a blocked command. After `enable` and before stamp, the candidate booted with the old stamp and no `CANARY PASSED`. After stamp and before output, it booted with the new stamp and no terminal log. An `enable` failure after writing links followed by working E4 can contain it, but loss there leaves the same open boot path. A hard `Wants=`, global link and legacy scope booted despite local cleanup. Shims model these documented effects and do not establish the live box's unit inventory.

**RD2 concrete counterexample.** At 10:29 ET, stage a restored checkout of `619abda7`, usable old dependencies and a 2027 ops restore with a current switched v2 observation. Reset can fail before replacing the old checkout. At 10:30 the same installed `fetch-contest-streak` line then executes old code, which overwrites `contest_streak.json` with v1. In the passing control, the target is `fef05b5b`, the same 10:30 fetch writes accepted v2. Two distinct accepted v2 inputs yielded identical old-writer output. A later correct checkout, sync and restart still refused it before another fetch. With no earlier backup and a prior fetch interrupted between its observation write and ledger append, the original accepted best and timestamp cannot be inferred from the remaining artifacts. A new fetch creates a new observation and cannot return a passed submission window. The 01:00 old scorer can independently drop `season`/`applied_dates` and double-apply a pending hit.
