## Why it stopped (round-2 findings; obligations for any next attempt)
1. **A signal before `begun` is published can contain a box this invocation never changed (both reviewers).** While publication is still uncertain, the handler treats only an ABSENT record as "not published". On any box that has deployed since boot, `/run/bts-deploy/attempt` holds the previous run's valid record, so a signal in the window between staging and renaming `begun` disables and stops the healthy scheduler, writes a false `deploy_failed` heartbeat, overwrites the prior record and pages. Never a pick; picks can be missed until a redeploy. **Obligation:** during `publication=beginning`, a valid record of a different attempt (or absence) is "not published" (`DEPLOY NOT STARTED`); only unreadable evidence or this attempt's own `begun` contains; a test with a prior `committed` and a prior `contained` record on disk.
2. **A legacy unit that becomes `not-found` skips its recorded cgroup (Codex).** Recovery records a loaded, fragmentless legacy unit's cgroup; after its stop the manager reports the name `not-found`, and the proof takes the absence branch without checking the recorded, still-populated cgroup, printing `Scheduler stopped: verified.` **Obligation:** a recorded cgroup path stays in the proof even after the unit is later reported absent.
3. **The fallback proof cutoff can skip the residual-process check with time left (Codex).** With the clock unavailable, a slow legacy jobs query consumed the proof window so that the required `pgrep` was never launched, while the handler finished at 216 s of its 280 s cap. **Obligation:** reserve a launch window for the residual-process check, independent of earlier proof queries, keeping the marker and POST budgets.
