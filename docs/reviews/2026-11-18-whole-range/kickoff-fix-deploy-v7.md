## Ledger: accepted limits (R54 and check 1; go into `CLAUDE.md` "Deployment")
- **L1** On a box whose restore checklist B8c was skipped, a failed reset can leave the October code (`619abda7`) checked out with its October crontab running (the 10:30 fetch rewrites a 2027 reading the live path then refuses: a missed pick, not a wrong one; October scoring can drop `season`/`applied_dates`).
- **L2** A lost SSH session, a forced cancellation, an action timeout or a lost runner can leave a candidate scheduler running with no completed handler; the recovery step may not start, may not reach the box, or may time out on the mutex. The soft hold cannot undo a pick already sent.
- **L3** A failed reset can leave a partial tree; cron jobs then run it; a running cron job can keep old code while files are replaced.
- **L4** The persistent page runs the checker from the checkout and needs `.env`; a reset or a broken `.env` can disable it and the immediate POST. Then GitHub's notice and the missed-ping checks remain.
- **L5** The candidate scheduler runs during the 30-second canary and can send a pick before a failure is found (as on the base).
- **L6** A retry deploy's scheduler start rewrites the heartbeat, so the heartbeat check can go up then down during a retry; a heartbeat read started just before containment can send one success ping after the `/fail`; a surviving process can rewrite the marker.
- **L7** The frozen incident-register parser reads the new lines as `canary=absent`, `rollback=none` (RD6).
- **L8** RD1's limits: a global user link, another target's `Wants=`/`Requires=`, an independent legacy system unit or a manual start can activate the scheduler; preflight refuses only what `LoadState`/`UnitFileState` and the legacy query show.
- **L9** Power loss before `disable` takes effect, or after `enable` has installed the link and before the commit record, can start the scheduler at the next boot; a boot also clears `/run`, so the attempt record is gone (recovery then reports "no phase-2 record on this boot").
- **L10** A deploy can commit on the box after the Actions run failed or was cancelled (the log tail was lost); recovery then reports `committed`.
- **L11** The canary's parity holds for the supported runtime: the service's environment can still change the interpreter or semantics (`UV_PROJECT_ENVIRONMENT`, `PYTHONPATH`, `PYTHONHOME`, `PYTHONTZPATH`); a divergent manager environment can give a false green canary. A7 records that the installed scheduler runs the supported candidate runtime.
- **L12** A 2xx from the POST confirms the HTTP response only, not that Eric was notified (A7 checks receipt).

## What a failed deploy does today (base; the first earlier check's corrected description, adopted)
`set -e`; `cd /home/bts/projects/bts`; `OLD_SHA=$(sudo -Hu bts git rev-parse HEAD)`; `git config --global --add safe.directory` (writes user git config); `git fetch origin` (changes refs, objects, `FETCH_HEAD`); `git reset --hard "$TARGET_SHA"` (a failure can leave a partial tree); locked `uv sync`; the legacy self-heal (`disable --now` and `pkill` errors ignored; `rm` and `daemon-reload` errors end the script); `systemctl --user restart bts-scheduler bts-dashboard`; `NEW_SHA`; `sleep 30`. Under `set -e` a non-zero exit of any of these ends the script with nothing stopped, rolled back or paged except GitHub's failed-run notice (W13). Then `set +e`; the canary accepts the scheduler active or the exact clean-exit tuple (activating / auto-restart / success / 0), the dashboard active, and HTTP 2xx on the tailnet address (loopback if `tailscale ip -4` gives nothing), ignoring failures of `id`, the `show` queries and curl's own exit; on a failed canary it resets to `OLD_SHA`, syncs, restarts, sleeps 15 and stamps if both units read active, printing `Rolled back cleanly` even when the rollback reset failed (W12: on a box restored from snapshot `446156433` that target is `619abda7`). The pass branch prints `CANARY PASSED` BEFORE stamping. The canary passes a box that starts, pages and idles with no usable contest state (W17).

## Rulings (lead's design authority as delegated to this session; Eric can overrule)
- **RD1, the soft hold is the scheduler's local boot link, and is called a soft hold everywhere.** Phase 2's first mutation is `systemctl --user disable bts-scheduler` (no `--now`), verified by `is-enabled` reading exactly `disabled`; the commit's `enable` (no `--now`) restores it. It suppresses starts at boot through that link only (L8, L9). No status line claims it as containment.
- **RD2, cron lines and timers keep running.** `INCIDENT.md` §6 carries the earlier Q1 inventory (job names and times, without its hold column): scoring and reconcile, the contest fetch, preview and asset sync can write against the reached tree; backups, research jobs, collectors and timers continue; the entry, day-outcome and fetch DMs depend on the installed cron and intent (the October fetch can DM in research); none sends a pick.
- **RD3, the dashboard is left running** and is inspection only during recovery (no saver control, no entry from its preview).
- **RD4, the heartbeat monitor runs on the system Python** (`/usr/bin/python3 scripts/check_heartbeat.py`, same arguments, sourcing prefix and logging), effective only after `cron-setup-hetzner.sh install`.
- **RD5, no deploy-failure Bluesky DM.**
- **RD6, the frozen parser and the dashboard's `/health` are unchanged.**
- **RD7, the mutex and the attempt record.** Directory `/run/bts-deploy/` (root, mode 0700). Lock file `/run/bts-deploy/lock`, a root-owned regular file never truncated, unlinked or replaced. Attempt record `/run/bts-deploy/attempt` and cancellation marks `/run/bts-deploy/cancelled.<run_id>.<run_attempt>`. Only the two workflow scripts read or write them; `/run` is cleared at boot (L9).
- **RD8, one containment function, byte-identical in both scripts** (a test compares them).
- **RD9, `bts deploy-canary`** answers with the scheduler's own predicates and loader (F9), never a parallel validator.
- **RD10, a live box with no usable contest state fails the deploy and is contained** (W17's purpose; a deploy on a refused day stops a scheduler that would otherwise have idled and paged). Recovery: correct today's state (B8a), confirm `live decision now: accepted`, re-run the deploy for the same tested SHA; never a bare start.
