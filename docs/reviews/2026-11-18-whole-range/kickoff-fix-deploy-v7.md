## What a failed deploy does today (base, step by step; the first check's corrected description, adopted)
`set -e`; `cd /home/bts/projects/bts`; `OLD_SHA=$(sudo -Hu bts git rev-parse HEAD)` (a failure here ends the script before the SHA is known); `git config --global --add safe.directory` (writes user git config); `git fetch origin` (can change refs, objects, `FETCH_HEAD`); `git reset --hard "$TARGET_SHA"` (a failure can leave a partial tree); locked `uv sync`; the legacy self-heal (its `disable --now` and `pkill` errors ignored; `rm` and `daemon-reload` errors end the script); `systemctl --user restart bts-scheduler bts-dashboard`; `NEW_SHA`; `sleep 30`. Under `set -e`, a non-zero exit of the reset, the sync, the self-heal's `rm`/`daemon-reload`, the restart, `NEW_SHA` or the sleep ends the script with nothing stopped, rolled back or paged except GitHub's failed-run notice (W13). Then `set +e`; the canary accepts the scheduler active or the exact clean-exit tuple (activating / auto-restart / success / 0), the dashboard active, and an HTTP 2xx on the tailnet address (loopback if `tailscale ip -4` gives nothing); it ignores failures of `id`, of the `show` queries and of curl's own exit in the probed cases. On a failed canary it resets to `OLD_SHA`, syncs, restarts, sleeps 15 and stamps `data/.last_deploy_iso` if both units read active, printing `Rolled back cleanly` even when the rollback reset failed (W12: on a box restored from snapshot `446156433` the rollback target is `619abda7`, which cannot serve 2027 and damages state the new code then refuses). The pass branch prints `CANARY PASSED` BEFORE stamping and exits with the stamp's status. The canary passes a box that starts, pages and idles with no usable contest state (W17). A GitHub failed run does not prove Eric was notified.

## Rulings carried from Draft 2, with the checks' edits (lead's design authority as delegated to this session; Eric can overrule)
- **RD1, the soft hold is the scheduler's boot enablement, and it is called a soft hold everywhere.** Phase 2 begins with `systemctl --user disable bts-scheduler` (no `--now`: the running process is untouched) and the success commit ends with `systemctl --user enable bts-scheduler` (no `--now`). What it does: a reboot, power loss or `Restart=` cycle of the MANAGER while the deploy is incomplete or failed does not start the scheduler at boot through the unit's own `default.target` link. **What it does not do (check 2, adopted as limits, not as requirements):** it does not stop a running scheduler or cancel its `Restart=always`; an explicit `start`/`restart` still starts a disabled unit (which is how the canary and a later deploy start it); a global user enable link, a `Wants=`/`Requires=` from another unit or an independent legacy system unit is not removed by it; `is-enabled` reading `disabled` does not prove there is no other activation path. Preflight therefore refuses a unit whose state it cannot account for (F1 item 7), and no status line claims the soft hold as containment.
- **RD2, cron lines and timers keep running** (check 1's Q1 table is adopted as the list and goes into `INCIDENT.md`): none sends a pick; the DMs they can send (`check-pick-entered`, `day-outcome`, the fetch failure DM) report real state. The state writers run whatever is checked out; after a failed deploy that is the candidate that passed the test gate (or, after a failed reset, possibly a partial tree or the old checkout: ledger L1 and L3).
- **RD3, the dashboard is left running** (F5 does not stop it). Recovery text treats it as inspection only: no saver button, no entry from its preview.
- **RD4, the heartbeat monitor runs on the system Python.** `scripts/check_heartbeat.py` is standard library only and must run under Python 3.11 (the box's `/usr/bin/python3`); the cron line in `scripts/cron-setup-hetzner.sh` becomes `/usr/bin/python3 scripts/check_heartbeat.py …` (same arguments). It takes effect on the box only after `bash scripts/cron-setup-hetzner.sh install` (checklist rows). Check 2's demand for a monitor outside the checkout is NOT adopted (it is an installation; ledger L4).
- **RD5, no deploy-failure Bluesky DM.** The pages are the paging table below.
- **RD6, the frozen incident-register parser and the dashboard's `/health` are unchanged.** The parser classes the new lines as `canary=absent`, `rollback=none`; ledger.

## New rulings for D3
- **RD7, the recovery step (F6).** A failed or cancelled deploy step is followed by a second SSH step that reaches the box again and contains it if phase 2 began and did not commit. The two box scripts serialise on one lock in `/run` (tmpfs, gone at reboot, read by nothing else). This is a mutex, not a hold: no service, timer or cron line reads it.
- **RD8, one failure handler, two copies.** The containment function is the same text in both box scripts; a test asserts the two function bodies are byte-identical.
- **RD9, the contest-state question is a new read-only command, `bts deploy-canary`,** that answers with the scheduler's own predicates and loader (no parallel validator): it refuses exactly when `bts schedule` would refuse to start (`entry_intent.live_gate_problem`) or, in a live configuration as the scheduler's morning state check defines it, when `load_decision_streak_state(picks_dir, require_contest_state=True, now=now)` raises `ContestStateError`. Research intent with private delivery passes without reading contest state.
- **RD10, a live box with no usable contest state fails the deploy and is contained.** This is W17's purpose and has a cost: a deploy on a day whose contest state is refused stops the scheduler, which would otherwise have idled and paged. Recovery: correct the state for the current ET day (checklist B8a), confirm `bts season-contract status` says the live decision is accepted, then re-run the deploy for the same ref (F7, §5 texts). Never a bare `systemctl start`.

## Standing hostile-input rows
- **An interrupt mid-step:** HUP, INT, TERM, PIPE as above (a trap waits behind a foreground command until it returns, so every phase-2 command is bounded: the author states each bound, including `uv sync` and `systemctl restart`); SIGKILL or a lost host: RD1's soft hold, the recovery step, GitHub's notice (L2).
- **A malformed or non-regular file:** `data/.heartbeat`, `.env`, the staged stamp's directory, the lock path (a directory or a FIFO at `/run/lock/bts-deploy.lock`: preflight fails), the configuration for `deploy-canary`.
- **Midnight ET and the year boundary:** the workflow's stamps and the heartbeat marker are UTC with no date logic; `deploy-canary` samples ET once (a deploy across midnight judges the new ET day; a live configuration in January with no switch for the new year refuses, by design: the offseason box runs research).
- **A failed or unconfirmed send:** the POST is checked (exit 0 and 2xx); a failed POST leaves the heartbeat page and healthchecks.io (paging table); the canary period can already have sent a pick before a failure (accepted, as on the base: the candidate scheduler runs during the 30 seconds).
- **A restart mid-step:** a reboot during phase 2 leaves the scheduler disabled for boot (RD1) with whatever tree is checked out; `/run` is cleared so the lock is gone; the next deploy runs normally.
