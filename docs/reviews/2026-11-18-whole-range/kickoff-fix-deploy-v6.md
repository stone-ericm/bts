## The design in one paragraph
A root-owned guard, installed by an explicit root step, provides a durable hold record outside the checkout (`/var/lib/bts-deploy/hold`) and one tool (`/usr/local/bin/bts-deploy-hold`, standard-library Python run by `/usr/bin/python3 -I`). While a hold exists, the scheduler unit's `ExecCondition` skips every start, the four state-writing cron commands skip, the dashboard's saver POST returns 409, and the heartbeat monitor pages. A deploy hands off to a transient on-box owner unit that arms the hold before changing anything, stops and drains, resets, syncs, runs a read-only canary (for a box set to enter picks: does the live contest-state read accept the state now?), starts the scheduler only after recording `activating`, verifies it, and releases the hold only when every step passed. Any failure leaves the box held, the scheduler stopped, and Eric paged; there is no automatic rollback. **What is new in D2:** the guard installer becomes the only writer of the `bts` crontab and of the scheduler and dashboard units, records the hashes of exactly what it wrote, and every proof of box state in preflight is a byte comparison with that record; the tool has no override path; the canary asks only the contest-state question; the race edges STOP-D named are closed.

## C: changes in D2
### C1. Byte comparison with what the installer wrote (replaces every parsed proof)
- **C1a, the installer is the only writer.** `scripts/install-deploy-guard-hetzner.sh --target <40-hex sha>` (root; `DESTDIR` for tests only, as now) installs, from ONE commit: itself, `scripts/cron-setup-hetzner.sh`, `scripts/systemd/bts-scheduler.service`, `scripts/systemd/bts-dashboard.service`. It reads the four blobs with `git -C /home/bts/projects/bts show <sha>:<path>` run as `bts` (object reads only: no checkout, ref or config change; an absent object is fetched as the starting point's `target_installer` does, into a temporary bare store) and FAILS unless its own bytes equal the target's installer blob. It takes `transaction.lock` EX non-blocking (busy → `FAILED: a deploy or release is in progress`) and FAILS while the hold is `pending` or `activating` (a `failed` or absent hold is fine: re-installing is part of fixing forward). Then, in this order: (1) the three lock files, the tool and the drop-in as now; (2) the two unit fragments written as `bts` to `/home/bts/.config/systemd/user/<unit>` (mode 0644, by temp file and rename); (3) `daemon-reload` of `bts`'s user manager; (4) the crontab (C1b); (5) the record (C1c), written last. Any failure prints `FAILED: <reason>`, exits 1, and leaves no record (the previous record is removed at the START, as `guard-install.sha256` is now, so a partial install can never satisfy preflight). The installer never creates, edits or removes the hold, never starts, stops or enables a unit.
- **C1b, the crontab.** `cron-setup-hetzner.sh` gains `render`: it prints to stdout exactly the BTS lines `install` would write (the `# BTS-HETZNER` lines for the configured intent, in install's order, each LF-terminated) and nothing else, with install's refusals and exits. The rendered gate path is always the literal `/usr/local/bin/bts-deploy-hold` and the monitor's hold path the literal `/var/lib/bts-deploy/hold`: no environment variable changes them (the `BTS_DEPLOY_HOLD_BIN` override stays only for `install`'s guard probe, as the starting point's test fixture uses it). The installer runs the staged copy as `bts` with a fixed environment: `env -i HOME=/home/bts USER=bts LOGNAME=bts PATH=/home/bts/.local/bin:/usr/local/bin:/usr/bin:/bin /bin/bash -c 'cd /home/bts/projects/bts && set -a && . ./.env && set +a && exec /bin/bash <staged cron-setup> render'` (bounded), FAILS on a non-zero exit or empty output, writes those exact bytes with `crontab -u bts -` (the WHOLE crontab: no line that is not rendered survives), reads back `crontab -u bts -l` and FAILS unless the bytes are identical. The previous crontab is saved first to `/var/lib/bts-deploy/crontab.before-<UTC stamp>` (root:root 0600; it holds the ping URLs) and the installer prints `crontab: replaced (<n> earlier lines saved to <path>)` with no line content. `install`, `show` and `remove` keep their behaviour and existing assertions; the docs stop telling anyone to run `install` or `remove` on the box (C6).
- **C1c, the record.** `/var/lib/bts-deploy/installed.json`, root:root 0644, written last by temp file, rename and directory fsync, schema `bts_deploy_guard_install_v2`: `target` (the sha), `blobs` (sha256 of each of the four blobs, keyed by repo path), `crontab_sha256` (of the read-back bytes), and per unit `cat_sha256` (sha256 of the stdout of `systemctl --user cat <unit>` after the reload) and `show_sha256` (sha256 of the stdout of `systemctl --user show <unit> -p LoadState -p FragmentPath -p DropInPaths -p NeedDaemonReload`). Before recording, the installer FAILS unless (i) the `cat` stdout equals, byte for byte, the bytes the installer composes from what it wrote: for the scheduler `# /home/bts/.config/systemd/user/bts-scheduler.service\n` + fragment + `\n# /etc/systemd/user/bts-scheduler.service.d/50-deploy-hold.conf\n` + drop-in; for the dashboard the first part only (the contract check must confirm `systemctl cat`'s exact framing on systemd 252, and A7 rehearses it); (ii) the `show` stdout is exactly `LoadState=loaded\nFragmentPath=<the fragment path>\nDropInPaths=<the drop-in path or empty>\nNeedDaemonReload=no\n` in the order systemd prints (the check confirms the order). So a foreign drop-in, a runtime override or an unloaded edit present at install time fails the install instead of being recorded. `guard-install.sha256` is replaced by this record.
- **C1d, preflight.** Preflight (and the hand release, and the owner again immediately before writing `activating`) refuses at `guard-stale` unless `installed.json` is a readable root-owned regular file of the schema whose four `blobs` equal the sha256 of the DEPLOY TARGET's four blobs; refuses at `crontab` unless the sha256 of `crontab -u bts -l` stdout (exit 0) equals `crontab_sha256`; refuses at `guard` unless, for each unit, the sha256 of `systemctl --user cat <unit>` stdout equals `cat_sha256` and the sha256 of the `show` stdout equals `show_sha256`. Nothing in preflight splits, tokenises, parses or pattern-matches a crontab line, a unit file or a property value. `verify_crontab`, `runs_heartbeat`, `CRON_GATE`, `WRITER_INVOKES`, `verify_unit_fields`, `execution_matches` and the `verify-unit` command are removed. The checks that stay as they are: `user-manager` (`LoadState` value `loaded`), `legacy-unit`, the hold and window checks, `guard-stale` for the installer itself (now inside the record). Refusal texts keep the existing `DEPLOY NOT STARTED — <step> failed …` form.
- **C1e, legitimate later changes.** Any change to the crontab (an intent change, a new cron line), to the two unit templates or to the guard is made by running the installer as root from the target commit (C6 gives the staging steps). `install-systemd-hetzner.sh` installs every template EXCEPT `bts-scheduler.service` and `bts-dashboard.service` and prints `<unit>: installed by install-deploy-guard-hetzner.sh` for those two (if `tests/test_*` on `main` pins its old loop, STOP and ask). A hand edit (`crontab -e`, `systemctl --user edit`, `set-property`, a copied unit) makes the next deploy or hand release refuse until the installer is re-run; that is the intended failure.

### C3. The canary asks only the contest-state question (STOP-D obligation 4 is NOT built)
`validate_runtime_config` is removed from `scheduler.py` and from the canary; the canary imports `bts.scheduler`, `bts.model.predict` and, for a live box, the delivery module, and nothing else; "configuration refused" comes only from `load_config` or `check_entry_intent` failing as on the starting point. `run_day` and every existing caller are unchanged. **Known and not fixed (ledger in `CLAUDE.md` and B8a):** a configuration the scheduler cannot run keeps today's behaviour (the unit restarts; the heartbeat check flags it), reproduced by `[scheduler] fallback_deadline_min = 20` with the default morning value 25, which starts, writes READY, and raises at `resolve_fallback_deadline_min` on the first cycle with an unlocked candidate pick; likewise `heartbeat_path` under a regular file and overflowing or negative minute settings. ### C4. The race edges (STOP-D obligation 5)
- **C4a, the hook.** `reconcile` waits up to 60 s for `transaction.lock` EX. If it cannot take it, it changes nothing (no stop, no page, no record write) and exits 1. Reason: the lock is free once the owner's main process has exited, so contention means another holder; every holder (a deploy owner, the installer, the hand release) either reconciles an abandoned record first (K5) or refuses on a `pending`/`activating` record (C1a, K11), so the next preflight contains and pages. The fallback stop is removed, which removes the stop-after-release interleaving of Codex r2 finding 2.
- **C4b, the hand release** also refuses (`hand release refused: scheduler not stopped`) unless `systemctl --user show bts-scheduler.service -p ActiveState -p MainPID` prints exactly `ActiveState=inactive\nMainPID=0\n` or `ActiveState=failed\nMainPID=0\n` (in systemd's order), read after the window check and before the audit line.
- **C4c, midnight.** No clock chase: (i) preflight refuses at `window` when the ET wall clock is in [23:30, 00:30); (ii) the owner refuses `activating` and the unlink (activation failure, hold kept, contained, paged) when, at that moment, the ET date differs from the date preflight sampled or the ET clock is in [23:45, 00:30). With `RuntimeMaxSec=1200`, a deploy that passes (i) ends before 23:52 ET. Year boundary: the same rule (December 31). Known and not fixed: a whole-VM pause longer than the remaining runtime between the last sample and the unlink.
