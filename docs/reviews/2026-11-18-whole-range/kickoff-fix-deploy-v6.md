## The design in one paragraph
A root-owned guard, installed by an explicit root step, provides a durable hold record outside the checkout (`/var/lib/bts-deploy/hold`) and one tool (`/usr/local/bin/bts-deploy-hold`, standard-library Python run by `/usr/bin/python3 -I`). While a hold exists, the scheduler unit's `ExecCondition` skips every start, the four state-writing cron commands skip, the dashboard's saver POST returns 409, and the heartbeat monitor pages. A deploy hands off to a transient on-box owner unit that arms the hold before changing anything, stops and drains, resets, syncs, runs a read-only canary (for a box set to enter picks: does the live contest-state read accept the state now?), starts the scheduler only after recording `activating`, verifies it, and releases the hold only when every step passed. Any failure leaves the box held, the scheduler stopped, and Eric paged; there is no automatic rollback. **What is new in D2:** the deploy owner becomes the only writer of the `bts` crontab and of the scheduler and dashboard unit fragments, switching them under the hold after the reset and sync; it records the hashes of exactly what it wrote, and every proof of box state in preflight and the hand release is a byte comparison with that record; the tool has no override path; the canary asks only the contest-state question; the race edges STOP-D named are closed.

## C: changes in D2
### C1. The owner writes the crontab and the units under the hold; preflight compares bytes (replaces every parsed proof)
- **C1a, the root installer (tool, drop-in, locks; provisioning).** `scripts/install-deploy-guard-hetzner.sh --target <40-hex>` (root; `DESTDIR` for tests only) keeps the starting point's job for the tool, the three lock files and the drop-in, and the installer fingerprint (`guard-install.sha256`, compared by preflight's `guard-stale`); it requires its own bytes to equal `git show <target>:scripts/install-deploy-guard-hetzner.sh` (read as `bts`) before any change and again before publishing the fingerprint, replaces the tool by rename (a compatible tool is in place at every moment), refuses while a hold is `pending` or `activating`, and writes NO crontab and NO unit fragment. **Provisioning** (only when `jobs.json`, C1c, does not exist): it requires the restore procedure's offline fence (adopted B8c text) to be in place, which it checks as: `bts-scheduler.service` and `bts-dashboard.service` inactive with `MainPID=0` and Debian's no-table status from `crontab -u bts -l`; otherwise FAILS. Then, in this order, each durable: (1) the provisioning hold (C1f); (2) `jobs.json` in state `provisioned` with `crontab` = the no-table state and, per unit, the hashes of the current `cat` and `show` bytes (the October fragments plus the new drop-in, after the installer's own `daemon-reload`). A failed or interrupted provisioning leaves either no `jobs.json` (re-run it) or a complete one.
- **C1b, the switch, in the owner (new phase `install-jobs`, inserted in K5 after the locked sync and before the dashboard restart).** With the hold `pending` and T held by the owner (never reacquired), the owner: (1) verifies the live crontab and units equal `jobs.json`'s current state (C1d); (2) reads the intent with the target's own synced runtime and renders the crontab and both fragments from the checkout (adopted C1b texts); (3) writes `jobs.json` in state `switching` with, per artifact, the BEFORE hashes (its current state) and the AFTER hashes (the bytes it will install; for units the composed `cat`/`show` bytes), plus `run` (the deploy id), `target`, `intent`; (4) saves the old crontab root-only and replaces the whole crontab, reads it back and requires the after bytes; writes both fragments as `bts`, `daemon-reload`, and requires each unit's `cat`/`show` to equal its after bytes; (5) writes `jobs.json` in state `installed` (target, intent, the after hashes). Any failure is an ordinary owner failure at step `install-jobs` (K6); `jobs.json` stays `switching`.
- **C1c, the record.** `/var/lib/bts-deploy/jobs.json`, root:root 0644, single link, bounded, exact schema `bts_deploy_jobs_v1`, written only by temp file, rename and directory fsync; states `provisioned` (as C1a), `switching` (as C1b(3)), `installed` (as C1b(5)). It replaces `installed.json`. Hashes are sha256 of the exact bounded stdout of the commands in the adopted "C1c/d" text.
- **C1d, the one verifier** (preflight, the owner's last check before `activating`, the hand release): in the adopted "C1c/d" order; the job step reads `jobs.json` (absent, unreadable or invalid → `guard`) and compares each live artifact: state `installed` or `provisioned` → each artifact must equal the recorded hashes (`crontab`, `guard`); state `switching` → each artifact must equal its BEFORE or its AFTER hashes (a partial switch is accounted for), and the hold must be a readable `failed` record (a deploy then fixes forward and its own `install-jobs` takes the current per-artifact state as BEFORE). Before `activating` the owner requires state `installed` with its own `run` and `target`. The hand release requires state `installed` whose `target` equals HEAD and the hold's `target`, and the current intent (read with `uv run --no-sync bts entry-intent` as `bts`) equal to the recorded intent. Nothing splits, tokenises, parses or pattern-matches a crontab line, a unit file or a property value. `verify_crontab`, `runs_heartbeat`, `CRON_GATE`, `WRITER_INVOKES`, `verify_unit_fields`, `execution_matches` and `verify-unit` are removed.
- **C1e, legitimate changes.** The crontab and the two units change only through a deploy; an intent change is a configuration edit followed by a deploy of the deployed commit (`workflow_dispatch` on `deploy`) in a verified window. `cron-setup-hetzner.sh install`/`show`/`remove` keep their behaviour and assertions for local use and fixtures (`show` reads the intent with `--no-sync`); `install-systemd-hetzner.sh` keeps `--diff` for the two units and no longer installs them. **Known and not fixed (ledger):** a configuration edit without a deploy leaves cron rendered for the old intent until the next deploy, and a scheduler restarted meanwhile uses the new configuration; `.env`, the manager environment, `/etc/cron.d`, the host time zone and unit enablement are outside the record (ruling D2-S1; A7 verifies them once).
- **C1f, the hold shapes.** The step vocabulary gains `install-jobs` and `provisioned`. A provisioning hold is exactly: `state` `failed`, `step` `provisioned`, `deploy_id` `provision-<UTC epoch>`, `owner_unit` `null`, `target` the installer's `--target`, `previous` `unknown`; every reader (gate, status, monitor, hook, owner, hand release) accepts this shape and no other owner-less one. It is held for the scheduler, the cron gate and the saver POST; the monitor pages for it (expected while provisioning); the owner and the hook do no containment and no page for it (it is intentional); the hand release refuses it (`hand release refused: provisioning fence; use a deploy`). The first deploy's target need not equal the provisioning `target` (recorded for the audit only). Only `check-clear --scheduler` may admit a live `activating` record: the cron gate `run` and the saver POST refuse every hold entry, including `activating` (adopted).

### C4. The race edges (STOP-D obligation 5)
- **C4a, the hook.** `reconcile` waits up to 60 s for `transaction.lock` EX. If it cannot take it, it changes nothing (no stop, no page, no record write) and exits 1. Reason: the lock is free once the owner's main process has exited, so contention means another holder; every holder (a deploy owner, the installer, the hand release) either reconciles an abandoned record first (K5) or refuses on a `pending`/`activating` record (C1a, K11), so the next preflight contains and pages. The fallback stop is removed, which removes the stop-after-release interleaving of Codex r2 finding 2.
- **C4b, the hand release** also refuses (`hand release refused: scheduler not stopped`) unless `systemctl --user show bts-scheduler.service -p ActiveState -p MainPID` prints exactly `ActiveState=inactive\nMainPID=0\n` or `ActiveState=failed\nMainPID=0\n` (in systemd's order), read after the window check and before the audit line.
- **C4c, midnight.** No clock chase: (i) preflight refuses at `window` when the ET wall clock is in [23:30, 00:30); (ii) the owner refuses `activating` and the unlink (activation failure, hold kept, contained, paged) when, at that moment, the ET date differs from the date preflight sampled or the ET clock is in [23:45, 00:30). With `RuntimeMaxSec=1200`, a deploy that passes (i) ends before 23:52 ET. Year boundary: the same rule (December 31). Known and not fixed: a whole-VM pause longer than the remaining runtime between the last sample and the unlink.
