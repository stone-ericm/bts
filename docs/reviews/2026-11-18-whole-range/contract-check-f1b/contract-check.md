# Verdict

**BUILD WITH THESE EDITS**

F1b serializes starts through a stable lock path. The proposed cap adds an interruption path at a time when the entry may still be actionable. Specify what can be lost, verify the actual Linux process chain, and make timeout signals visible in `cron.log`. These edits keep the cron-only scope and require no `src/` change.

## Checks

1. **Writers and starts.** Searched `src/`, `scripts/`, `tests/`, `deploy/`, both workflows and all checked-in cron/systemd text. `cli.check_pick_entered` alone calls `_check_pick_entered`, whose `mark` writes the production filename. `health/pick_entry.py` reads it and tests seed it. The `ops` backup includes it and the restore drill copies it into an empty/new restore tree. Copying a restore into the live tree can also replace it. Two different `--picks-dir` values with the same parent share a marker. No dashboard, scheduler unit, timer, `day-outcome` or 03:00 pull/build/preview/sync path invokes the writer. Historical installer lines were tagged back to `4f13eb36`. A marked active/commented line disappears on install, an unmarked active line survives, and an unmarked comment survives without running. An old invocation can stay alive across an install or deploy. A second crontab or manual run can bypass the lock. The live crontabs were unavailable. [Install check](installer.log)

2. **Lock and limit.** Generated the `enter` line with the real installer's `show` and `test_entry_intent.py` fixture. Ran its shell command including prefix and redirects with absolute paths mapped to shims and a 1.2-second limit plus 0.2-second grace. A concurrent contender exited 1 in 22–24 ms, started neither timeout nor its command, and appended zero bytes. A normal child got TERM and the holder returned 124. When both stand-ins ignored TERM, KILL returned 137. The next invocation acquired the lock in both cases. With early wrapper exit plus a TERM-ignoring child, or a child in a new session, the monitor returned 124 yet another contender stayed blocked until the recorded child was killed. The generated arithmetic is `840 + 30 = 870 < 900` seconds, with 30 seconds of nominal margin.
   The real local `/usr/bin/timeout` is BSD-derived. It returned 124 with Homebrew `uv` 0.13.7 and a Python child that received TERM and inherited the lock descriptor. With TERM ignored by both stand-ins it returned 137. The follow-up acquired the lock. No wrapper output reached app `cron.log` except the test-only `uv --no-sync --no-project` warning and the intentionally bad lock-path diagnostic. The directory case reached the command, then the lock script stopped on its own assertion because its stand-in slept in that mode. The separate standing check verified directory and read-only file locks directly. [Lock checks and PIDs](lock.log) · [Standing checks](standing.log)
   Read the installed `timeout(1)` manual on group signals, grace and statuses, and used `fcntl.flock` for the local lock. No GNU `timeout`, util-linux CLI, or offline copies of their manuals were found here. Linux assumptions for the gate: util-linux uses a nonblocking exclusive lock, default conflict status 1, passes the descriptor to the command chain, and keeps the inode locked until the last referring descriptor closes. GNU `timeout` without `--foreground` signals the original process group, waits for its monitored child, returns 124 after handled TERM and normally 137 after group KILL. If the monitored child exits first, a surviving descendant can outlast the monitor and retain the descriptor. A new session can miss both signals. An uninterruptible kernel wait can delay exit even after KILL. App `cron.log` contains output written through the redirect, and Debian cron can separately log the launch according to its configuration. Default wrapper status alone writes no app log entry. The shell prefix and log open precede the lock and timer. Linux reference points for verification. [GNU timeout manual](https://www.gnu.org/software/coreutils/manual/html_node/timeout-invocation.html) · [flock(1)](https://man7.org/linux/man-pages/man1/flock.1.html) · [flock(2)](https://man7.org/linux/man-pages/man2/flock.2.html)

3. **Killed run.** Sent real TERM/KILL to the installed CLI with pinned ET and captured transports. Before and during fetch, after a successful or failed DM but before marker replacement, and during a partial marker write, the old marker bytes or absence survived. A marker temp remained after the partial write and both marker readers ignored it. During receipt writing the new, complete marker survived. A partial receipt temp and a renamed but unsealed JSON each remained invisible to discovery. After the seal rename the receipt counted. Killing the all-clear transport after the `confirmed` marker left a terminal marker referencing a missing receipt. The next run wrote an `already_confirmed` receipt referring to that ID, fetched nothing and sent no all-clear. Before marker replacement the next qualifying run uses the old tiers and may repeat an accepted DM. After replacement it uses the new tiers regardless of receipt publication. A completed `dm_failed` keeps its unsent tier retryable while due and in-window. [Signal checks](killed.log)

4. **K1–K5.** K1's six explicit M11/M12 cases and 144/1,728 ordered pairs/triples passed. K2 and K3 worked with path-mapped shims on POSIX and partly with real BSD tools. A single sleeping child doesn't test `uv` plus Python, group KILL, or retained descriptors. Both workflows use `ubuntu-latest`, pin uv 0.11.6 and run `uv run pytest -m "not slow"`. `test.yml` runs on PRs and pushes to main, and `deploy.yml` gates deploy unless its emergency dispatch skips tests. A new ordinary test file is collected by both. Their YAML doesn't check the binary paths. K4's archived order reproduced the false all-clear, and the archived assertion itself expects the observation to survive. Reversing it for a passing gate would reject a future fix. K5 holds for F1 command behavior on runs that can complete, with 173 selected F1/receipt/health/morning checks passed including both FIFO cases. The cap changes the effects of an installed run interrupted before completion. [F1 checks](f1-tests.log) · [FIFO cases](fifo-tests.log) · [Overlap replay](standing.log)

5. **Installer rows.** Searched for `cron-setup-hetzner`, `check-pick-entered`, `BTS-HETZNER`, `crontab` and `Would install`. Two files under `tests/` inspect generated cron. Ran both against a scratch copy with the exact proposed watchdog line. All 55 passed. Compared real `show` before and after under identical shims. Only the entry line changed. Installed twice over foreign, marked active/commented and unmarked active/commented lines, then removed it. [Scratch tests](installer-tests.log) · [Generated line](generated-cron.txt)

6. **Standing rows.** A missing parent is an open failure. A directory or existing readable mode-0444 file can be locked, as the local advisory lock check showed. Recheck util-linux's directory and read-only opens on Linux. A persistent capture FIFO can hang every applicable run, including receipt publication on the no-pick path. Neither a killed nor a skipped slot promises a morning DM. The actual report gave `entry_unverifiable` without bound evidence and a clean `entered_game_unverified` with an older timely match. A reboot releases process locks and can miss every slot while down. A cron or app restart has different process-lifetime effects. At 23:45 the nominal signals are 23:59 and 23:59:30. The date and capture season are anchored at CLI start in ET. The next day discards the old marker for tier decisions. UTC-dated captures can disagree with the ET year. Enumerated the spring and November ET transition days, each with 56 watchdog slots, all 900 seconds apart within the daytime window. The repeated/skipped early hour does not contain a watchdog slot. [Standing checks](standing.log)

7. **Ordinary loss cases.** With a 19:30 first pitch, the 18:15 slot can send `initial`, the 18:30 slot can observe a wrong game but time out during the warning before `mark`, and the 18:45 slot can see a conflicting capture and send a false all-clear. The signal check reproduced that serial order with the initial alert pinned at 18:25. A manual or untagged legacy run can still produce the archived overlap with the same result. A trickling response can finish 850 seconds into an 18:45 check with a 19:00 cutoff. The base sent its initial absence DM in the pinned case. The 840-second TERM ends that check and 19:00 is already outside the window. A hard stop during the all-clear send can leave the terminal marker without a delivered DM or sealed receipt. The base also sent an 08:30 `ENTRY UNVERIFIABLE` DM after its terminal wrong-game batter match. F1 continued checking and its later unbound match yielded clean `entered_game_unverified` while `game_unresolved` stayed true. Consecutive timeouts from a persistent FIFO, an unopenable lock, or an inherited descriptor held by a surviving process can suppress more than one slot.
