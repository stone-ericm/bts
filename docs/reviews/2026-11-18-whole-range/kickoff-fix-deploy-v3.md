## The design in one paragraph
A **root-owned guard** is installed once on the box by an explicit step (G1). It provides one durable **hold file** outside the checkout, `/var/lib/bts-deploy/hold`, and one tool, `/usr/local/bin/bts-deploy-hold` (Python 3 standard library, run by `/usr/bin/python3 -I`). While the hold file exists in any form, a **systemd drop-in** makes every start of `bts-scheduler.service` a clean skip (`ExecCondition=`), except a start inside the deploy's own short, same-boot canary lease; the four state-writing cron commands skip; monitoring and analytics jobs keep running; the heartbeat monitor pages. The deploy arms the hold before it changes anything, drains running writers, stops the old scheduler, resets, syncs, starts the candidate under the lease, runs the canary (now including the contest-state question for a box set to enter picks), and releases the hold only after every step and check has passed. Any failure, interrupt or lost controller leaves the hold in place with the scheduler stopped, and Eric is paged. There is no automatic rollback.

## Rows

### G1. The guard and its installation (an explicit root step; the deploy never installs it)
- `scripts/install-deploy-guard-hetzner.sh`, **self-contained** (it embeds the tool and the drop-in, so it can be fetched from git and run on a box whose checkout is older), run as root by Eric. It creates, idempotently: `/var/lib/bts-deploy/` (root:root 0755), `/var/lib/bts-deploy/writers.lock` (root:root 0644, empty), `/usr/local/bin/bts-deploy-hold` (root:root 0755), and `/etc/systemd/user/bts-scheduler.service.d/50-deploy-hold.conf` (root:root 0644):
  ```
  [Service]
  ExecCondition=/usr/bin/python3 -I /usr/local/bin/bts-deploy-hold check-clear --scheduler
  ```
  then reloads `bts`'s user manager (`runuser -u bts -- env XDG_RUNTIME_DIR=/run/user/<uid> systemctl --user daemon-reload`) and verifies that `systemctl --user show bts-scheduler -p ExecCondition --value` names that exact command and `-p NeedDaemonReload --value` is `no`. It prints each item as `installed`, `already current` or `FAILED: <reason>` and exits non-zero if any item failed or the verification did not pass. It never creates, edits or removes the hold file, never starts, stops or enables a unit, and never touches crontab. A `DESTDIR` environment variable (default empty) prefixes every path, for tests only.
- Root-owned under `/etc` and `/var/lib` so that the `bts` user (and any agent session running as `bts`) cannot remove or edit the hold or the guard; the drop-in lives in the system-wide user-unit directory so it survives a restore of `bts`'s home and is not in the checkout.
- **A box without the guard:** the new deploy refuses before changing anything (E1 `guard`); the new `cron-setup-hetzner.sh install` refuses (G7); a crontab already written by the new installer has guarded lines that fail closed (the tool or lock file is missing, so the job does not run); the scheduler unit without the drop-in starts as it does today (that is why the deploy refuses).
- The tool reports a protocol version (`bts-deploy-hold version` prints exactly `bts-deploy-hold 1`); the deploy refuses on any other output (E1 `guard`), so a changed tool needs a re-run of the install before the next deploy.

### G2. The hold record and the tool's commands
- The hold file is `/var/lib/bts-deploy/hold`. **Its existence as any directory entry (regular file, symlink, FIFO, directory, anything `os.lstat` succeeds on) is a hold.** Only the tool writes it, by a unique temporary file in `/var/lib/bts-deploy/` then `os.replace` (replaces a regular-file, symlink or FIFO entry without following or opening it; fails on a directory, which then stays a hold). Content: one JSON object, duplicate members rejected: `schema` `"bts_deploy_hold_v1"`, `deploy_id` (`<epoch>-<pid>`), `state` one of `pending`, `canary`, `failed`, `step` from the fixed vocabulary (E2), `target` (40 lowercase hex), `previous` (40 lowercase hex or `"unknown"`), `armed_at` and `updated_at` (integer UTC epoch seconds), `boot_id` (the content of `/proc/sys/kernel/random/boot_id` at the write), `lease_until` (integer epoch or `null`), `prior` (the previous record object if this arm replaced a readable one, else `null`). A record that is not a regular file, cannot be read within the size bound (8 KiB) without blocking, or fails any field check is **unreadable**: still a hold, reported as `unreadable`.
- Commands (root only unless marked; each prints one line per action and never prints `.env` content or any URL):
  - `version` (any user); `status` (any user, read-only): `no deploy hold` exit 0, or the record's state, step, target and previous (7 hex), armed time (UTC ISO) and whether a lease is in effect, exit 1; `unreadable` exit 1.
  - `check-clear --scheduler` (any user; the ExecCondition): exit 0 if no hold entry exists, or the record is readable with `state == "canary"`, the same `boot_id` as now and `now < lease_until`; exit 1 in every other case (including an unreadable record and a missing or non-directory `/var/lib/bts-deploy/`). Never exits with any other code by design (an uncaught exception exits 1: still a skip).
  - `run <name> -- <argv…>` (any user; the cron gate, `<name>` from `check-results`, `reconcile`, `fetch-contest-streak`, `nightly-preview`): opens `writers.lock` read-only, takes a SHARED `fcntl.flock` non-blocking, THEN checks for a hold entry. Held, lock busy, lock missing: prints `[<UTC ISO>] bts-deploy-hold: <name> skipped: <reason>` and exits 75 without running anything. Clear: `os.execv` of the argv with the locked descriptor inherited (so the shared lock lasts as long as the job's processes keep it open).
  - `arm --deploy-id --target --previous`: writes `pending` (keeping a readable prior record in `prior`); `drain --timeout <s>`: takes an EXCLUSIVE flock on `writers.lock` within the timeout and releases it (proof that every writer that passed the gate before the arm has exited); `abort --deploy-id`: only if the record is this deploy's and `pending`, restores `prior` (or removes the hold if `prior` is `null`); `canary --deploy-id --lease <s>`: `state = canary`, `lease_until = now + s`, current `boot_id`; `fail --deploy-id --step <step>`: `state = failed` with that step (writes a fresh `failed` record if the existing one is unreadable or another deploy's); `release --deploy-id`: removes the hold only if the record is this deploy's and `canary`; `release --by-hand --reason <text>` (G6); `expire-lease --deploy-id` (G4); `page --deploy-id --step <step> --stop <verified|unverified>` (E4 d).
- No date logic except UTC epoch seconds; no ET, no season.

### G4. The canary lease (a bounded on-box owner for the provisional start)
Before the candidate is started, the deploy sets the hold to `canary` with a 300-second, same-boot lease and creates a transient system timer as root, `systemd-run --unit=bts-deploy-lease-<deploy_id> --on-active=300 --timer-property=AccuracySec=1s /usr/bin/python3 -I /usr/local/bin/bts-deploy-hold expire-lease --deploy-id <deploy_id>`. `expire-lease` acts only if the hold is this deploy's and still `canary`: it sets `failed` with step `lease-expired`, stops the scheduler as `bts`, and sends the E4 page. So a lost controller (SSH drop, cancelled run, the action's timeout) during the canary leaves a stopped, held scheduler within about five minutes; a reboot during the lease starts nothing (the `boot_id` no longer matches). The timer does not survive a reboot (nothing to stop then). The success commit stops the timer (best effort; `expire-lease` is a no-op after the release).

### G5. Paging while the hold stands

- no hold entry: byte-identical output, exit code and pings to the base for every input, under a pinned clock;

### G6. Release by hand

```

No canary has certified this box. Nothing was started: the scheduler stays stopped until it is started deliberately or a deploy restarts it. The held cron commands run at their next scheduled times on the code checked out now (<7 hex>), and so does the scheduler if the box reboots.
```

### E3. The success commit
Only after every check passed: write the UTC stamp to a temporary file in `data/` as `bts` and rename it over `data/.last_deploy_iso` (step `stamp`; failure runs E4, the old stamp is untouched); then `release --deploy-id` (step `release`; failure runs E4); then stop the lease timer (best effort, never a failure); then print `Deployed <7 hex>` and the base's `CANARY PASSED — <7 hex> is live and healthy` between its separators; exit 0. The commit point is the release: an interrupt between the stamp and the release leaves the hold (paged, the lease stops the scheduler) with a new stamp; ledgered.

### E4. The failure function (each step attempted whatever happened before; each result recorded; never exits early)
(a) print `DEPLOY FAILED at <step> — requested target <7 hex>, previous SHA <old-or-unknown>. No automatic rollback was attempted. Recovery has not been verified.` and one `Check <name> failed (<status>).` per failed check; (b) `fail --step <step>` and verify with `status` that the hold reads `failed` → `Deployment hold: verified|unverified.`; (c) `systemctl --user stop bts-scheduler`, verified by `is-active` = `inactive` or `failed` → `Scheduler stopped: verified|unverified.`; (d) `page`: reads exactly one literal line `BTS_SCHEDULER_HEARTBEAT_PING_URL=https://…` from `/home/bts/projects/bts/.env` as a bounded regular file (never executed or sourced; missing, duplicate, non-`https` or a non-regular `.env` → not sent), one POST to `<url>/fail` with the E5 body, 10-second timeout, no redirect followed, accepted only on a 2xx answer → `Failure ping received HTTP 2xx: verified|unverified.`; (e) `Recovery procedure: INCIDENT.md §4.`; (f) no stamp; (g) `exit 1`. The dashboard is not touched. No `data/.heartbeat` marker is written (the monitor reads the hold; drafts 1 and 2's marker is dropped).

### E6. The canary's contest-state question (W17)
A new read-only command `bts deploy-canary --config <path>` (run by the workflow as `bts` from the checkout, `uv run --no-sync`, 60-second timeout, config `/home/bts/.bts-orchestrator.toml`):
- **"Set to enter picks"** means: `live_gate_problem`'s conditions in `bts.entry_intent` read on this configuration, i.e. the scheduler's effective delivery (`scheduler._pick_delivery_mode`) is `dm` or `public`, OR `[scheduler].entry_intent` is exactly `"enter"`; a configuration whose delivery cannot be determined (a `ValueError`), or that cannot be loaded, counts as set to enter picks (fail closed).
- Not set to enter picks (private delivery and any intent other than `"enter"`): prints `deploy canary: contest state not checked (delivery <d>, entry_intent <i>: not set to enter picks).` and exits 0.
- Set to enter picks: if `live_gate_problem(config)` reports a problem, prints `deploy canary: live configuration refused: <problem>` and exits 1. Otherwise calls the scheduler's live read, `contest_state.load_decision_streak_state(<orchestrator.picks_dir>, require_contest_state=True)`, at the real clock, exactly as the live path does: accepted → `deploy canary: contest state accepted for live picks (<observation kind>, streak <n>).` exit 0; `ContestStateError` → `deploy canary: no usable contest state for live picks: <first line, at most 300 characters>.` exit 1; any other exception → `deploy canary: contest state could not be read (<exception type>).` exit 1.
- Read-only: a test snapshots every file under the temporary state root before and after and finds them identical. It does not consult the hold.
- Consequence (Eric's choice; say it in INCIDENT and B8a): a deploy of a box set to enter picks FAILS, and leaves the hold, whenever the box has no usable contest state at that moment, for example on a dated-observation day before that day's observation is entered, or just after midnight ET before it is.

## Standing hostile-input rows
- **Interrupt mid-step:** the trap (E2) plus the durable hold: after any interrupt from `arm` onward the hold exists, so neither boot nor `Restart=always` starts the scheduler and the four writers skip; during the canary the lease bounds the candidate's run. An interrupt during preflight changes nothing.
- **Malformed or non-regular file:** the hold entry (row above), `writers.lock` (missing or non-regular: gate skips, deploy refuses), `.env` (bounded regular read, literal line only), `data/.last_deploy_iso` (renamed over; a directory there fails the stamp → E4).
- **Midnight ET and the year boundary:** the tool and workflow use UTC epoch seconds only. The contest-state question uses the loader's ET clock: just after midnight on a dated-observation day it can fail a live deploy (E6 consequence; the operator text says so). Test the canary command at 23:59:59 and 00:00:01 ET on a dated day and on December 31 / January 1 with a pinned clock.
- **A failed or unconfirmed send:** the POST is checked for a 2xx answer only; a failure is reported `unverified` and the monitor's next tick pages; no Bluesky DM is involved.
- **A restart mid-step:** a reboot at any boundary finds the hold; the scheduler is not started; the lease timer is gone with the boot and not needed.
