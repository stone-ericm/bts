## The material change (replaces draft 3's "design in one paragraph", G4, and E2 steps 7 to 10)
1. **One on-box transaction owner.** The workflow's SSH script does only what is needed to hand over: it checks that the guard is installed, writes the phase script it carries (the part of the YAML payload after the hand-over marker, byte for byte) to `/var/lib/bts-deploy/run-<deploy_id>.sh` (root, 0700), and starts it as a transient root unit: `systemd-run --unit=bts-deploy-<deploy_id> --collect --property=RuntimeMaxSec=1380 --property=TimeoutStopSec=120 --property=KillMode=mixed /bin/bash /var/lib/bts-deploy/run-<deploy_id>.sh`. The unit owns the whole transaction, from taking `/var/lib/bts-deploy/transaction.lock` (exclusive, held for the unit's lifetime) through the final status line. The SSH script then follows the unit's log file `/var/lib/bts-deploy/run-<deploy_id>.log` and its result file `run-<deploy_id>.result` (written last, by rename: `committed`, `failed <step>`, `not-started <step>`) with a bounded poll, prints the log, and exits 0 only on `committed`. Losing the SSH session does not stop the transaction; it finishes on its own and its result stays on the box. `appleboy/ssh-action` gets `command_timeout: 25m` in `with:` (its documented default is 10m); the unit's `RuntimeMaxSec` (23 minutes) is below it, so the owner ends first. When `RuntimeMaxSec` expires, systemd sends `SIGTERM` (to the main process first, `KillMode=mixed`) and the script's trap runs E4 within `TimeoutStopSec`; a later `SIGKILL` leaves the hold in place (fail closed; the monitor pages, G5).
2. **The production scheduler is never started before the commit.** There is no canary lease and no `canary` state: while the hold exists, `check-clear --scheduler` returns 1 in every case, so no caller (boot, dependency, `Restart=always`, an explicit start) can start production before the release. G4 is deleted.
3. **The candidate is certified by a read-only readiness check, `bts deploy-canary`** (E6 as replaced below), run by the owner as `bts` from the reset and synced checkout with the same interpreter, imports, configuration and state paths the scheduler uses, with no pick transport, grading, scheduling, state write or at-lock dispatch. The dashboard is restarted and checked before the commit (it is not held; its saver write is refused while held, G3).
4. **Commit, then activation.** After every check passed: release the hold (the commit), then start production (`systemctl --user restart bts-scheduler`), then the **activation check** (30 seconds, then the base's scheduler test read in ONE `show -p ActiveState,SubState,Result,ExecMainStatus` call: `active`, or exactly `activating`/`auto-restart`/`success`/`0`). Activation failure arms a NEW failed hold (step `activation`), stops the scheduler and pages (E4), exit 1. Only after activation passes: write the stamp (E3) and print `Deployed <7 hex>` and `CANARY PASSED — <7 hex> is live and healthy`.
   **Accepted cost (ruled):** during the 30 seconds of activation the new scheduler is live, exactly as during the base's canary; a pick sent in that window before an activation failure is not undone. The read-only check has already proved the candidate imports, reads its configuration and (when set to enter picks) has a usable contest state.
