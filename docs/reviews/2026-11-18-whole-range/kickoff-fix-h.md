## What is wrong on `main`
The reach-57 lookup returns skip at streak 57 or higher (`mdp._lookup_indices` returns no cell for `streak >= 57` or no days, so `lookup_action` and, since change set G, `lookup_action_guarded` both answer skip with no guard). Fresh selection and the display bar use that lookup when a usable base policy is loaded, and the heuristic when it is not. A 57 streak therefore never plays again with the shipped artifacts. Eric's objective from there is the longest streak possible.

## The design
1. **One constant.** `bts.simulate.tail_policy.LONGEST_STREAK_FROM = 57`. The new regime governs a state iff `streak >= LONGEST_STREAK_FROM` and the RAW slate day count (`strategy._days_remaining(date)`, today included) is at least 1. It is decided in `mdp_objective` (its only production caller is `strategy._regime`) from the streak and the raw day count, BEFORE the legacy horizon clamp and before any artifact is consulted. In this regime the day count used by the rule is the raw count clamped to a FIXED 180 (a constant of the rule, `LONGEST_STREAK_HORIZON = 180`), never the base artifact's `season_length` (a readable base with a bad `season_length` must not switch the regime off). The reach-57 and tail regimes keep their existing artifact horizon and date behaviour. At zero slate days the existing branch is used unchanged (skip with the shipped base; the heuristic can play without one). Nothing may depend on the boundary being 57 except through the constant; tests derive their ranges from it.
2. **The rule.** Objective: expected longest streak, uncapped, one quality bin, the current run assumed to be the best so far, any miss ending it. With p = the tail policy's `bin_p_hit[0]` and pb = its `bin_p_both[0]` (shipped 0.7336111111111111 and 0.5511111111111111): iterate in binary64 `g = 0`, then for each of the `d` effective days `g = max(p*(1+g), pb*(2+g), g)`; the action for `d >= 1` is the FIRST exact maximum in the order **single, double, skip** at the last step. New pure function `tail_policy.longest_streak_action(days: int, p_hit: float, p_both: float) -> str`. With the shipped rates: `double` for d = 1, 2, 3, `single` for d = 4 to 180 (the single/skip float tie that begins at day 116 resolves to single), never `skip`. For every valid one-bin pair of rates a play is a maximiser on every positive day, so the function never returns `skip` for `days >= 1`. It does not depend on the streak, the saver, the best streak or the candidate's probability.
3. **Where the rates come from.** The decoded, validated tail policy already in the decision context (`mdp["tail"]`), only when the base sha is non-empty and equals the tail's `base_policy_sha256` (the pairing check `_tail_action` makes) AND the tail has exactly one bin. In every other case (no artifacts, base unreadable, sha missing or mismatched, tail invalid, a tail with more than one bin, the rule function raising an `Exception`): the action is `single`, `degraded_reason` is `longest-streak rule unavailable (<why>); forced single`, and it is logged as the tail's forced fallback is. Never `skip`, never the reach-57 table, never the heuristic. `KeyboardInterrupt` and `SystemExit` propagate as they do through `_tail_action` today.
4. **The clamps are unchanged and come after:** `allow_double` false turns `double` into `single`; no executable different-game second pick turns `double` into `single`. `policy_action` keeps the rule's action and `action` the clamped one, both saved on the pick.
5. **The decision.** `PolicyDecision` in the new regime: `objective = "longest_streak"` (new constant `OBJECTIVE_LONGEST` in `tail_policy.py`), `source = "mdp"`, `streak`, `days_effective` (the clamped count the rule used), `best_supplied` as supplied, `best_status` the existing normalised value (`missing`, `trusted`, `untrusted`), `effective_best = None`, `guard = None` (change set G's field: the monotone skip guard belongs to the reach-57 lookup and is never consulted here), `tail_sha256` = the tail artifact's sha when its rates were used and `None` when degraded, `degraded_reason` as in item 3, `reason = None`, `pick_bar = None`. `daily_decision.OBJECTIVES` gains `"longest_streak"` (without it `write_decision` returns None and the day has no record). The journal line `Policy: objective=longest_streak …` appears through the existing `_log_policy_decision`.
6. **`effective_pick_bar`** in the new regime (positive raw days) returns `0.0`, with unusable artifacts too. The whole display operation, artifact loading included, is guarded against ordinary exceptions (it must never raise).
7. **Readers of `objective`** (each shown by a test or a probe to treat `"longest_streak"` as "not reach57"): `daily_decision.decision_objective` and `is_reach57_mdp_skip` (skip-policy shadow and census: excluded); `health/mdp_policy_alignment.py` (a pick with a finalized record is excluded); `scripts/audit/boundary_shadow_census.py` (excluded from the per-row comparison and the primary sample); `scheduler._selection_decision_meta` and the commit writers (recorded from the selection and from a saved pick's `policy_decision`); `scripts/audit/season_walk/walk.py` (records it).

## Known and not fixed (limits, each true as written)
1. **The state checks still refuse a streak or best above 57:** the dated observation's checks 5 and 6 and the dated CLI, the automatic file's active and best caps, the fetch's best cap, `classify_best_streak`'s trust cap, `picks._valid_chosen_on`. Raising them is change set H2 (R65), right after H. **Until H2, after a hit at 57 the fetch refuses the new reading and the last accepted automatic file (57/57) stays in use:** the rule keeps picking on the stale 57 (the action is the one it would choose at 58, the recorded streak is wrong) and nothing alerts until the reading is 14 hours old. **H is never deployed without H2** (R66); H2's contract carries "a refused reading above 57 must not leave a stale 57 silently in use" as a must-still-catch row.
2. **R33 across the boundary (R66: kept as it is).** A pick chosen on an automatic reading is delivered on a later automatic reading without comparing streak or saver. So a pick chosen at 57 under this rule can go out after a late settlement has moved the automatic streak to 0, where a fresh decision might be the tail's stop; and a pick chosen below 57 can go out after the reading reaches 57. The objective is the one selected at pick time.
3. With one bin the rule cannot wait for a strong day; it plays on every positive day with an eligible candidate.
4. The rule assumes the current run is the season's best and that any miss ends at it. A best above the streak is ignored (at the boundary it cannot occur while best is capped at 57; if the boundary moved to 56, a trusted best of 57 could exceed the streak).
5. Days are calendar days through the finale; off-days are not modelled ("3 or fewer days left" can be two game days). The rates are the tail policy's late-season rates applied all season, and the value calculation assumes both actions are available every day.
6. The decision record's slots follow the existing commit writer: on a single the runner-up is stored in `double_down` (W8), and a cached pick sent by the final fallback after an empty refresh can be recorded with a null primary or another refresh's state (the cases Eric accepted with G's merge on 2026-11-25; since G a refresh that made no decision records the saved pick's slots). H does not change the writer.
7. A named pipe at either policy artifact path hangs selection and the artifact health read, and a tail manifest with a malformed `bin_counts` can raise `TypeError` through the loader: both on the base today, not changed here (ledgered).
8. Readers not changed: the season-ledger tooling's own objective list (frozen: it normalises the new value to `unknown` and keeps the raw string); `bin_collapse_read.py` groups whatever string the ledger holds; `p05_tail_policy_audit.py` is a tool for the fixed 2026 window; bin alignment counts an H pick that has no finalized record yet; the census's all-flat sensitivity includes H rows and its artifact identity gate runs first.
9. Before a rollback to the base, outstanding H commits must be finished under H: the base rejects the write for an H saved pick.
10. At zero slate days with no base policy the heuristic can play (the base's behaviour).
11. With no eligible candidate at 57 the check's skip notice is `main`'s text for a check that made no decision, and that text is wrong in a way already recorded (`STOP-E.md`: it can call a candidate "below" a bar; with the 0.0 bar of this regime it can say a candidate is below a 0% bar). The corrected text (`No candidate was chosen …`) is in change set Ea, which is with Eric and not on `main`. H changes no operator text.
