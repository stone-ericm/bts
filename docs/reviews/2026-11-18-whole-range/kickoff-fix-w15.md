## Ruling W15-S1 (bts-wr-fresh4, lead's delegated design authority; Eric can overrule)
Not built here, ledgered in `CLAUDE.md` with their cost: (1) **R2 sync** keeps its behaviour (it uploads whatever cache is present, rotates two manifest generations, and blocks hashing a FIFO at the cache path): changing `sync.py` is its own change set; the unreadable alert tells the operator to secure a good R2 copy immediately (P6). (2) **Explicit live status root through every feature caller:** the producer keeps the path derived from the cache (`<cache dir>/../health_state`), which on the box is `data/health_state`, the same directory the health run reads with the default `picks_dir`; a configuration whose `picks_dir` parent is not the cache's data directory does not see the status (the box uses the defaults), and a backtest in the SAME checkout reads, reports on and may rewrite the live cache as it does today (its reports are true observations of that file). Cost if wrong: a non-default configuration gets no W15 alert; the stderr line still appears. (3) **Two writers racing** (a person's restore committed between a scanner's read and its rename is overwritten): the base's known limit ("two processes can lose each other's new entries"); the docs say a repair is staged and verified and cut over with the scheduler stopped and no feature run in progress.

## The defect (base `main`)
`bts.features.compute._build_probable_pitcher_lookup` loads `data/models/probable_pitcher_lookup.json` with `lookup = {int(k): v for k, v in cached.items()}` and returns it; `compute_all_features` reads `probable_pitchers.get(pk, {}).get("away")` (and `"home"`, `"away_tid"`, `"home_tid"`). A cache that parses as a JSON object but holds a non-object entry raises `AttributeError` in every feature run that evaluates a plate appearance of that game (training, the scheduler's prediction pass, the 03:00 preview, backtests) until a person removes the file; the game is already a key, so its feed is never rescanned. Invalid JSON, a non-object top level, or a key `int()` rejects already gives one stderr `WARNING: unreadable probable-pitcher cache …` line and a rebuild from the raw feeds present.

## What the base accepted (corpus; the check's table "Corpus and feature values" is part of this contract)
- **Real caches:** the main checkout's cache (5,095 entries) and the frozen `~/bts-runs/inputs/probable_pitcher_lookup.2017-2025.json` (20,087) hold only entries with exactly the four members, each an `int` or `null` (team ids never `null`); every key is decimal digits. The check reproduced lookup equality, both levels of key order, exact types, bytes, mtime and silent stderr on both.
- **What the scanner can write:** the four members from `gameData.probablePitchers.{away,home}.id` and `gameData.teams.{away,home}.id`, whatever JSON value the feed holds (the check made it write a string, a boolean, a float and an object id from a fixture feed; all 24 sampled official feeds gave integers).
- **What the base accepted that this change refuses** (the check's corpus table, shapes and fixture tuples): object entries with missing, extra, string, float (integral or not), boolean, array, object, `NaN` or infinite members. **Accepted loss:** dropping an extra-key entry or an integral-float entry can remove a usable pitcher or team (the base computed the right tuple for `51.0` and ignored extra keys); a game with no usable rescan then has no probable pitcher. This is the price of one exact rule. The author's first deliverable, BEFORE code, is the table of these shapes with base and after values on the check's fixture (`contract-check-w15/probe_features.py`), extended with the scanner-candidate shapes.

## Standing hostile-input rows
- **An interrupt mid-step:** P3's order (preserve, publish, replace) means an interrupt before the replace leaves the old cache; after it the evidence is already durable; during the replace, the base's case. A hard kill can leave an unreferenced temporary file.
- **A malformed or non-regular file:** the cache, raw feeds, the `rejected/` and status destinations, the status read, each as above.
- **Midnight ET and the year boundary:** `recorded_date_et` from `recorded_at` in `America/New_York`; records are per ET date, so a later day's record cannot hide an earlier one.
- **A failed or unconfirmed send:** inherited, best effort: a dispatcher failure is retried only when a later run presents the alert again; the failure banner counts CRITICALs only; an empty transport identifier can be marked sent by the ordinary end-of-day dispatch; a restart after a send and before its receipt can repeat the DM. The records are evidence, never receipts. Ledger in `CLAUDE.md`.
- **A restart mid-step:** the evidence order above; a bad member not yet rewritten is reported again.
