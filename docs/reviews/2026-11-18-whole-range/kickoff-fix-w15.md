## The defect (base `main`)
`bts.features.compute._build_probable_pitcher_lookup` loads `data/models/probable_pitcher_lookup.json` with `lookup = {int(k): v for k, v in cached.items()}` and returns it; `compute_all_features` reads `probable_pitchers.get(pk, {}).get("away")` (and `"home"`, `"away_tid"`, `"home_tid"`). A cache that parses as a JSON object but holds a non-object entry raises `AttributeError` in every feature run that evaluates a plate appearance of that game (training, the scheduler's prediction pass, the 03:00 preview, backtests) until a person removes the file; the game is already a key, so its feed is never rescanned. Invalid JSON, a non-object top level, or a key `int()` rejects already gives one stderr `WARNING: unreadable probable-pitcher cache …` line and a rebuild from the raw feeds present.

## What the base accepted (corpus; the check's table "Corpus and feature values" is part of this contract)
- **Real caches:** the main checkout's cache (5,095 entries) and the frozen `~/bts-runs/inputs/probable_pitcher_lookup.2017-2025.json` (20,087) hold only entries with exactly the four members, each an `int` or `null` (team ids never `null`); every key is decimal digits. The check reproduced lookup equality, both levels of key order, exact types, bytes, mtime and silent stderr on both.
- **What the scanner can write:** the four members from `gameData.probablePitchers.{away,home}.id` and `gameData.teams.{away,home}.id`, whatever JSON value the feed holds (the check made it write a string, a boolean, a float and an object id from a fixture feed; all 24 sampled official feeds gave integers).
- **What the base accepted that this change refuses** (the check's corpus table, shapes and fixture tuples): object entries with missing, extra, string, float (integral or not), boolean, array, object, `NaN` or infinite members. **Accepted loss:** dropping an extra-key entry or an integral-float entry can remove a usable pitcher or team (the base computed the right tuple for `51.0` and ignored extra keys); a game with no usable rescan then has no probable pitcher. This is the price of one exact rule. The author's first deliverable, BEFORE code, is the table of these shapes with base and after values on the check's fixture (`contract-check-w15/probe_features.py`), extended with the scanner-candidate shapes.

## Required
| # | Required |
|---|---|
| P1 | **Validity.** An entry is valid when it is a `dict` whose member names are exactly `away`, `home`, `away_tid`, `home_tid`, each value `None` or of exact type `int` (`type(v) is int`). The rule applies to each DECODED cache member and to each SCANNER candidate, without coercion. An invalid scanner candidate contributes no entry and does not count as a scan (it is counted `unusable_feed`, P4). A missing side object in a feed defaults as on the base (`pp.get("away", {})`); an explicit `null` or malformed side object that makes extraction raise is an unusable feed, as on the base. **Parity:** for a cache in which every member is valid, the returned dict equals the base's with both levels of key order and exact value types, nothing is printed, nothing is written, and the file's `st_mtime_ns` is unchanged when no usable new game is scanned. |
| P2 | **Decoding and recovery.** Keep the base's all-or-nothing path (the existing stderr line byte for byte, an empty starting lookup, a rebuild) for invalid JSON, a non-object top level, or any key `int()` rejects; it is reported as `unreadable_cache` (P4). For accepted keys, validate each decoded member before resolving integer aliases (`"1"`, `"01"`, `" 1"` all name game 1): the surviving value is the LAST valid alias, at the position of the FIRST alias of that game in the file (the base's position rule, so all-valid caches keep base parity); every invalid member is counted even when a valid alias survives (`recovered_from_cache`). A game with no valid alias is treated as missing: the existing raw search runs for it; the first usable candidate wins. A present feed that is rejected, malformed, unreadable or not a regular file, with no usable alternative, is `unusable_feed`; no feed at all is `without_feed`. A game with neither a valid entry nor a usable feed is absent from the lookup (the base's missing-game feature behaviour). |
| P3 | **No rewrite while the cache holds an invalid member (the design change).** The cache file is replaced only when (a) at least one usable game was newly scanned AND (b) no decoded member of this call was invalid. While (b) fails, nothing is written: the newly scanned games are used in memory only and are rescanned on the next call; the bad bytes stay on disk, so every later call drops and reports them again, a restart cannot lose the evidence, and an unrelated scan cannot erase it. The way back is a person's repair (P6, P7). **Unreadable cache:** the base's rebuild and rewrite stay (rewrite when at least one usable game was scanned), but the status (P4) is published BEFORE the replace; if publishing fails, the cache is NOT replaced (the corrupt bytes stay; the next call retries) and the usable lookup is still returned. The write path itself (temporary file, `os.replace`, cleanup, error propagation for a failed cache write) is unchanged. A call with nothing to report writes no status. |
| P4 | **Report: stderr and a status file per reason.** A call that drops at least one member prints ONE stderr line `WARNING: probable-pitcher cache <path>: dropped <n> invalid entr(y|ies) (<a> recovered from valid cache entries, <k> rescanned from raw feeds, <u> with unusable feeds, <m> without feeds); first game ids: <up to 10 sorted distinct normalized ids>` (`a+k+u+m = n`). The unreadable path keeps its existing line byte for byte. One file per reason, latest call wins (an `invalid_entries` report cannot overwrite an `unreadable_cache` one; a persistent bad member is re-recorded by every call, P3). **Write rules:** an exclusive fresh temporary file (`O_CREAT|O_EXCL`, random name) in the same directory, written, closed, then `os.replace`; an existing destination that `lstat` shows is not a regular file (directory, FIFO, symlink) is a write failure, never replaced; no wait on any lock or FIFO; any failure prints `WARNING: could not write probable-pitcher cache status at <path> (<ExceptionName>)` and continues (P3's unreadable rule then keeps the old cache). ## Raw-feed discovery and files (adopted from the check)
- Open the cache and each raw feed non-blocking and check the opened descriptor is a regular file: a special cache is `unreadable_cache` and is left in place: a special file at the cache path is never replaced, even when a scan found usable games (an exception to P3's unreadable rewrite); a special feed is `unusable_feed`. Reading a symlink to a regular cache keeps working, and a successful rewrite of an unreadable cache replaces the link as on the base.
- A raw root that is not a directory is "no raw feeds" (no raise); the report is still published. A file name that passes `isdigit()` but fails `int()` (`².json`) is skipped; the base's eligibility rule for signed names stays (`-100.json` is ignored). An inaccessible season directory or feed that prevents a lookup counts as `unusable_feed`.

## Standing hostile-input rows
- **An interrupt mid-step:** invalid members: nothing is written, so an interrupt anywhere loses nothing (the next call reports again). Unreadable: an interrupt before the status rename leaves the old cache (nothing replaced); after it and before the cache replace, the status stands and the old cache stays; during the cache replace, the base's case (temporary file cleaned, previous cache intact). A hard kill can leave an unreferenced temporary file; the active files stay complete.
- **A malformed or non-regular file:** the cache, the raw feeds, the status destination and the status read, each as in the rows above.
- **Midnight ET and the year boundary:** `recorded_date_et` from `recorded_at` in `America/New_York`; the health window is the processed day and the day before.
- **A failed or unconfirmed send:** inherited, best effort: a dispatcher failure is retried only when a later run presents the alert again (the daily re-recording of a persistent bad member does that); the failure banner counts CRITICALs only; an empty transport identifier can be marked sent by the ordinary end-of-day dispatch. The status file is evidence, never a receipt. Ledger these in `CLAUDE.md`.
- **A restart mid-step:** the bad member is still on disk and is reported again (P3).
