Written 2026-11-20 by `bts-wr-fresh3` on Eric's decision of 2026-11-20 12:50 (`FINDINGS.md`): *"drop bad entries with a warning the system or i can react to"*. Tier A (a model-feature input). Author's run rules as in `kickoff-fix-deploy-v3.md` ("Author's run rules"), with worktree `~/projects/bts-work/wr-fix-w15` and branch `fix/wr-w15`. **If an existing test's assertion would change, STOP and ask, naming the test.**

## The defect (base `main`)
`bts.features.compute._build_probable_pitcher_lookup` loads `data/models/probable_pitcher_lookup.json` with `lookup = {int(k): v for k, v in cached.items()}` and returns it; `compute_all_features` then reads `probable_pitchers.get(pk, {}).get("away")` (and `"home"`, `"away_tid"`, `"home_tid"`). A cache that parses as a JSON object but holds an entry that is not an object (`null`, a number, a string, a list) raises `AttributeError` in every feature run (training, the scheduler's prediction pass, the 03:00 preview, backtests) until a person removes the file. Because the game is already a key, the scanner never rescans its feed. A non-object top level, a key that `int()` rejects, or invalid JSON is already handled: one stderr `WARNING: unreadable probable-pitcher cache …` line, and the cache rebuilt from the raw feeds present.

## What the base accepted (the corpus, measured before the contract)
- **Real caches:** the main checkout's cache on the studio (5,095 entries) and the frozen `~/bts-runs/inputs/probable_pitcher_lookup.2017-2025.json` (20,087 entries) hold ONLY entries whose members are exactly `away`, `home`, `away_tid`, `home_tid`, each an integer or `null` (`away` `null` 8 and 12 times, `home` `null` 13 and 6 times; the team ids are never `null`). Every key is decimal digits.
- **What the scanner writes:** exactly those four members, from `gameData.probablePitchers.{away,home}.id` and `gameData.teams.{away,home}.id` (whatever JSON value the feed holds; a feed whose `probablePitchers.away` is `null` raises inside the scan and is skipped).
- **What the base accepted without raising that this change refuses:** an object entry with a missing, extra or non-integer member (for example `{"away": "123", …}`, `{"away": true, …}`, `{}`, an entry with a fifth member). The base used such a value as it stood (a missing member reads as no probable pitcher; a boolean `true` compares equal to pitcher id 1). The author's first deliverable, BEFORE any code: a table of these shapes with, for each, the base's `_is_reliever_pa`, `_probable_pid` and team-id values on a small fixture and the values after the change (rescanned from the feed, or no probable pitcher when the feed is absent). The contract check rules on it.

## Standing hostile-input rows
- **An interrupt mid-step:** an interrupt between the drop and the status write leaves no status (the next run reports again, the entry still being on disk) or a complete status (written by rename); between the scan and the cache write it is the base's case (temporary file cleaned, previous cache intact).
- **A malformed or non-regular file:** the cache (base handling, now also reported), the status path (P4 write failure row), a raw feed (base: skipped by the scan's `except`).
- **Midnight ET and the year boundary:** `recorded_date_et` is computed from `recorded_at` in `America/New_York`; the health window is the processed `today` and the day before; test a drop at 23:59 and 00:01 ET and on December 31 / January 1.
- **A failed or unconfirmed send:** the DM goes through the existing dispatcher (a failed send is retried by its existing failure-banner rule); the status file is evidence, not a receipt.
- **A restart mid-step:** the feature run is restarted with the scheduler; the bad entry is still on disk and is dropped again (P3), so a restart cannot lose the report.
