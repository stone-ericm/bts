## Blocking findings

1. **A same-cycle pick can go out after its dated observation has changed.** On March 24 at 18:25 ET, two synthetic candidates at 99% and 98% produced a double at streak 0. The real `set-contest-streak` command corrected the dated observation to streak/best 30 just after the pick save and before the delivery read. The scheduler sent the double by DM and both `bts run` and `bts orchestrate` posted it publicly. All three messages said `Streak: 30`. When the correction preceded selection, each sent a single with the same predictions. The scheduler also sent the double when the first read was a 20-hour-old automatic observation and the second was dated. The resulting pick had `chosen_on.kind = automatic`, a null `automatic_reading`, and no stale warning. This makes a late correction capable of allowing a wrong send during the very cycle that rereads it. `interactions.py`, `fresh_correction_race`. The smallest fix is to compare the chosen-on identity with the final accepted snapshot on every live outward path when either snapshot is dated. Use the existing refusal on a mismatch and preserve the automatic-to-automatic rule. `src/bts/scheduler.py:1253–1280`, `src/bts/cli.py:1262–1272`, `src/bts/orchestrator.py:438–449`.

2. **A later check can strand an eligible saved pick before fallback runs.** At 18:20 ET the day already had a required-read pick for game 101 at 19:10, with the exact same dated observation still in effect. Neither lineup cascade returned predictions. The 18:25 check slept directly to the 19:25 check for game 102, passing the 18:35 fallback deadline and the 19:05 cutoff. The later check archived the saved pick. There was no fallback prediction, pick DM, missed-pick DM, or decision. The one-game control ran final fallback at 18:35 and delivered the same saved pick even though its refresh also returned nothing. `interactions.py`, `deadline_starved_by_later_check`. The smallest fix is to compute the deadline from a still-eligible on-disk candidate when a check returns no pick. Wake for fallback before any later check beyond its deadline and run the normal final state and delivery guards. `src/bts/scheduler.py:260`, `:1825–1841`, `:3097–3129`, `:3293–3333`.

3. **The fallback that should reuse an overrun check starts a second cascade.** On an ordinary 10:00 start with a one-game slate, the two early checks returned nothing and the 18:25 check returned a valid projected pick at 19:00. `run_single_check` computed `LockDecision` but omitted it from the returned dict. The in-loop fallback started another cascade at 19:00, returned empty at 19:06 and archived the pick after the 19:05 cutoff. The first result had five minutes left to send. The health DM went out only after the cutoff. The missing producer predates this range, but the failure occurs without the restart described in the accepted 5b risk. `interactions.py`, `overrun_double_cascade`. The smallest fix is to return the computed `lock_decision` from the normal successful check so the guarded reuse branch can run. Keep the final state and cutoff checks. `src/bts/scheduler.py:1957–1978`, `:3145–3163`.

4. **The scheduler and the new day watchdog both accept a malformed schedule as an off-day.** A successful HTTP response body `{"message":"synthetic upstream error"}` got the same result as the valid `{"dates":[]}` control. The scheduler printed `No games scheduled`, idled before contest-state monitoring and wrote no day state. `day-outcome` exited 0 with `no_games` and sent no alert. `refusals.py`, `malformed_schedule`. The smallest fix is to require a list-valued `dates` field and valid `games` lists in date entries in the shared schedule parser. The watchdog already reports an exception as `schedule_unverifiable`. `src/bts/scheduler.py:284–296`, `src/bts/day_outcome.py:146–155`.

## Findings that need an owner decision

- **A refused preview can disable season replay indefinitely.** A March 24 preview refused at final fallback stayed as an unresolved root pick. `check-results` correctly skipped it as uncommitted. At 02:00 the next day, and again after a March 25 hit and on July 1, `reconcile` exited 0 and printed `No scoring changes detected` while keeping the planted bad streak, now 20. The receipt said `replay.state=unavailable`. Archiving just the refused preview let replay rebuild 1. This removes the documented recovery path for corrupt model state and prevents the model saver/counter from incorporating corrections. Live contest state remains authoritative. Choose whether to archive definitively refused candidates at finalization or teach replay to exclude provably uncommitted unresolved picks. Print an explicit warning for incomplete replay, preserving the distinction from an unresolved scoreable pick. `clocks_and_scoring.py`, `refused_preview_blocks_replay`. `src/bts/picks.py:826–862`, `:1509–1514`, `src/bts/cli.py:2748–2755`, `:2917–2923`.
- **A valid JSON cache with an invalid entry can fail every prediction using it.** On cold start with historical parquet and only spring raw feeds online, changing one historical entry to `null` caused two feature runs to raise `AttributeError` at the same mapping, with no cache warning or repair. An unreadable JSON file did warn and recover from the available spring raw feeds, losing historical bullpen coverage as documented. The `null` case requires bad preexisting data or another writer. A local tier reports the prediction error in the journal. Apply entry-shape validation and recover valid entries if that file shape is in scope for restore protection. `cold_features.py`. `src/bts/features/compute.py:59–79`, `:473–480`.
