**Status:** DRAFT v3 (incorporates Codex design reviews r1 `w06b-profile-campaign-design-codex.md` and r2 `w06b-round-campaign-design-codex.md`; both BLOCK sets addressed below; not yet re-reviewed) · **Owner rulings (verbatim):** "i mean i want to grab all the picks all the public profiles (i assume 95000+)" · "i'm mildly concerned that once the season ends the leaderboard and the picks listings will be unavailable. what if we did an initial capture today and then ran a supplemental capture around 9/28 to fill in the last days?" · **Exposure:** accepted by the owner (MLB ToU §1(xi) prohibits automated collection; the season is over; next-season account standing is the risk). Hygiene only, no evasion.

## 1. What is being captured, and from where
MLB's per-round leaderboard (`LEADERBOARD_ROUND_URL_TEMPLATE`: `/api/rank/leaderboard/round/{round_id}?page&limit&usersType=ALL&ranksType=ACTIVE_STREAK&xSid=`) lists that round's participants; **each rank row carries a `predictions` object** `{roundId, result, streak, streakIncrease, roundPredictions:[{number, unitId, playerId, result, hits, atBats}]}`. A full-depth walk of one round's board therefore yields every *listed* participant's slots for that round. Facts from the real 2026-05-01 round-859 fixture: 100 rows, `allParticipantsCount` 70,061, `nextPage` true; **86 users with slots, 139 slots, 14 rows with void/empty predictions**; ranking `streak` (34) ≠ post-round `predictions.streak` (35) and `streak == predictions.streak − streakIncrease` for all 100 rows. Season 2026 has 187 rounds (ids 823→1009; 9/21 = 1003, 9/22 = 1004, 9/27 = 1009). Today's season board reports 121,625 participants (a round board will list fewer: only that round's participants).

**What this does NOT establish (r2 BLOCK 1):** that every picker is listed (zero-streak entrants? users below some floor?), that old rounds are still served in full, or that `limit=300` behaves on the round endpoint. These are the pilot's questions.

## 2. Units, states, outputs
- **Target list** `campaign/targets.v1.json` (+ sha256): all 2026 rounds from the archived `rounds.json` whose round date ≤ the last COMPLETED date, ordered **newest → oldest** (r2: preserves the latest completed snapshot first). A supplemental later (after 9/27) is `targets.v2.json`, a versioned EXTENSION (new rounds appended + previously incomplete rounds listed for a fresh attempt); never a silent rewrite.
- **Unit of work** = one round attempt: `data/leaderboard/round_campaign_2026/round_<id>/attempt_<n>/` (immutable once closed): `plan.json`, `status.json` (per-request intent/outcome as in the signed walker), `raw/page_NNN.json.gz` (scrubbed bytes; wire sha256 and archived sha256 both recorded), `manifest.json` (written last; acceptance predicate below), `participants.parquet`, `slots.parquet`, `rejected_records.parquet`.
- **Round states** (ledger): `pending` → `in_flight` → {`complete` | `incomplete` (walk ended by error / no-progress / repeated page / contradiction) | `paused` (window/budget/operator stop mid-walk) | `quarantined` (ambiguous in-flight receipt; blocks the WHOLE campaign until reconciled) | `halted` (campaign halt)}. `paused`/`incomplete` never auto-continue a partial walk: a new **attempt** re-walks the round from page 1 (server pagination is not resumable across time), explicitly accounted, only after reconciliation, at most one automatic re-attempt per round and only for classified transient terminations (5xx/transport/no-progress); never after rejection.
- **Campaign states:** `running`, `paused_window`, `paused_budget`, `halted_rejection` (403/429/401/redirect/challenge/auth-error envelope), `halted_errors` (rolling ≥10 errors in 50 or 3 consecutive), `halted_operator`, `quarantine_pending`, `complete_targets_v<n>`.

## 3. Durability contract (r1 BLOCK 1–3, r2 BLOCK 3–4)
- **Ledger** = SQLite (`campaign/ledger.sqlite`, WAL), single writer via `flock` on `campaign/lock` acquired BEFORE credentials. Tables: `campaign_state`, `rounds`, `attempts`, `requests` (receipt rows), `halts`, `resumes`, `day_totals` (ET date → requests/logins/errors), `versions` (code sha, uv.lock sha, targets sha, config sha).
- **Receipt at headers:** the transport records `(attempt, seq, status_code, received_headers_at)` into `requests` and COMMITS before reading the body; body read/archive/parse update the row afterwards. A 403/429/401/3xx or an auth-error-shaped 200 body sets `halts` (reason, seq) in the SAME transaction as the receipt, before any DM. DM failure never unblocks.
- **Startup reconciliation:** any `requests` row without a terminal outcome → its attempt becomes `quarantined` and the campaign refuses to send until a human writes a `resumes` row (reason, who, when). Missing/corrupt ledger → refuse (exit 5). Resume also requires: same targets sha (or an explicit `targets.v<n+1>`), same code sha or an explicit `resumes.code_change_ack`.
- **Pre-send checks** every request: campaign state `running`, inside the window, ET-day cap not reached, no halt row, lock still held; recheck after every sleep. Window/budget stop mid-walk → attempt `paused` (in-flight receipt completed first), campaign `paused_*`; the next segment starts a NEW attempt for that round.
- **Acceptance predicate** for `manifest.json` (an attempt is `complete` only if ALL hold): walk exhausted (`short_page` / `next_page_false`) · every page had valid `allParticipantsCount` + `updatedAt` and they were constant (`endpoint_list_census` if listed unique == reported) · zero duplicate-payload conflicts (full `predictions` compared, not rank/streak only; conflicts → `incomplete`) · every request receipt terminal · wire+archived hashes recorded for every page · extractor ran with zero *unexplained* rejections (rejected records are listed with reasons; they do not block completion but are reported) · producer/parser version + config sha + lookup hashes bound. A round is `complete` iff its latest attempt's manifest passes; skipping a round on resume requires re-verifying the manifest hashes against the files.
- **Process-death tests** at: intent written / request sent / headers received / body read / raw archived / status flushed / manifest written; concurrent start (second process refused by lock); disk full; DM failure; day-boundary restart; interruption on the terminal page; halt file/row precedence.

## 4. Extraction (r2 BLOCK 2) — `bts/leaderboard/round_extract.py`, strict, tested
Per rank row → one **participant-round** record (user_id, username, rank, ranking_streak, active_streak, post_round_streak, streak_increase, round_result, n_slots_raw, has_slots, void_or_empty flag, page, page_seq, raw wire sha) so zero-slot observations survive; per slot → one **slot** record (user_id, round_id (must equal the requested round), slot_number ∈ {1,2} unique per user-round, unit_id > 0, player_id > 0, result ∈ {hit, not_hit, void, pending?} (enum recorded; unknown → rejected), hits ≥ 0, at_bats ≥ 0 when result is settled; batter/game names resolved from the archived lookups with `lookup_miss` flags). Anything violating the rules → `rejected_records` with a reason code; never coerced. Revisions across attempts reconcile on `(user_id, season, round_id, slot_number)`, conflicts retained.

## 5. Pacing, limits, coordination (r1 BLOCK 2; r2 SHOULD)
- Jittered gap 3–8 s between page requests; 60–180 s pause between rounds; daily window 08:00–22:00 ET; ET-day request cap default 8,000 (a ceiling, not a target); one login per segment start (planned request; never a re-login after rejection). No completion date is promised.
- **Pilot first:** ONE observed round (the latest completed, 1003) with limit 300 → inspect latency, page sizes, participant/listed counts, void/empty share, retention of an OLD round (second pilot: round 823 from 3/25) before any expansion. Expansion only after a human reads the pilot memo.
- Account-wide coordination: the campaign's login is one more authenticated consumer next to the 4×/day `fetch-contest-streak` cron and the static captures; the `day_totals` count all campaign requests; the cron schedule is recorded in the plan (no change to it).
- Disk/response bounds: page bodies bounded (reject > 5 MB), free-disk check before each round (≥ 5 GB reserve), inode check.

## 6. Coverage and analysis contract (r1 BLOCK 4–5; r2 BLOCK 1)
Per round: reported participants, listed unique users, users with slots, void/empty rows, slots raw/resolved/rejected, conflicts, lookup misses, walk termination, metadata consistency; `endpoint_list_census` ∈ {true,false,unknown}; `all_pickers_coverage = unknown` (cannot be established from the endpoint alone; the pilot compares against known saved picks: Eric's own contest ledger and the 5/01 top-100 fixtures). Campaign summary: rounds complete/incomplete/paused/quarantined, per-round counts, day totals, halts/resumes history. W2 estimands are stated over *listed participants with slots per round*, with missingness by rank/date; no claim about unlisted participants.

## 7. Backup (r1 SHOULD)
Sealed checkpoints: quiesce (no segment running) → SQLite backup API copy + manifests → tag-isolated restic snapshot → restore into an empty root → verify hashes + accounting + halt state. The daily `archive` set still covers `data/leaderboard/` in between.

## 8b. Learned from the 9/22 season-board capture (feeds the pilot)
- The season board lists only users with season best ≥ 4 (72,600 of a header count of 121,625): a **listing floor** exists; round boards may have their own floor (e.g. only that round's pickers, or only non-zero streaks) — the pilot must measure it.
- The EMPTY terminal page reported a different `allParticipantsCount` (54,293) than every full page (121,625) with a constant `updatedAt`: the census predicate must evaluate metadata consistency over FULL pages and record the terminal page's metadata separately (otherwise every exhausted walk is "drift").
- Observed pace ≈ 7 s/request end-to-end (2–4.5 s jitter + 3–4 s server latency); page bodies ≈ 67 KB gz; 300 profiles ≈ 35 min; profile histories retained the whole season (3/25→9/21) for all 300.
- 67,548 distinct usernames for 72,600 user ids: usernames are NOT identifiers (≈5k collisions) — id-keyed everything.
